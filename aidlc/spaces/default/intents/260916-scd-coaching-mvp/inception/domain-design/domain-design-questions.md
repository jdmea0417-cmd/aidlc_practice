## Q1. 목표 추천(A5)과 다음 코칭 추천(C1)은 어느 컴포넌트가 가집니까?

도메인 모델에는 추천 엔티티(`Recommendation`)가 하나뿐인데 `[spec:04]`, 실제로 추천은 두
곳에서 다른 규칙으로 만들어집니다 — 리포트 직후 목표 선택 화면(A5)의 추천 목표 1~3개(FR6.1)와,
기록 화면(C1)의 다음 코칭 추천(FR8.5, Must 는 "가장 최근 어려움 하나" — D-78) `[req]`. 기술 명세의
패키지 구조는 추천을 `record/` 에 두었습니다 `[spec:02]` §6. 하나로 두면 두 규칙이 한 곳에 섞이고,
나누면 엔티티가 둘이 됩니다.

- A. 하나의 추천 엔티티를 기록(Record) 컴포넌트가 가진다 — 명세 패키지 구조 그대로. 리포트 쪽 목표 추천도 Record 에 요청한다
- B. 둘로 나눈다 — 목표 추천(A5)은 평가(Assessment)가, 다음 코칭 추천(C1)은 기록(Record)이 가진다
- C. 둘 다 연습(Training)이 가진다 — 추천의 결과가 곧 연습 목표이기 때문이다
- D. 하나의 추천 엔티티를 평가(Assessment)가 가지고, 기록(Record)은 읽기만 한다
- X. Other (please specify)

[Answer]: C. 둘 다 연습(Training)이 가진다 — 추천의 결과가 곧 연습 목표이기 때문이다

## Q2. 판정의 버전 정보(기준·프롬프트·모델·전사 버전)는 어떻게 둡니까?

도메인 모델은 버전 정보를 별도 엔티티(`VersionInfo`)로 두고 판정·시도가 그것을 가리키게
했고 `[spec:04]`, 패키지 구조는 "버전 이력"을 기록(Record) 쪽에 두었습니다 `[spec:02]` §6.
그런데 버전 정보를 쓰는 쪽은 판정을 만드는 평가(Assessment)와 연습(Training)이고, 기록(Record)은
판정을 읽어 추이를 만듭니다. 명세대로면 Assessment → Record(버전 저장)와 Record → Assessment(판정
조회)가 서로를 부르는 **순환**이 생깁니다. 한편 팀 관행은 세 버전 값을 값 객체 하나로 묶고
판정 테이블에 `NOT NULL` 컬럼으로 두기로 했습니다 `[practices]` Code Style.

- A. 별도 엔티티를 두지 않고, 버전 값을 판정·시도에 함께 저장하는 **값 객체**로 둔다 — 순환이 없어지고 팀 관행과 맞는다. 버전 "이력" 조회는 판정을 읽는 쪽이 모아 보여 준다
- B. 명세대로 별도 엔티티를 기록(Record)이 가지고, 두 컴포넌트가 서로 부르는 순환을 의도적으로 허용한다
- C. 별도 엔티티를 두되 평가(Assessment)가 가진다 — 연습(Training)은 Assessment 를 통해 저장한다
- D. A 와 같되, 모델·프롬프트 목록 같은 버전 목록표는 별도 참조 데이터로 둔다
- X. Other (please specify)

[Answer]: A. 별도 엔티티를 두지 않고, 버전 값을 판정·시도에 함께 저장하는 **값 객체**로 둔다 — 순환이 없어지고 팀 관행과 맞는다. 버전 "이력" 조회는 판정을 읽는 쪽이 모아 보여 준다

## Q3. 모의 대화 시도의 판정은 누가 만듭니까?

리포트의 판정은 평가(Assessment)가 전사를 분석해 만들고, 모의 대화 시도의 판정은 연습(Training)
안에서 시도마다 만들어집니다(Mock 은 시나리오별 키워드 규칙) `[spec:06]` §3. 평가용 프롬프트와
코칭용 프롬프트는 파일·버전을 분리하기로 되어 있고 `[constraint]` TC-09, 기록 추이는 실제 대화
판정과 모의 대화 판정을 함께 읽되 섞지 않아야 합니다(FR8.2) `[req]`. 도메인 모델은 두 판정을
같은 판정 엔티티(`BehaviorJudgment`, mode REAL/ROLEPLAY)로 둡니다 `[spec:04]`.

- A. 연습(Training)이 시도 판정을 만들되, 저장은 평가(Assessment)가 가진 같은 판정 엔티티에 Assessment 의 인터페이스로 한다
- B. 판정은 전부 평가(Assessment)가 만든다 — Training 은 시도를 넘기고 결과를 받는다(코칭용 프롬프트도 Assessment 가 호출)
- C. 연습(Training)이 자기 시도 판정 엔티티를 따로 가진다 — 기록(Record)이 두 엔티티를 함께 읽어 추이를 만든다
- D. A 와 같되, 판정 규칙(분모·보류·근거 검증)은 공유 도메인 규칙 모듈로 두고 두 컴포넌트가 함께 쓴다
- X. Other (please specify)

[Answer]: A. 연습(Training)이 시도 판정을 만들되, 저장은 평가(Assessment)가 가진 같은 판정 엔티티에 Assessment 의 인터페이스로 한다

## Q4. 사용자, 첫 방문 동의, 보호자 초대·권한은 어느 컴포넌트가 가집니까?

패키지 구조에는 사용자나 계정을 담는 자리가 없고, `privacy/` 가 "공유 권한, 삭제 요청"을
가집니다 `[spec:02]` §6. 그런데 이번에 새로 들어온 것들 — 첫 방문 동의를 사용자 단위로 서버에
저장(AC1.1.3), 보호자 계정과 초대 코드(FR14.2), 정식 로그인(FR13, Should) — 의 주인이 없습니다
`[stories][req]`. 데이터 모델은 이 개념을 처음부터 갖춰야 합니다(FR11.2).

- A. 개인정보(Privacy)가 모두 가진다 — 사용자, 동의, 보호자 연결·초대, 열람 권한, 삭제 요청
- B. 새 계정(Account) 컴포넌트를 만든다 — 사용자·동의·로그인·보호자 계정과 초대는 Account, 열람 권한과 삭제 요청은 Privacy
- C. 새 계정(Account) 컴포넌트는 사용자·동의·로그인만 가지고, 보호자 초대·열람 권한·삭제 요청은 Privacy 가 가진다
- D. B 와 같되 Account 는 Should 기능(로그인·보호자 계정)이 생길 때 만들고, Must 동안에는 사용자·동의를 Privacy 에 둔다
- X. Other (please specify)

[Answer]: B. 새 계정(Account) 컴포넌트를 만든다 — 사용자·동의·로그인·보호자 계정과 초대는 Account, 열람 권한과 삭제 요청은 Privacy

## Q5. 대화를 삭제할 때 연결된 데이터 지우기를 어떻게 전파합니까?

단일 백엔드로 바뀌면서 삭제 전파가 새어 나갈 위험(R3)은 이 단계가 계층 경계로 닫기로 되어
있습니다 `[constraint]` TC-14. 팀 관행에는 잠정 규칙이 있습니다 — 삭제 진입점은 개인정보(Privacy)의
삭제 유스케이스 하나, 각 컴포넌트는 자기 테이블 정리 함수를 노출, 순서는 파일 삭제 → DB 행 삭제,
FK 연쇄 삭제는 그물로만 `[practices]` Code Style. 삭제 목록에는 맥락과 "분석이 이상해요" 요청이
추가되었고, 목표·추천은 사용자가 유지를 고르면 원본 연결만 비웁니다(US8.1·US8.2) `[stories]`.

- A. 잠정 규칙을 확정한다 — Privacy 의 삭제 유스케이스가 각 컴포넌트의 정리 인터페이스를 순서대로 부르고, 한 트랜잭션 안에서 DB 행을 지운 뒤 커밋 후 파일을 지운다
- B. A 와 같되 파일 삭제를 DB 커밋 **전에** 한다(잠정 규칙의 "파일 → DB 행" 순서 유지) — 실패하면 DB 행이 남아 다시 삭제할 수 있다
- C. Privacy 는 "대화 삭제됨" 사건만 알리고, 각 컴포넌트가 그 사건을 받아 자기 데이터를 지운다(프로세스 안 사건)
- D. DB 의 FK 연쇄 삭제를 주 수단으로 삼고, Privacy 는 파일 삭제와 목표·추천 선택 처리만 맡는다
- X. Other (please specify)

[Answer]: A. 잠정 규칙을 확정한다 — Privacy 의 삭제 유스케이스가 각 컴포넌트의 정리 인터페이스를 순서대로 부르고, 한 트랜잭션 안에서 DB 행을 지운 뒤 커밋 후 파일을 지운다 — 확인 필요 → Q9 (팀 관행의 파일 → DB 순서와 승인된 AC8.1.4 와 부딪힘)

## Q6. 재분석으로 생기는 "분석 회차"를 어떻게 모델링합니까?

재분석은 새 판정을 추가하고 이전 판정은 "대체됨"으로 남기며(AC3.3.3), 집계는 재분석 전에는
이전 판정을, 재분석 후에는 새 판정만 셉니다(D-74). 분석 중 다시 누르면 두 번째 회차가 생기지
않아야 하고(AC3.3.4), 삭제 영향 항목은 "판정 3 + 재분석분"을 셉니다(AC8.1.3) `[stories]`. 도메인
모델에는 회차도, 대체 관계도 없습니다 `[spec:04]`.

- A. 대화마다 **분석 회차** 엔티티(회차 번호, 전사 버전, 상태: 진행 중 / 완료 / 대체됨)를 두고 판정이 회차에 속한다 — 집계는 대화별 최신 완료 회차만 센다. 진행 중 회차가 있으면 새 회차를 만들지 않는다
- B. 판정마다 "대체한 판정" 연결을 둔다 — 회차 개념은 없고 판정끼리 이어진다
- C. 판정에 상태 값(유효 / 대체됨)만 둔다 — 재분석 때 이전 판정의 상태를 바꾼다
- D. A 와 같되 사회적 사건(SocialEvent)도 회차에 속하게 한다 — 전사가 바뀌면 장면 구분도 달라질 수 있기 때문이다
- X. Other (please specify)

[Answer]: B. 판정마다 "대체한 판정" 연결을 둔다 — 회차 개념은 없고 판정끼리 이어진다

## Q7. 근거 발화가 없어도 되는 판정은 어디까지입니까?

도메인 규칙 3 은 "근거가 없거나 없는 발화 ID 를 가리키면 INVALID_EVIDENCE" 입니다 `[spec:04]`.
그런데 합성 데이터의 기대 판정에는 근거가 적혀 있지 않은 보류가 있습니다 — S2 의 명료화·수리
(기회 없음, ABSENT)와 S3 의 명료화·수리·주제 유지(관찰 기회 UNCERTAIN, 맥락 부족) `[spec:05]`.
사용자 스토리는 ABSENT 보류만 예외로 정했고(AC4.1.3), UNCERTAIN·맥락 부족의 근거 요구 여부를
이 단계로 넘겼습니다 `[stories]`. 규칙을 그대로 두면 S3 의 두 판정이 INVALID_EVIDENCE 로 바뀌어
기대 판정과 어긋납니다.

- A. 근거는 **결과가 있는 판정**(관찰 기회 PRESENT 이고 보류 사유 없음)에만 필수다 — 모든 보류는 근거가 없어도 된다. 근거가 주어졌는데 없는 발화 ID 를 가리키면 어떤 판정이든 INVALID_EVIDENCE
- B. 근거는 관찰 기회가 PRESENT 인 판정에 필수다 — ABSENT 와 UNCERTAIN 은 근거가 없어도 된다(S3 의 UNCERTAIN 두 건 통과, S3 의 응답 관련성 PRESENT 보류는 u2 근거를 가짐)
- C. 근거는 보류 사유가 기회 없음(NO_OPPORTUNITY)이 아닌 모든 판정에 필수다 — S3 의 맥락 부족 두 건은 픽스처에 근거 발화를 채워 넣는다
- D. A 와 같되, 보류라도 근거를 줄 수 있으면 함께 저장한다(없어도 되지만 있으면 검증한다)
- X. Other (please specify)

[Answer]: D. A 와 같되, 보류라도 근거를 줄 수 있으면 함께 저장한다(없어도 되지만 있으면 검증한다)
