## ADR-001: 업무 컴포넌트 6개와 지원 컴포넌트 2개

**Context** — 백엔드는 단일 FastAPI 서비스이고 `api` → `service` → `repository` 계층을 5개 기능
이름(conversation, assessment, training, record, privacy)으로 나누기로 되어 있었다 `[constraint]`
TC-01·TC-14, `[spec:02]` §6, `[practices]`. 단일 백엔드로 바뀌면서 서비스 경계가 지키던 데이터 소유
경계가 사라졌고(R3), 사용자·동의·보호자 초대의 주인이 없었다.

**Decision** — 업무 컴포넌트는 Conversation, Assessment, Training, Record, Account, Privacy 6개다.
기술 명세가 자리를 정해 둔 WebApp(`frontend/`)과 ProviderAdapters(`providers/`)를 지원 컴포넌트로
카탈로그에 함께 둔다. 의존은 한 방향이며 순환이 없다 `[components]`.

**Consequences**
- (+) 엔티티마다 주인이 하나이고, 삭제 전파·판정 규칙의 위치가 분명하다
- (+) 팀 관행의 "기능 이름으로 세 계층을 나눈다" 규칙을 그대로 따라 분담이 기계적이다
- (-) 팀 관행 문서의 "5개 이름"과 설계가 달라진다 — 차이를 이 단계의 배움 기록으로 남긴다 `[Q8]`
- (-) 기술 명세 §6 패키지 구조를 고쳐야 한다(3.1 착수 전)

**Alternatives Rejected**
- 5개 유지, Account 를 `privacy/` 하위 모듈로 — 이름은 지키지만 변경 이유가 다른 둘이 한 패키지에 섞인다 `[Q8]` B
- 5개 유지, 사용자·동의를 Privacy 에 — `[Q4]` A, `[Q8]` D

**보안·규제 영향** — 계정(인증)과 개인정보 처리(권한·삭제)가 다른 컴포넌트라 권한 판정 코드가 한 곳(Privacy)에
모인다. 실사용 확장 시 Account 에 인증 강화(비밀번호 정책, 세션 만료)를, Privacy 에 접근 감사 기록을 붙일
자리가 분리되어 있다.

## ADR-002: 추천 두 종류를 Training 이 가진다

**Context** — 도메인 모델은 추천 엔티티가 하나이고 `[spec:04]` 패키지 구조는 `record/` 에 두었지만
`[spec:02]` §6, 실제로는 목표 선택 화면(A5)의 목표 추천(FR6.1)과 기록 화면(C1)의 다음 코칭 추천(FR8.5, Must
는 가장 최근 어려움 하나 — D-78)이 다른 규칙으로 만들어진다 `[req]`.

**Decision** — 추천 엔티티 하나(`kind` 로 두 종류 구분)를 Training 이 가진다. Record 는 C1 표시를 위해
Training 에서 다음 코칭 추천을 받는다 `[Q1]`.

**Consequences**
- (+) 추천의 결과인 목표와 추천이 한 컴포넌트에 있어 받아들임·변경·거절 저장과 목표 생성이 한 트랜잭션이다
- (+) 추천 재계산 대기(FR3.3)를 목표와 같은 곳에서 처리한다
- (-) Training 이 판정을 읽기 위해 Assessment 에 의존한다(ADR-004 와 같은 방향이라 순환은 없다)
- (-) 명세 패키지 구조와 다르다

**Alternatives Rejected**
- 하나, Record 소유(명세 그대로) — Record 가 쓰기 책임을 가지게 되어 ADR-010 의 읽기 전용 성격이 깨진다
- 둘로 나눔(A5 는 Assessment, C1 은 Record) — 추천 엔티티가 둘이 되고 선택 이력이 흩어진다
- 하나, Assessment 소유 — 판정 규칙 컴포넌트가 사용자 선택 흐름까지 맡게 된다

**보안·규제 영향** — 추천 근거(`sourceIds`)가 다른 컴포넌트의 판정·장면을 가리키므로, 원본 삭제 시 Privacy 가
Training 정리 인터페이스로 참조를 비우거나 추천을 지운다(ADR-006). 근거 없이 남는 추천이 없어야 한다.

## ADR-003: 버전 정보는 판정·시도의 값 객체다

**Context** — 도메인 모델은 `VersionInfo` 를 별도 엔티티로 두었고 `[spec:04]` 패키지 구조는 버전 이력을
Record 에 두었다 `[spec:02]` §6. 그대로면 판정을 만드는 Assessment 가 Record 를 부르고 Record 는 판정을 읽으러
Assessment 를 불러 순환이 생긴다. 팀 관행은 세 버전 값을 값 객체로 묶어 `NOT NULL` 컬럼으로 두기로 했다
`[practices]`. 모든 판정은 기준·프롬프트·모델·전사 버전을 가져야 한다(TC-10, FR4.8).

**Decision** — 별도 엔티티 없이 판정(`BehaviorJudgment.provenance`)과 시도(`Attempt.provenance`)에 값 객체로
저장한다. 버전 이력 조회는 판정을 읽는 쪽이 모아 보여 준다 `[Q2]`.

**Consequences**
- (+) 순환이 없고, "함께 저장한다"가 스키마 제약이 된다
- (+) 판정 한 행만 읽어도 어느 기준·모델로 만든 것인지 안다
- (-) 같은 버전 문자열이 행마다 반복 저장된다(합성 데이터 규모에서는 무시할 수준)
- (-) 버전 목록표(쓸 수 있는 모델·프롬프트 목록)는 따로 없다 — 필요해지면 참조 데이터로 더한다

**Alternatives Rejected**
- Record 소유 엔티티 + 순환 허용 — 순환은 테스트와 분담을 어렵게 한다
- Assessment 소유 엔티티 — 순환은 없지만 조인이 늘고 NOT NULL 제약을 한 행에서 보장할 수 없다
- 값 객체 + 버전 목록표 — 목록표를 쓸 요구가 아직 없다

**보안·규제 영향** — 판정이 어떤 모델·프롬프트로 만들어졌는지 행 단위로 남아, 실사용 확장 시 설명 책임(어떤
기준으로 판단했는가)을 뒷받침한다. 프롬프트 본문이나 전사를 이 값에 넣지 않는다.

## ADR-004: 모의 대화 시도 판정은 Training 이 만들고 Assessment 로 저장한다

**Context** — 실제 대화 판정은 Assessment 가, 모의 대화 시도 판정은 연습 흐름 안에서 만들어진다(Mock 은
시나리오별 규칙) `[spec:06]` §3. 평가용·코칭용 프롬프트는 분리한다(TC-09). 도메인 모델은 두 판정을 같은
엔티티(`mode` REAL/ROLEPLAY)로 두고, 기록 추이는 둘을 함께 읽되 섞지 않는다(FR8.2).

**Decision** — Training 이 코칭 쪽 판정 후보를 받아 시도 판정을 만들고, 저장은 Assessment 가 가진 판정
엔티티에 Assessment 인터페이스로 한다. 근거 검증·보류 규칙·배타성·버전 값 객체 같은 저장 규칙은 Assessment 가
실제·모의 판정에 똑같이 적용한다 `[Q3]`.

**Consequences**
- (+) 판정 규칙이 한 곳에만 있다 — 기록 추이가 한 엔티티를 `mode` 로 걸러 읽는다
- (+) 코칭 프롬프트는 Training 쪽에 남아 평가 기준 변경이 연습 동작에 섞이지 않는다
- (-) Training 이 Assessment 에 의존한다
- (-) Assessment 의 저장 인터페이스가 실제·모의 두 입력 모양을 받아야 한다

**Alternatives Rejected**
- 전부 Assessment — 코칭 프롬프트까지 Assessment 가 불러 TC-09 의 분리가 흐려진다
- Training 별도 판정 엔티티 — 판정 규칙이 두 곳에 복제되고 Record 가 두 엔티티를 합쳐야 한다
- 공유 규칙 모듈 — 저장 입구가 둘이 되어 규칙 우회 경로가 생긴다

**보안·규제 영향** — 사용자 입력(시도 문장)이 판정 저장 전에 Assessment 의 검증을 거친다. LLM 출력이 계약을 어기면
강제 변환하지 않고 보류로 저장하는 규칙이 실제·모의 모두에 적용된다.

## ADR-005: 계정(Account) 컴포넌트 신설

**Context** — 사용자·계정의 자리가 패키지 구조에 없었고 `[spec:02]` §6, 첫 방문 동의를 사용자 단위로
서버에 저장해야 하며(AC1.1.3), Should 에서 사용자 회원가입·로그인(FR13)과 보호자 자기 계정·초대(FR14.2,
D-69)가 온다. 데이터 모델은 이 개념을 처음부터 갖춰야 한다(FR11.2). 사용자 계정은 사용자가 만들고 보호자가
대신 만들지 않는다(D-25).

**Decision** — Account 가 사용자(역할: 주 사용자/보호자), 첫 방문 동의, 로그인, 보호자 초대를 가진다.
Privacy 는 열람 권한과 삭제 요청을 가진다 `[Q4][Q8]`. Must 동안 Account 는 시드 고정 사용자와 동의만
동작시키고, 로그인·초대는 Should 시점에 켠다(엔티티는 처음부터 둔다).

**Consequences**
- (+) Should 기능이 들어와도 스키마를 바꾸지 않는다
- (+) 인증과 권한 판정의 변경 이유가 분리된다
- (-) Must 에는 쓰임이 적은 컴포넌트가 하나 늘어난다
- (-) 팀 관행 "5개 이름"과 달라진다(ADR-001)

**Alternatives Rejected**
- 모두 Privacy — 계정 관리와 개인정보 처리가 한 곳에 섞인다
- Account 최소(초대는 Privacy) — 보호자 계정과 초대가 두 컴포넌트에 걸친다
- Account 를 Should 때 신설 — 사용자·동의를 Privacy 에 두었다가 옮기는 이전 작업이 생긴다

**보안·규제 영향** — 보호자 권한은 기본 NONE 이고 사용자만 바꾼다. 초대 코드는 만료 시각을 가진다. 미성년
사용자 전제(13–18세)에서 보호자 연결이 동의 없이 만들어지지 않도록, 연결은 사용자가 만든 초대로만 생긴다.
실사용 확장 시 법정대리인 동의 요건을 다시 본다(A2).

## ADR-006: 삭제 전파 — Privacy 단일 진입점, DB 커밋 후 파일 삭제, 남은 파일 추적

**Context** — 단일 백엔드에서는 삭제가 여러 컴포넌트의 데이터와 디스크 파일에 걸친다(R3, TC-14). 팀 관행의
잠정 규칙은 삭제 진입점을 Privacy 하나로, 순서를 "파일 삭제 → DB 행 삭제"로 두었고 이 단계가 최종 정의를
닫기로 했다 `[practices]`. 삭제 목록에는 맥락과 분석 수정 요청이 더해졌고, 목표·추천은 사용자가 유지를 고르면
원본 참조만 비운다(US8.2). 파일 삭제가 실패하면 "일부 완료"로 두고 남은 항목을 다시 삭제 요청할 수 있어야
한다(AC8.1.4, 승인됨).

**Decision** — Privacy 의 삭제 유스케이스가 유일한 진입점이다. 확인되면 (1) 지울 파일 경로를 삭제 요청의
영향 항목(`pendingFilePaths`)에 먼저 기록하고, (2) 한 트랜잭션 안에서 Conversation·Assessment·Training 의 정리
인터페이스를 순서대로 불러 DB 행을 지운 뒤 커밋하고, (3) 커밋 후 파일을 지운다. 실패한 경로는 요청을 일부
완료로 남기고, 다시 삭제 요청하면 그 경로만 지운다. FK 연쇄 삭제는 그물로만 쓰고, 목표의 원본 참조는 비우기다
`[Q5][Q9]`.

**Consequences**
- (+) DB 는 한 트랜잭션으로 원자적이다 — 반쯤 지워진 DB 상태가 없다
- (+) 남은 파일이 영향 항목에 기록되어 AC8.1.4 의 재요청이 가능하다
- (-) 팀 관행 잠정 규칙의 "남는 쪽은 항상 DB 행" 원칙을 대체한다 — 남는 쪽이 파일이 될 수 있고, 그것을 삭제 요청 기록이 추적한다
- (-) 파일 삭제 실패 시 음성 파일이 잠시 디스크에 남는다

**Alternatives Rejected**
- 파일을 커밋 전에 삭제(잠정 순서 유지) — 커밋이 실패하면 DB 행은 남는데 파일은 이미 없다 `[Q5]` B
- 프로세스 안 사건으로 각 컴포넌트가 스스로 지움 — 한 트랜잭션 보장이 어렵고 삭제 누락을 찾기 어렵다 `[Q5]` C
- FK 연쇄를 주 수단으로 — "유지" 선택과 파일 삭제를 표현할 수 없다 `[Q5]` D
- 삭제 대기 폴더 / 기동 시 정리 작업 — `[Q9]` C·D

**보안·규제 영향** — 삭제 요청이 무엇을 지웠고 무엇이 남았는지를 기록해, 실사용 확장 시 삭제 이행 증빙의 바탕이
된다. 남은 파일 경로 기록에는 경로만 두고 전사 내용을 넣지 않는다.

## ADR-007: 재분석은 판정끼리 대체 연결로 모델링한다

**Context** — 재분석은 새 판정을 추가하고 이전 판정을 지우지 않으며(AC3.3.3), 집계는 재분석 전에는 이전
판정, 재분석 후에는 새 판정만 센다(D-74). 분석 중 다시 누르면 두 번째 분석이 생기지 않아야 한다(AC3.3.4).
도메인 모델에는 회차도 대체 관계도 없다 `[spec:04]`.

**Decision** — 판정마다 `supersedesJudgmentId` 를 둔다. 재분석의 새 판정은 같은 대화·같은 행동 묶음의 이전
판정을 가리킨다. 집계는 다른 판정이 가리키지 않는(대체되지 않은) 판정만 센다. 분석 중 중복 요청은 대화의
분석 중 상태로 막는다 `[Q6]`.

**Consequences**
- (+) 엔티티가 늘지 않고, 대체 이력이 판정 사이에 직접 남는다
- (+) 삭제 영향 항목의 "판정 3 + 재분석분"을 대화 기준으로 바로 센다
- (-) "이번 분석 회차의 판정 전부"를 한 번에 묶는 단위가 없다 — 대화와 생성 시각으로 모은다
- (-) 전사 정정으로 장면 구분이 달라지면 행동 묶음 단위 대체가 장면을 잘못 이을 수 있다(가정으로 기록)

**Alternatives Rejected**
- 분석 회차 엔티티 — 중복 방지와 묶음 조회가 자연스럽지만 엔티티가 늘어난다 `[Q6]` A·D
- 판정 상태 값만 — 무엇이 무엇을 대체했는지 남지 않는다 `[Q6]` C

**보안·규제 영향** — 이전 판정을 지우지 않으므로, 사용자가 대화를 삭제하면 대체된 판정까지 모두 지워져야 한다
(ADR-006 의 Assessment 정리 인터페이스가 대화 기준으로 전부 지운다).

## ADR-008: 근거는 결과가 있는 판정에만 필수, 보류는 있으면 검증

**Context** — 도메인 규칙 3 은 근거가 없거나 없는 발화 ID 면 INVALID_EVIDENCE 다 `[spec:04]`. 그런데 합성
데이터 기대 판정의 S2 명료화·수리(ABSENT)와 S3 두 판정(UNCERTAIN, 맥락 부족)은 근거가 없다 `[spec:05]`.
사용자 스토리는 ABSENT 만 예외로 정하고 나머지를 이 단계로 넘겼다(AC4.1.3).

**Decision** — 근거는 결과가 있는 판정(관찰 기회 PRESENT 이고 보류 없음)에만 필수다. 보류는 근거가 없어도
되지만, 근거가 주어지면 함께 저장하고 검증한다. 근거가 없는 발화 ID 나 분석에서 뺀 발화를 가리키면 어떤
판정이든 INVALID_EVIDENCE 로 바꾼다 `[Q7]`. 도메인 규칙 3 은 이 결정으로 보완된다.

**Consequences**
- (+) 합성 데이터 기대 판정 3건이 규칙과 함께 성립한다
- (+) 보류에도 근거를 붙일 수 있어 S3 응답 관련성(u2) 같은 보류가 근거를 보여 준다
- (-) "결과가 있는데 근거가 없는" 판정만 막으므로, 보류 판정의 근거 품질은 제공자 출력에 기댄다

**Alternatives Rejected**
- PRESENT 면 필수 — S3 응답 관련성처럼 PRESENT 인 보류가 근거를 반드시 가져야 해 제공자 출력이 부족하면 보류가 INVALID_EVIDENCE 로 바뀐다 `[Q7]` B
- 기회 없음만 예외 — S3 의 맥락 부족 판정에 억지로 근거를 채워야 한다 `[Q7]` C

**보안·규제 영향** — 근거 검증은 LLM 출력이 존재하지 않는 발화를 지어내는 경우를 막는다. 전사 속 지시문이 판정에
영향을 주지 못하게 하는 규칙(TC-08)과 함께, 근거 없는 강한 결론을 쓰지 않는다는 서비스 원칙 4 를 지킨다.

## ADR-009: 정정 → 재검토 → 추천 재계산은 프로세스 안 사건으로 흐른다

**Context** — 발화를 고치면 그 발화를 근거로 한 판정에 재검토 필요를 표시하고(Assessment), 관련 추천을 재계산
대기로 둔다(Training) — FR3.3. Assessment 는 발화를 읽으러 Conversation 을 부르고, Training 은 판정을 읽으러
Assessment 를 부른다. 정정하는 쪽(Conversation)이 Assessment 를 직접 부르면 순환이 생긴다.

**Decision** — Conversation 은 정정 때 "발화 정정됨" 사건을, Assessment 는 재검토 표시 때 "판정 재검토 필요"
사건을 프로세스 안에서 알린다. 받는 쪽(Assessment, Training)이 구독한다. 같은 요청 트랜잭션 안에서 동기적으로
처리한다. 이 결정은 질문으로 묻지 않고 리드가 정했다 — 사용자가 정한 컴포넌트 경계를 순환 없이 구현하는 유일한
방법에 가까운 기술 선택이기 때문이다.

**Consequences**
- (+) 의존 방향이 한 방향으로 유지된다
- (+) A3 재검토 안내(FR3.4)가 정정 요청의 응답에 바로 반영된다(동기 처리)
- (-) 사건 흐름은 호출 그래프에 드러나지 않아 추적이 조금 어렵다 — 사건 이름과 구독자를 이 ADR 과 3.1 설계에 고정한다

**Alternatives Rejected**
- Conversation 이 Assessment 를 직접 호출 — 순환(Conversation ↔ Assessment)
- API 계층에서 두 서비스를 차례로 호출 — 계층 규칙(업무 규칙은 service)에 어긋나고 누락되기 쉽다
- 비동기 메시지 큐 — MVP 범위에 인프라가 늘고 재검토 표시가 늦어진다

**보안·규제 영향** — 사건에는 식별자만 싣고 전사 본문을 싣지 않는다(로그에 전사를 남기지 않는 관행과 같다).

## ADR-010: Record 는 자기 엔티티 없는 읽기 전용 집계 컴포넌트다

**Context** — 기록 화면(C1)과 상세 화면(C2~C4), 보호자 열람 화면은 대화·판정·연습·추천을 모아 보여 준다.
Record 가 자기 데이터를 가지면 다른 컴포넌트와 쓰기 경계가 겹치고, 추천·버전 이력을 Record 에 두는 명세안은
순환을 만들었다(ADR-002, ADR-003).

**Decision** — Record 는 엔티티를 가지지 않고 Conversation·Assessment·Training 을 읽어 집계·조회만 한다. 추이
집계 규칙(분모, 대체된 판정 제외, 비교 불충분)은 Record 의 순수 규칙으로 둔다. 집계 결과를 저장하지 않는다.
이 결정은 ADR-002·ADR-003 의 사용자 결정에서 따라 나온 리드 결정이다.

**Consequences**
- (+) 삭제 전파 대상이 아니다 — 원본이 지워지면 집계도 사라진다
- (+) 집계 규칙이 입력만 받는 순수 함수라 단위 테스트가 쉽다(팀 관행의 픽스처 기반 테스트와 맞는다)
- (-) 조회 때마다 계산한다 — 합성 데이터와 사용자 한 명 규모에서는 문제가 없다

**Alternatives Rejected**
- 집계 결과를 저장하는 읽기 모델 — 원본 변경·삭제 때마다 동기화가 필요하다
- Record 가 추천·버전 이력 소유 — 순환(ADR-002, ADR-003)

**보안·규제 영향** — (Should) 보호자 열람 데이터는 Privacy 의 권한 판정을 받은 뒤 Record 가 범위(SUMMARY: 목표·추이,
FULL: 리포트까지)에 맞춰 만든다. 전사 원문·원음은 어느 권한에서도 주지 않는다(FR14.4).
