## Q1. 전사와 분석 요청은 응답을 어떻게 돌려줍니까?

대화를 올리면 처리 상태가 업로드 중 → 전사 중 → 완료/실패로 바뀌고(FR1.3), 분석도 "분석 중" 상태를 가집니다
`[req]` `[components]`. Mock 모드에서는 분석이 3초 안에 끝나야 하지만(NFR3), live 제공자는 아직 정해지지 않아 응답
시간을 모릅니다(D-37). 연습·기록 담당 단위가 이 응답 모양 위에 화면을 만들기 때문에, 동기로 기다릴지 상태를 물어볼지를
지금 정해야 오류 처리 모양이 갈라지지 않습니다 `[practices]` evidence.md.

- A. **동기** — 요청이 전사·분석을 끝낼 때까지 기다렸다가 결과를 돌려준다. Mock 에서는 단순하지만, live 가 느리면 화면이 오래 멈춘다
- B. **접수 후 상태 조회** — 요청은 바로 "접수됨"(202)과 대화 ID 를 돌려주고, 작업은 서버 안 백그라운드로 돈다. 화면은 상태 조회 API 를 주기적으로 불러 완료·실패를 확인한다
- C. **업로드만 접수 후 상태 조회, 분석은 동기** — 전사는 B 방식, 분석 요청은 A 방식(Mock 3초 기준)
- D. **API 모양은 B, 구현은 당장 동기** — 응답 계약은 202 + 상태 조회로 고정하되, 서버 안에서는 요청 처리 중에 끝까지 실행한 뒤 상태를 완료로 둔다. live 가 들어올 때 계약을 바꾸지 않고 백그라운드로 옮긴다
- X. Other (please specify)

[Answer]: B. **접수 후 상태 조회** — 요청은 바로 "접수됨"(202)과 대화 ID 를 돌려주고, 작업은 서버 안 백그라운드로 돈다. 화면은 상태 조회 API 를 주기적으로 불러 완료·실패를 확인한다

## Q3. 병렬로 시작하기 위한 시드 상태는 누가 만들고 유지합니까? (OQ-U2)

기능 단위들은 앞 단위가 아직 없으면 시드 데이터로 대신해 시작하기로 했습니다(D-92) `[units]`. 필요한 상태는 예를 들어
"S1 전사 완료", "S1 분석 완료", "S1 분석 완료 + 목표 선택됨", "연습 시도가 쌓인 기록", "S1 정정 후 재검토 필요"입니다.
시드는 `scripts/seed.py` 에 둡니다 `[practices]` Deployment. 시드가 실제 구현과 다른 모양이면 통합할 때 깨집니다.

- A. **U1 이 시드 틀과 모든 상태 시드를 한 번에 만들고 유지한다** — 한 곳에서 관리하지만, U1 담당자가 모든 단위의 데이터 모양을 알아야 한다
- B. **U1 이 시드 틀과 기본 상태(고정 사용자, S1~S3 전사 완료)만 만들고, 그 뒤 상태는 그 데이터를 만드는 단위가 소유한다** — 예: "S1 분석 완료" 시드는 수행 평가 단위(U5)가 만들고, 자기 구현이 바뀌면 함께 고친다. 다른 단위는 그때까지 계약에 맞춘 임시 시드를 쓴다
- C. **이 단계에서 시드 상태 목록과 각 상태의 데이터 모양까지 계약으로 고정하고, 만드는 사람은 B 처럼 나눈다**
- X. Other (please specify)

[Answer]: A. **U1 이 시드 틀과 모든 상태 시드를 한 번에 만들고 유지한다** — 한 곳에서 관리하지만, U1 담당자가 모든 단위의 데이터 모양을 알아야 한다

## Q4. API 경로와 응답 모양의 기준 문서는 무엇입니까?

단위들이 동시에 화면과 백엔드를 만들려면 같은 모양을 보고 일해야 합니다. 이 단계의 계약 요약(`contract-summary.md`)에
OpenAPI 초안을 적고, 구현이 끝나면 FastAPI 가 실제 스키마(`openapi.json`)를 만듭니다. 두 문서가 어긋났을 때 어느
쪽이 이기는지를 정해 둬야 합니다.

- A. **계약 요약이 기준** — 구현은 계약 요약에 맞춰 만들고, 어긋나면 구현을 고친다. 계약을 바꾸려면 계약 요약을 먼저 고친다
- B. **구현 전까지는 계약 요약, 구현 후에는 생성된 스키마가 기준** — 단위가 병합되면 생성 스키마가 기준이 되고, 계약 요약은 그 시점의 초안 기록으로 남긴다
- C. **생성된 스키마가 기준이고 CI 가 계약 요약과 대조한다** — 경로·필드가 어긋나면 GitHub Actions 검사가 실패한다
- X. Other (please specify)

[Answer]: A. **계약 요약이 기준** — 구현은 계약 요약에 맞춰 만들고, 어긋나면 구현을 고친다. 계약을 바꾸려면 계약 요약을 먼저 고친다

## Q5. 이미 합의한 계약을 깨는 변경은 어떻게 처리합니까?

한 저장소 안의 내부 계약이라 버전을 여러 개 동시에 유지할 필요는 없습니다. 다만 5명이 병렬로 일하는 동안 필드 이름을
바꾸거나 빼면 다른 단위가 깨집니다. 필드를 추가하는 변경은 받는 쪽이 모르는 필드를 무시하면 안전합니다.

- A. **추가는 자유, 깨는 변경은 그 계약을 쓰는 단위 담당자의 PR 리뷰 승인이 필요하다** — 계약 요약을 같은 PR 에서 고친다
- B. **추가는 자유, 깨는 변경은 decision-log 에 기록하고 팀 전체가 합의한 뒤에만 한다**
- C. **Must 단위가 모두 통합될 때까지 깨는 변경을 금지한다** — 꼭 필요하면 새 필드를 추가하고 옛 필드는 통합 뒤에 지운다
- X. Other (please specify)

[Answer]: A. **추가는 자유, 깨는 변경은 그 계약을 쓰는 단위 담당자의 PR 리뷰 승인이 필요하다** — 계약 요약을 같은 PR 에서 고친다

## Q6. 여러 단위가 같은 화면을 만질 때 화면 경계를 어떻게 나눕니까?

기능 단위가 컴포넌트를 가로질러 같은 화면을 함께 만집니다 — 업로드 화면 A2 는 녹음·전사(U3)와 맥락(U4), 전사 확인
화면 A3 는 U3 와 정정·삭제(U9), 리포트 화면 A4 는 수행 평가(U5)와 U9 `[units]`. 한 파일을 두 사람이 동시에 고치면
병합 충돌이 납니다.

- A. **화면 페이지는 한 단위가 소유하고, 다른 단위는 끼워 넣을 컴포넌트를 만든다** — 소유 단위가 자리(props 계약)를 비워 두고, 예: A3 페이지는 U3, 상단 재검토 안내 컴포넌트는 U9
- B. **화면을 구역별 하위 라우트로 나눠 단위마다 따로 소유한다**
- C. **나누지 않고 먼저 만든 단위가 페이지를 만들고, 뒤 단위는 그 파일에 이어서 쓴다**
- X. Other (please specify)

[Answer]: B. **화면을 구역별 하위 라우트로 나눠 단위마다 따로 소유한다**

## Q8. 분석을 접수 후 상태 조회(Q1)로 바꾸면 "Mock 분석 3초 이내"(NFR3)는 무엇을 재는 기준이 됩니까?

시간 단언"입니다 `[req]`. Q1 에서 요청이 바로 202 로 돌아오게 정했으므로, 요청 응답만 재면 목표가 거의 의미를 잃습니다.

- B. **접수 응답(202)이 3초 이내** — 백그라운드 분석 시간에는 목표를 두지 않는다. 확정된 품질 목표를 약하게 만드는 선택이다
