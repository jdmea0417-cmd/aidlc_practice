## Q1. 저장소를 만들고 어떻게 운영합니까?

이 작업 공간은 아직 git 저장소가 아닙니다. `[org]` 의 일하는 방식(트렁크 기반, 짧은
브랜치, squash 머지)은 저장소가 있다는 전제 위에 쓰여 있고, AI-DLC 의 Construction
기능 자체도 git 저장소 없이는 돌지 않습니다 `[draft]`.

또 하나 같이 정해야 할 것이 있습니다. CI 파이프라인 단계(3.7)가 이번 범위에서
빠져 있어, 병합 전에 검사를 강제할 자동 수단이 없습니다. 초안은 로컬
`scripts/check.sh` 를 제안했는데, 무엇이 그걸 실제로 지키게 만드는지가 원격 저장소
사용 여부와 함께 결정됩니다 `[quality]`.

**먼저 고쳐야 할 사실이 하나 있습니다.** 저장소는 없지만 `.gitignore` 파일은 이미
있습니다(85줄). 그런데 `node_modules` 만 들어 있고 `.env`, `__pycache__/`, `.venv/`,
음성 업로드 디렉터리가 전부 빠져 있습니다. 즉 지금 상태로 저장소를 만들고 전체를
추가하면 **`.env` 가 첫 커밋에 들어갑니다** `[devsecops]`. 어느 선택지를 고르든 이
파일을 먼저 손보는 것이 저장소 생성의 첫 단계가 됩니다.

- A. 로컬 저장소만 만든다 — 병합 전 검사는 `pre-push` 훅으로 강제한다
- B. 원격(GitHub 등)을 쓰고 PR 로 병합한다 — 검사는 GitHub Actions 로 강제한다
- C. 원격을 쓰되 PR 없이 직접 push 한다 — 검사는 `pre-push` 훅으로 강제한다
- D. 저장소를 지금 만들지 않는다 — Construction 진입 시점에 다시 정한다
- X. Other (please specify)

[Answer]: B. 원격(GitHub 등)을 쓰고 PR 로 병합한다 — 검사는 GitHub Actions 로 강제한다

## Q2. 걷는 뼈대가 무엇을 관통해야 합니까?

걷는 뼈대를 먼저 만든다는 것은 이미 정해져 있습니다(D-46). 남은 것은 그 첫
슬라이스가 무엇을 지나가느냐입니다. 초안은 React 화면 1개 → FastAPI 엔드포인트 1개 →
`service` → `repository` → PostgreSQL 테이블 1개 → Mock 호출 → 화면 표시를 제안하고,
여기에 가정 A1(브라우저 녹음이 `localhost` 에서 HTTPS 없이 동작하는가) 확인을 넣자고
제안했습니다 `[draft]`. 이 가정이 틀리면 로컬 인증서 작업이 통째로 추가되는데, 늦게
알수록 비쌉니다 `[raid]`.

- A. 임시 엔드포인트로 얇게 관통시키고 녹음 확인도 첫 Bolt 안에서 함께 한다
- B. 임시 엔드포인트로 얇게 관통시키되 녹음 확인은 별도 작업으로 뺀다
- C. 실제 첫 기능(PU-01 업로드)으로 관통시키고 녹음 확인도 함께 한다
- D. 실제 첫 기능(PU-01 업로드)으로 관통시키되 녹음 확인은 별도 작업으로 뺀다

## Q3. 테스트를 언제 씁니까?

초안은 **섞는 방식**을 제안했습니다. 집계·판정 규칙 모듈만 기대 결과를 테스트로 먼저
고정한 뒤 구현하고, 나머지 계층은 구현한 뒤 테스트를 씁니다 `[draft]`. 근거는 합성
대화 3건의 기대 판정이 이미 문서로 존재한다는 것입니다 `[spec:05]`.

품질 담당은 이 선택에 찬성하되, 의무를 "TDD 사이클을 돈다"가 아니라 "기대 판정표가
구현보다 먼저 픽스처로 고정된다"는 산출물 순서로 다시 쓰라고 했습니다. 그러면 Python
이 처음인 팀에 얹히는 비용이 사실상 없으면서 보장은 유지됩니다 `[quality]`.

- A. 섞는 방식으로 간다 — 규칙 모듈만 테스트 선행, 나머지는 구현 후. 의무는 "기대 판정표를 픽스처로 먼저 고정한다"로 쓴다
- B. 섞는 방식으로 가되 의무를 "규칙 모듈은 TDD 사이클로 만든다"로 더 강하게 쓴다
- C. 전부 구현 후 테스트로 단순화한다 — 방법론을 하나로 두어 헷갈리지 않게 한다
- D. 전부 테스트 선행으로 통일한다
- X. Other (please specify)

[Answer]: C. 전부 구현 후 테스트로 단순화한다 — 방법론을 하나로 두어 헷갈리지 않게 한다

- C. 저장소 전체에 라인 80% 를 건다 — 조직 표준에 맞춘다
- D. 이번 범위에서는 커버리지 바닥을 두지 않는다 — 테스트 개수 기준(Standard)만 지킨다

## Q5. "배포에 성공했다"를 무엇으로 판정합니까?

클라우드가 없어서 `[org]` 의 배포 절차(머지 시 스테이징 배포, 운영 배포는 별도 승인)를
걸 대상이 없습니다. 초안은 그 자리를 "`docker compose up --build` 후 헬스체크 통과 +
합성 대화 3건이 종단으로 지나감"으로 대체했습니다 `[draft]`.

품질 담당은 이 정의가 SM1 을 약화시킨다고 지적했습니다. "끊김 없이 지나간다" 아래에서는
**화면이 틀린 판정을 표시해도 통과합니다**. `[spec:05]` 에는 각 대화마다 기대 판정이
붙어 있으니, 지나가는지가 아니라 기대와 맞는지를 보라는 것입니다 `[quality]`.

- A. 기대 판정 대조까지 넣는다 — 3건이 지나가고, 그 결과가 `[spec:05]` 의 기대 판정과 일치해야 성공이다
- B. 초안대로 둔다 — 끊김 없이 지나가면 성공. 판정 정확성은 별도 단위 테스트가 본다
- C. 기대 판정 대조를 넣되 시연 직전 한 번만 한다
- D. 헬스체크만으로 한다 — 종단 실행은 별도 확인 절차로 뺀다
- X. Other (please specify)

[Answer]: B. 초안대로 둔다 — 끊김 없이 지나가면 성공. 판정 정확성은 별도 단위 테스트가 본다

## Q7. 합성 대화 3건 중 일부 검증 항목이 Must 범위 밖입니다. 어떻게 합니까?

검토 중에 드러난 범위 문제입니다. 이건 관행 선택이 아니라 성공 기준의 의미에 관한
확인입니다.

`[spec:05]` 의 세 번째 합성 대화(S3)에는 검증 항목이 네 개 붙어 있는데, 그중 두 개가
Must 범위 밖입니다 `[quality][scope]`.

| S3 의 검증 항목 | 필요한 기능 | 등급 |
|---|---|---|
| 1. 종단 여섯 단계 통과 | F01~F06 | Must — 확인 가능 |
| 2. 전사 정정 후 관련 판정 재검토 표시 | F07 (화면 A3) | **Should — 확인 불가** |
| 3. 보류가 실패로 집계되지 않음 | F03 | Must — 확인 가능 |
| 4. 삭제 시 연결 항목 처리 | F07 (화면 C5) | **Should — 확인 불가** |

즉 Must 만 만들면 SM1 의 "합성 대화 3건이 끊김 없이 이어진다"는 통과하지만, S3 가
원래 확인하려던 것의 절반은 확인되지 않은 채 남습니다.

- A. 그대로 둔다 — SM1 은 종단 연결만 본다. 항목 2·4 는 F07 을 만들 때 함께 확인한다
- B. F07 의 두 기능만 Must 로 끌어올린다 — S3 를 원래 의도대로 전부 확인한다
- C. 그대로 두되 산출물에 명시한다 — "Must 범위에서 S3 의 검증 항목 2·4 는 확인되지 않는다"를 적어 나중에 오해하지 않게 한다
- D. S3 를 이번 검증 대상에서 빼고 S1·S2 두 건으로 SM1 을 판정한다
- X. Other (please specify)

[Answer]: B. F07 의 두 기능만 Must 로 끌어올린다 — S3 를 원래 의도대로 전부 확인한다
