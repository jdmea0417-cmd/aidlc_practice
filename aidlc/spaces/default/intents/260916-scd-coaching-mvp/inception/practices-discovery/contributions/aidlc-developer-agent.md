### 1. 계층 경계 — 규칙 자체는 맞지만 R3 을 대신하지 못한다

#### 1.1 계층 규칙이 닿지 않는 자리가 정확히 R3 이 걱정하던 자리다

초안은 `api` → `service` → `repository` 와 Pydantic 응답 모델을, 사라진 "analysis 의 DB
직접 접근 금지"의 대체물로 제시한다(TC-14, R3). **이 둘은 서로 다른 것을 막는다.**

- 원래 규칙이 막던 것: 한 데이터를 두 주체가 각자 건드려서 **삭제가 한쪽에만 적용되는
  것**(F07 삭제 전파 누락).
- 계층 규칙이 막는 것: 업무 규칙을 건너뛴 **읽기·쓰기 경로**와 필드 과다 노출.

계층 규칙을 100% 지켜도 삭제는 샌다. 이유는 이 프로젝트에 **저장소가 둘**이기 때문이다.
TC-05 가 음성 파일을 DB BLOB 이 아니라 파일 저장소 + 메타데이터 테이블로 두라고 못박았고,
그래서 "대화 삭제"는 **DB 트랜잭션 하나로 끝나지 않는 연산**이다. `service` 를 경유해도
파일이 디스크에 남으면 F07 은 깨진 것이다. 계층 규칙 어디에도 이 문장이 없다.

추가로 새는 자리: 업로드가 중간에 실패해 DB 행은 없는데 파일만 남는 경우. 이건 디스크
누수이자 **삭제 요청으로도 찾을 수 없는 음성 파일**이라 F07 관점에서 더 나쁘다.

#### 1.2 그래서 계층 규칙에 붙여야 할 세 문장

domain-design(2.6)이 최종 정의를 닫기 전까지 코드가 따를 잠정 규칙으로 제안한다.
(2.6 에서 바뀔 수 있고, 바뀌면 그쪽이 이긴다.)

1. **한 애그리거트의 삭제 진입점은 하나다.** 대화/음성/전사/판정/기록에 걸친 삭제는
   `service/privacy/` 의 삭제 유스케이스 한 곳에서만 시작한다. 다른 `service` 모듈은
   자기 소유 테이블의 정리 함수를 노출하고, 삭제 유스케이스가 그것들을 호출한다.
   각자 알아서 지우면 R3 이 그대로 재현된다.
2. **파일과 행의 순서를 못박는다.** 쓰기는 `DB 행(status=pending)` → `파일 저장` →
   `DB 행(status=ready)` 순서. 삭제는 `파일 삭제` → `DB 행 삭제` 순서. 어느 쪽이 중간에
   죽어도 **남는 쪽이 항상 DB 행**이 되게 하는 것이 핵심이다. 삭제 경로가 찾을 수 있는
   것은 DB 행뿐이므로, 고아는 반드시 DB 쪽에 생겨야 한다. 반대 순서로 하면 아무도
   모르는 파일이 남는다.
3. **FK 에 `ON DELETE CASCADE` 를 건다** — 애플리케이션 규칙의 대체물이 아니라 그물로.
   코드가 한 테이블을 잊었을 때 DB 가 대신 지운다. 다만 파일 저장소에는 그물이 없으므로
   1·2 가 여전히 필요하다.

#### 1.3 빠진 역방향 규칙

초안은 아래로 내려가는 방향만 적었다. 올라오는 방향이 없으면 계층은 하루 만에 섞인다.

- `service` 는 `fastapi` 를 import 하지 않는다. 특히 `HTTPException` 을 `service` 에서
  던지지 않는다(§4 오류 처리와 직결).
- `repository` 는 `service` 를 import 하지 않는다.
- `providers` 는 `service`·`repository` 를 import 하지 않는다. 어댑터는 도메인을 모른다.
- `SttProvider` / `LlmProvider` **인터페이스(Protocol)는 `providers/` 가 아니라
  `service/ports.py`(또는 `common/ports.py`)에 둔다.** 인터페이스가 구현체와 같은 패키지에
  있으면 `service` 가 `providers` 를 import 하게 되고, `providers/__init__.py` 를 타고
  `stt_live.py` 가 함께 로드되어 **`ANALYSIS_MODE=mock` 인데 live SDK 가 없다고 죽는**
  실패가 난다. SC-04 가 mock 을 기본 경로로 못박았으므로 이건 가상의 위험이 아니다.

#### 1.4 무엇이 실제로 강제하는가 (비용순)

| 강제 수단 | 무엇을 잡는가 | 비용 |
|---|---|---|
| `response_model=` 을 모든 라우트에 필수화 + `app.routes` 를 순회해 `response_model` 이 `BaseModel` 하위인지 확인하는 검사 1개 | ORM 모델 직접 반환 전부 | 8줄 |
| SQLAlchemy 관계에 `lazy="raise"` | ORM 객체가 API 쪽으로 새면 직렬화 시점에 조용히 N+1 이 아니라 **즉시 예외**로 터진다 | 설정 1줄 |
| Ruff `TID251`(banned-api)로 `app.repository` import 를 전역 금지 + `per-file-ignores` 로 `app/service/**`·`app/repository/**`·`tests/**` 만 해제 | `api` → `repository` 직접 호출 | 설정 6줄, 도구 추가 없음 |
| `import-linter` 의 layers 계약 | 위 전부 + 역방향 전부를 한 번에 | 개발 의존성 1개, 설정 10줄 |
| 삭제 경로 검사: 대화 1건을 만들고 삭제한 뒤, **관련 테이블 전부와 파일 경로**가 비었는지 확인 | F07 삭제 전파 회귀 | 검사 1개 |

권고: `response_model` 검사 + `lazy="raise"` + Ruff `TID251` 조합부터 넣는다. 새 도구가
0개이고 R1(Python 초심자) 부담이 없다. `import-linter` 는 역방향 규칙까지 다 걸고 싶을 때
올린다. 이 중 어느 것도 없으면 계층 규칙은 리뷰어 1명의 기억력에 걸린 상태다(OC-03 상
리뷰어도 고정이 아니다).

### 2. 도구 제안 검토

#### 2.1 uv — 동의. 이유를 하나 바꾸자

초안의 근거("빠르다, 설정 파일 하나")보다 R1 에 더 직접 닿는 이유가 있다. **`uv run` 을
쓰면 가상환경 활성화라는 개념 자체가 사라진다.** Python 이 처음인 사람이 첫 주에 가장
많이 넘어지는 자리가 "venv 를 안 켜고 실행해서 모듈을 못 찾는 것"인데, uv 는 그 단계를
없앤다. Poetry 는 없애지 못한다.

붙여야 할 것:
- `uv.lock` 을 저장소에 커밋하고 `scripts/check.sh` 는 `uv sync --frozen` 으로 시작한다.
  잠금이 커밋 안 되면 5인 재현성이라는 채택 이유가 사라진다.
- **backend Dockerfile 도 uv 로 설치한다.** 컨테이너가 `pip install -r requirements.txt`
  로 다르게 설치되면 로컬과 컨테이너가 갈라지고, 그 어긋남은 시연 전날에 드러난다.
- Dockerfile 의 uv 버전을 태그로 고정한다.

인터뷰 질문에 대한 의견: "Poetry 경험자가 있으면 뒤집는다"는 기준이 너무 낮다. 뒤집을
근거는 "써 봤다"가 아니라 "**잠금 충돌이 났을 때 풀 수 있다**"여야 한다. 그 정도가 아니면
5인 중 1명의 익숙함보다 나머지 4명의 진입 비용이 크다.

#### 2.2 SQLAlchemy 2.0 — 동의. 다만 **sync 를 명시해야 한다**

초안에 빠진 결정이고, 빠뜨리면 반드시 사고가 난다. FastAPI 라는 이유로 async
SQLAlchemy(`AsyncSession`)를 고르면 다음이 따라온다: `await` 전파, lazy load 금지에서
오는 `MissingGreenlet`, 테스트 픽스처 복잡도 증가, Testcontainers 설정 증가. 이 프로젝트는
로컬 데모에 사용자 5명이라 동시성 요구가 **없다**(SC-01, OC-01). 그리고 명세 §7.1 의 예시
자체가 이미 `def get_report(...)` 로 **동기**다.

- 제안: **동기 SQLAlchemy 2.0 + 동기 `def` 라우트**로 간다. FastAPI 는 동기 라우트를
  스레드풀에서 돌리므로 이벤트 루프를 막지 않는다.
- Java 배경에 직접 닿는 점: `Mapped[str]` / `mapped_column()` 선언 스타일은 JPA 엔티티와
  읽는 느낌이 거의 같고, mypy 가 그대로 이해한다. R1 완화에 실제로 기여한다.
- 위 1.4 의 `lazy="raise"` 를 관계 기본값으로 둔다.

#### 2.3 Alembic — 동의. 운영 규칙 세 줄이 빠졌다

- `--autogenerate` 결과는 **초안이다.** enum 변경, server default, 인덱스 이름 변경을
  놓친다. 사람이 읽고 고친 뒤 커밋한다.
- **마이그레이션이 언제 도는지 한 곳에 정한다.** 컨테이너 기동 시 자동인지,
  `scripts/migrate.sh` 를 사람이 부르는지. 5인 병렬에서 이걸 안 정하면 "내 DB 만 다름"이
  주간 이벤트가 된다.
- DB 연동 검사는 `Base.metadata.create_all()` 이 아니라 `alembic upgrade head` 로 스키마를
  만든다. 그래야 마이그레이션이 한 번이라도 실행된다. 이건 초안이 스스로 적은
  "태그에서 새로 clone 해 처음부터 올려 본다"는 시연 리허설과 같은 것을 앞당겨 잡는다.
- 병합 충돌 대비: Bolt 하나당 마이그레이션 파일 하나, 병합된 마이그레이션은 수정 금지,
  `down_revision` 이 갈라지면 새 파일을 만들지 말고 `alembic merge` 를 쓴다.

#### 2.4 Ruff — 동의. 다만 규칙 집합을 정하지 않으면 거의 아무 일도 안 한다

Ruff 의 기본 활성 규칙은 `E4`, `E7`, `E9`, `F` 뿐이라 사실상 문법 오류 검출기다.
"Ruff 를 쓴다"만 적고 끝내면 `org.md` 가 기대하는 린트 게이트가 성립하지 않는다.

제안하는 출발 집합(작게 시작해서 늘린다):

- `E`, `F` — 기본
- `I` — import 정렬. **5인 병렬에서 import 순서 차이는 그 자체로 병합 충돌 원인**이다.
  이 하나가 주는 이득이 가장 크다.
- `UP` — 낡은 Python 관용구를 현대 문법으로. Java/TS 배경이 옛 예제를 베껴 올 때 잡힌다.
- `B` — 가변 기본 인자 등 초심자 함정
- `SIM` — 불필요한 중첩 줄이기
- `TID` — 1.4 의 계층 강제에 필요
- `RUF` — Ruff 고유 규칙

`ANN`(타입 어노테이션 강제)은 `app/service/**` 에만 켠다(§2.5 와 짝).
줄 길이는 기본 88 을 그대로 쓴다. 정하지 않으면 사람마다 다르게 줄바꿈해서 diff 가 는다.

Black → Ruff format 이 org 기본값을 좁힌 것이지 뒤집은 것이 아니라는 초안의 논리에는
동의한다.

#### 2.5 mypy — 방향은 동의, **지금 쓰인 형태로는 강제되지 않는다**

초안: "`strict` 는 끄고 시작하되 `service/` 의 공개 함수는 인자와 반환에 타입을 반드시
붙인다."

문제: 기본 설정의 mypy 는 **타입이 없는 함수의 본문을 아예 검사하지 않는다.** 즉 타입을
안 붙인 함수는 검사에서 조용히 빠진다. "반드시 붙인다"가 사람의 선의로만 남고, 안 붙인
쪽이 오히려 검사에서 자유로워지는 역인센티브가 생긴다.

고치는 법(`pyproject.toml`):

- 전역: `check_untyped_defs = true` — 어노테이션이 없어도 본문은 검사한다.
- 전역: `warn_unused_ignores = true`, 서드파티는 `ignore_missing_imports = true`.
- `plugins = ["pydantic.mypy"]`. SQLAlchemy 2.0 은 `Mapped[]` 덕에 플러그인이 불필요하다.
- **`app.service.*` 모듈 오버라이드에만 `disallow_untyped_defs = true`.** 이걸로
  "`service/` 공개 함수는 타입 필수"가 문장이 아니라 검사가 된다. Ruff `ANN` 과 겹치므로
  둘 중 하나만 켜도 된다 — mypy 쪽이 반환 타입의 정합성까지 보므로 mypy 를 권한다.
- `scripts/check.sh` 에서 **ruff → mypy → pytest → vitest 순서로 두고 실패 시 즉시 중단**.
  mypy 가 선택이 되는 순간 2주 안에 오류 수백 개가 쌓여 아무도 안 켠다.

#### 2.6 SQLModel 기각 — 결론은 맞지만 **기각 사유가 사실과 다르다**

초안과 `evidence.md` 는 "SQLModel 은 ORM 모델과 응답 모델을 같은 클래스로 합치는
방식이라 TC-14 와 정면으로 어긋난다 — 결정적"이라고 썼다. 이건 과장이다. SQLModel 에서도
`table=True` 모델과 응답용 모델을 **분리해서 쓸 수 있다.** 합치는 것은 강한 관용구이지
구조적 강제가 아니다. `inception.md` 가 "대안 검토는 정확해야 한다"고 요구하므로 이
문장은 고쳐야 한다. 결정을 바꾸자는 것이 아니라 **근거를 바꾸자**는 것이다.

정확한 기각 사유 세 가지:

1. SQLModel 은 SQLAlchemy 위의 얇은 층이고, 조금만 복잡한 질의로 가면 결국 SQLAlchemy 를
   직접 쓰게 된다. 결과적으로 **두 가지 사고 모형을 동시에 배운다.** Python 이 처음인
   팀에게는 이게 가장 비싸다(R1).
2. 유지보수 폭이 좁아 Pydantic·SQLAlchemy 주요 버전 대응이 늦은 전력이 있다. 7주 일정에
   **한 주를 막히면 복구할 여유가 없다**(R5).
3. 관용구가 TC-14 가 금지한 형태 쪽으로 기울어 있다. 즉 **금지된 것이 가장 쉬운 길**이
   된다. 규칙과 도구가 반대 방향을 가리키면 규칙이 진다. (이건 "불가능하다"가 아니라
   "기본 경로가 반대다"라는 약한 형태의 주장으로 적어야 한다.)

| 빠진 것 | 왜 필요한가 |
|---|---|
| `python-multipart` | FastAPI 의 multipart 업로드에 필수. 없으면 업로드 라우트가 기동 시점에 죽는다. 명세 §2 가 업로드를 multipart 로 못박았다 |
| `pydantic-settings` | Pydantic v2 에서 설정 관리가 **별도 패키지로 분리**되었다. `ANALYSIS_MODE` 등 환경변수 파싱의 단일 지점 |
| `httpx` (런타임 의존성으로도) | 이미 테스트 도구로 잡혀 있다. 제공자 HTTP 호출에 같은 것을 쓰면 새 의존성이 0 |
| `openapi-typescript` (frontend) | 명세 §2 의 "frontend 타입은 OpenAPI 스키마에서 생성"을 실행할 도구가 지정되어 있지 않다 |

생성 타입 규약도 없다. 제안: `npm run gen:api` 로 생성하고 **결과물을 커밋하되 손으로
고치지 않는다**(파일 머리에 생성물 표시). `scripts/check.sh` 는 재생성 후 diff 가 비어
있는지 본다 — 비어 있지 않으면 백엔드 계약과 프론트 타입이 갈라졌다는 뜻이다.

### 3. 이름 — 한국어 허용은 되는데, 경계가 지금 그어져 있지 않다

#### 3.1 명세 자체가 이미 두 스타일을 섞고 있다

- §7.3: `def test_보류와_기회없음은_분모에서_제외된다()`
- §7.4: `def test_evidence_ids_must_exist(client)`

같은 문서 안에서 갈린다. 초안의 "테스트 함수 이름 밖의 식별자는 영어"만으로는 이 둘 중
어느 쪽이 기본인지 정해지지 않는다. 5명이 각자 고르면 파일마다 다른 스타일이 된다.

#### 3.2 제안하는 경계선 — "무엇을 검증하는가"로 가른다

- **판정 규칙(보류, 기회 없음, 독립 수행, 도움 후 수행, 분모 제외 등) 자체를 검증하는
  것은 한국어.** 기준 문서와 한 줄씩 대조해야 하는 것들이고, 영어로 옮기는 순간 대조가
  어려워진다는 초안의 논리가 정확히 여기에 적용된다.
- **기술적·배관 동작(ID 검증, 상태 코드, 직렬화, 권한, 마이그레이션)을 검증하는 것은
  영어.** 여기엔 대조할 한국어 기준 문서가 없다.

그리고 한국어를 **함수 이름에만** 허용한다는 것을 더 좁혀야 한다. 다음은 회색지대이고
전부 영어로 못박기를 권한다:

- **파일·모듈 이름**: 항상 ASCII. 모듈 이름은 import 경로가 되고 `grep`·경로 지정·도구
  인자에 들어간다.
- **fixture 이름**: 항상 영어. fixture 이름은 **다른 함수의 매개변수 이름으로 쓰인다.**
  매개변수까지 한국어가 되면 "테스트 함수 이름 밖은 영어"가 바로 깨진다.
- **클래스·마커·파라미터화 id**: 영어.

즉 규칙 문장을 이렇게 바꾸기를 제안한다: *"한국어는 `def test_...` 함수 이름에만 쓴다.
파일 이름, fixture 이름, 클래스 이름, 그 밖의 모든 식별자는 영어다."*

#### 3.3 가장 큰 누락 — 도메인 용어집

초안에 없고, 이 프로젝트에서 이름 관련 위험 1순위다. 5명이 AI 보조로 병렬로 쓰면
**판정**이 `judgment` / `assessment` / `evaluation` 로, **기회**가 `opportunity` / `chance`
로 파일마다 달라진다. AI 는 매번 그럴듯하게 다르게 번역한다. 그렇게 갈라진 이름은
나중에 한꺼번에 고치기가 가장 비싼 종류의 부채다.

제안: `docs/glossary.md` 에 **한국어 용어 → 확정 영어 식별자** 표를 만들고, 명세 §7.2 가
이미 쓴 이름을 씨앗으로 삼는다 — `BehaviorGroup`, `BehaviorJudgment`, `OpportunityStatus`,
`JudgmentResult`, `HoldReason`, `PerformanceMode`, `SummaryStatus`, `valid_opportunities`,
`min_opportunities`. 새 도메인 명사를 만들 때는 이 표에 먼저 한 줄 추가한 뒤 코드에 쓴다.
첫 주에 30분이면 만들고, 이후 모든 Bolt 와 모든 AI 프롬프트가 같은 이름을 쓰게 된다.

부수 효과: 이 표는 domain-design(2.6)과 contract-design 의 입력이 되고, 한국어 UI 문구
(OC-06)와 영어 식별자 사이의 대응표도 겸한다.

#### 3.4 TC-10 의 세 값은 함께 다니게 만든다

`model_version`, `prompt_version`, `criteria_version` 을 매번 따로 넘기면 하나를 빠뜨리는
것을 아무도 못 잡는다. 제안: 세 필드를 묶은 값 객체(`JudgmentProvenance` 등) 하나로 다루고,
LLM 판정을 저장하는 테이블은 **세 컬럼을 `NOT NULL` 로** 둔다. "함께 저장한다"는 규칙이
사람의 주의력이 아니라 스키마 제약이 된다.

### 4. 오류 처리 — 초안에 사실상 비어 있는 절

`construction.md` 는 "통합 경계마다 오류 처리", "조용한 실패 금지", "복구 가능/치명 구분"을
요구한다. 초안의 `## Code Style` 에는 이에 해당하는 문장이 없다. 아래를 넣기를 제안한다.

#### 4.1 예외 계층과 오류 봉투

- `common/exceptions.py` 에 기반 예외 `AppError(code, message, http_status)` 하나와
  하위 예외: `NotFoundError`(404), `PermissionDeniedError`(403), `ValidationError`(422),
  `ConflictError`(409), `ProviderError`(502), `ProviderTimeoutError`(504).
- **`service` 는 `AppError` 하위만 던진다. `HTTPException` 은 던지지 않는다.** 이게 §1.3 의
  "`service` 가 `fastapi` 를 import 하지 않는다"를 실질적으로 강제한다. HTTP 로의 번역은
  `common/` 의 예외 핸들러 한 곳이 담당한다.
- 오류 봉투는 하나로 고정:
  `{"error": {"code": "...", "message": "...", "details": [...], "request_id": "..."}}`
- **`code` 는 영어 고정 토큰, `message` 는 한국어.** OC-06 은 사람이 읽는 것을 한국어로
  하라는 규칙이므로 `message` 는 한국어여야 하지만, `code` 는 프론트가 분기하는 기계용
  값이라 영어로 안정적이어야 한다. 초안의 OC-06 문장은 이 구분을 하지 않는다.
- `request_id` 는 미들웨어에서 요청마다 발급하고 로그와 응답에 같은 값을 넣는다. 5명이
  각자 컨테이너를 돌리는 환경에서 "어느 요청이 터졌는지"를 되짚는 유일한 수단이다.
- 처리되지 않은 예외는 500 + 같은 봉투로 나가되 **내부 메시지를 노출하지 않는다.**
  스택은 로그에만 남긴다.

#### 4.2 경계별 규약

**업로드(multipart)**

- 디스크에 쓰기 **전에** 검증한다: content-type 허용 목록(MediaRecorder 의 webm/opus),
  최대 크기(`MAX_UPLOAD_BYTES` 설정값 — 코드에 숫자를 박지 않는다), 빈 파일 거부.
  크기 초과는 413.
- `await file.read()` 로 통째로 메모리에 올리지 않고 청크로 흘려 쓴다. 긴 녹음이 들어오면
  컨테이너 메모리를 그대로 먹는다.
- 임시 경로에 쓴 뒤 성공 시 최종 경로로 옮긴다. 실패 시 임시 파일을 지운다. §1.2 의
  순서 규칙과 함께 "아무도 모르는 음성 파일"을 없앤다.
- 저장 경로는 **설정값**이고 `.gitignore` 에 들어간다. 코드에 경로를 박으면 컨테이너와
  로컬이 갈라진다.

**STT·LLM 제공자 호출**

- 모든 호출에 **명시적 타임아웃**을 준다. 기본값에 맡기지 않는다. connect 와 read 를
  따로 준다.
- 재시도는 타임아웃·연결 실패에만 **최대 1회**. 4xx 는 재시도하지 않는다. 무한 재시도
  루프를 만들지 않는다 — 데모 중에 화면이 멈추는 가장 흔한 원인이다.
- **제공자 예외는 `providers/` 를 넘지 않는다.** `httpx` 예외나 SDK 예외를 그대로 올려
  보내지 말고 어댑터 경계에서 `ProviderError` / `ProviderTimeoutError` 로 바꾼다. 그래야
  Mock↔live 교체(TC-06)가 상위 코드에 안 보인다.
- 로그에는 모델명·프롬프트 버전·소요 시간·`request_id` 를 남기고 **전사 본문은 남기지
  않는다.** 합성 데이터라도(SC-02) 발화 전문을 로그에 흘리는 습관은 그대로 굳는다.

**LLM 출력 파싱 — 이 프로젝트에 특히 중요**

LLM 출력은 **신뢰할 수 없는 입력**이다. Pydantic 으로 파싱하고, 계약을 어긴 결과가
리포트 전체를 500 으로 만들지 않게 한다. 명세 §7.4 의 `validate_evidence` 가 이미 존재하지
않는 발화 ID 를 `hold_reason=INVALID_EVIDENCE` 로 바꾸는 방식을 보여 준다. 이걸 일반
규칙으로 올린다: **LLM 계약 위반은 500 이 아니라 "보류"가 된다.** 데모에서 "서버 오류"가
뜨는 것과 "보류로 표시됨"이 뜨는 것의 차이다. TC-08(전사는 데이터 블록으로만 전달)과도
한 짝이다.

**설정 / Mock↔live 전환 — 빨리 실패하기**

- `ANALYSIS_MODE` 를 비롯한 환경변수는 **기동 시 한 번** `pydantic-settings` 로 파싱한다.
  알 수 없는 값이면 첫 요청이 아니라 **부팅에서 죽는다.**
- `ANALYSIS_MODE=live` 인데 필요한 키가 없으면 역시 부팅에서 죽는다. 요청이 들어온 뒤
  502 로 알게 되는 것은 늦다.
- 코드 곳곳에서 `os.environ` 을 직접 읽지 않는다. 설정 객체 하나를 주입한다.

**DB**

- 요청당 세션 하나를 `Depends` 로 주입한다. **커밋은 `service` 경계에서 한 번**,
  `repository` 는 커밋하지 않는다. 각자 커밋하면 부분 저장이 생기고, 그게 §1.1 의 삭제
  누수와 같은 계열의 사고다.
- `IntegrityError` 는 500 이 아니라 `ConflictError`(409)로 번역한다.
- `repository` 에서 예외를 잡아 `None` 을 반환하지 않는다. 조용한 실패다.
  "없음"과 "실패"는 서로 다른 값이어야 한다.

**프론트엔드**

- API 호출은 얇은 클라이언트 한 곳을 지나고, 거기서 오류 봉투를 타입 있는 오류로 바꾼다.
  컴포넌트마다 `fetch` 를 부르면 오류 처리가 화면 수만큼 갈린다.
- `alert()` 로 오류를 띄우지 않는다. 화면에 표시 자리를 둔다.
- TanStack Query 의 재시도 기본값을 그대로 두지 않는다. 업로드·전사 같은 비멱등 호출은
  재시도를 끈다.
- (열린 질문 — 내가 정할 자리가 아님) 전사는 오래 걸릴 수 있다. 동기 응답인지
  `202` + 폴링인지에 따라 오류 처리 모양이 완전히 달라진다. **contract-design 에서 닫아야
  한다**고 표시만 해 두기를 권한다.

### 5. 파일 구조 — §6 은 대체로 유지, 다만 빈 칸이 있다

#### 5.1 계층 우선 구조를 유지하는 데 동의한다

프레임워크 기본 지침은 기능 우선 구조를 권하지만, 여기서는 §6 의 계층 우선을 유지하는
편이 낫다. 이유: (a) 이미 명세로 확정되어 있고, (b) Java/Spring 배경에 그대로 읽히며
`service/` 안에 이미 5개 기능 묶음이 있어 업무 규칙은 기능별로 모여 있고, (c) 7주짜리
단일 백엔드에서 구조를 갈아엎는 비용이 이득보다 크다.

다만 계층 우선의 대가를 규칙으로 상쇄해야 한다: **한 기능을 고치면 `api/`, `service/x/`,
`repository/` 세 곳을 건드린다.** 그래서 —

- **`api/` 와 `repository/` 도 `service/` 와 똑같은 5개 이름으로 나눈다**:
  `conversation`, `assessment`, `training`, `record`, `privacy`. §6 은 `service/` 만
  나눠 놓고 나머지 둘은 평평하게 그려 놓았다. 이름이 세 계층에서 일치하면 세 자리를
  찾는 일이 기계적이 되고, 5인 병렬에서 파일 충돌도 줄어든다.

#### 5.2 §6 에 빠져 있어 지금 채워야 할 것

| 빠진 자리 | 제안 |
|---|---|
| **Pydantic 요청·응답 모델의 위치** | `api/<feature>/schemas.py`. 명세는 ORM 모델 반환을 금지하면서 응답 모델을 어디 두는지는 말하지 않는다. 안 정하면 5명이 5곳에 만든다 |
| **SQLAlchemy 모델의 위치** | `repository/models.py`(또는 `repository/<feature>/models.py`). 이 둘을 물리적으로 떨어뜨려 두는 것 자체가 TC-14 를 돕는다 |
| `config.py` | `pydantic-settings` 설정 객체 한 곳 |
| `db.py` | 엔진·세션·`Depends` 의존성 |
| `main.py` | 앱 조립, 예외 핸들러 등록, `request_id` 미들웨어 |
| `alembic/` + `alembic.ini` | `backend/` 아래. `app/` 안이 아니라 밖 |
| `tests/` | `backend/tests/` 아래에 `app/` 의 계층 구조를 거울처럼 둔다 |
| 업로드 저장 경로 | 예: `backend/storage/audio/`. 설정값이고 `.gitignore` 대상이며 Docker 볼륨으로 뺀다 |
| `scripts/` | `check.sh`, `seed.py`, `migrate.sh` — 초안이 본문에서 이미 언급했으니 구조에도 올린다 |

#### 5.3 §6 에서 모호한 자리 셋

1. **`app/fixtures/` (합성 데이터 기대 결과)** — 두 가지가 섞여 있다. Mock provider 가
   런타임에 반환하는 고정 응답은 **배포되는 코드의 일부**다(SC-04 상 mock 이 시연 경로다).
   반면 테스트의 기대 결과는 시연에 실리지 않는다. 섞어 두면 "테스트 데이터인데 왜
   패키지 안에 있지?"라는 이유로 누군가 지운다. 제안: `providers/mock_data/`(런타임,
   패키지 안) 와 `tests/fixtures/`(기대 결과, 패키지 밖)로 나눈다.
2. **`app/prompts/assess_v1.md`** — 파일 이름이 버전을 들고 있는데 코드가 버전 문자열을
   따로 들고 있으면 둘이 어긋난다(TC-10 이 저장하라는 그 값이다). 제안: 프롬프트 로더가
   **파일 이름에서 버전을 뽑아** `prompt_version` 으로 쓴다. 로더는 모듈 기준 상대 경로로
   읽는다(작업 디렉터리에 의존하면 컨테이너에서만 깨진다).
3. **`frontend/src/pages/` 의 `A1..A5` 명명** — 화면 ID 로 추적성을 유지한다는 목적에는
   동의하지만, `A1.tsx` 는 import 문과 스택 트레이스에서 아무 의미가 없다. 제안:
   **ID + 영어 역할** 형태(`A1UploadPage.tsx`, `B3GoalSelectPage.tsx`)로 둘 다 얻는다.
   UI 명세와의 대조는 접두사로 그대로 되고, 파일 이름은 ASCII 로 유지된다(§3.2).

### 6. `## Code Style` 통합용 문장 (리드가 그대로 쓸 수 있는 형태)

- (제안) 백엔드 계층은 `api` → `service` → `repository` 로만 내려간다. 올라오는 방향으로는
  `service` 가 `fastapi` 를, `repository` 가 `service` 를, `providers` 가 `service`·
  `repository` 를 import 하지 않는다. 제공자 인터페이스는 `service/ports.py` 에 두고
  구현체만 `providers/` 에 둔다.
- (제안) 계층 규칙은 사람이 아니라 `scripts/check.sh` 가 지킨다: Ruff `TID251` 로
  `app.repository` import 를 막고 `service`·`repository`·`tests` 만 예외로 푼다.
- (제안) 모든 라우트는 `response_model` 을 선언한다. SQLAlchemy 관계는 `lazy="raise"` 로
  둔다. ORM 객체가 API 쪽으로 새면 조용히 넘어가지 않고 그 자리에서 터진다.
- (제안) ORM 모델은 `repository/`, Pydantic 요청·응답 모델은 `api/<기능>/schemas.py`.
  `api/` 와 `repository/` 도 `service/` 와 같은 5개 기능 이름으로 나눈다.
- (제안) `service` 는 `common/exceptions.py` 의 `AppError` 하위만 던진다. HTTP 번역과
  오류 봉투는 `common/` 의 예외 핸들러 한 곳이 담당한다. 오류 봉투의 `code` 는 영어
  고정 토큰, `message` 는 한국어, `request_id` 는 항상 포함한다.
- (제안) 외부 경계(업로드, STT·LLM, DB)는 예외를 그대로 올려 보내지 않는다. 제공자 예외는
  `providers/` 를 넘지 않고 `ProviderError` 계열로 바뀐다. 모든 제공자 호출에 명시적
  타임아웃을 주고 재시도는 타임아웃·연결 실패에 한해 1회다.
- (제안) LLM 출력의 계약 위반은 서버 오류가 아니라 보류 판정으로 바꾼다(§7.4 의
  `validate_evidence` 를 일반 규칙으로).
- (제안) 설정은 기동 시 한 번 파싱한다. `ANALYSIS_MODE` 가 알 수 없는 값이거나 live 인데
  키가 없으면 부팅에서 실패한다. 코드에서 `os.environ` 을 직접 읽지 않는다.
- (제안) SQLAlchemy 는 **동기** 2.0 declarative(`Mapped[]` / `mapped_column()`)를 쓰고
  라우트도 동기 `def` 로 쓴다.
- (제안) 한국어는 `def test_...` 함수 이름에만 쓴다. 파일 이름, fixture 이름, 클래스
  이름을 포함한 그 밖의 모든 식별자는 영어다. 판정 규칙 자체를 검증하는 테스트는 한국어,
  기술적 동작을 검증하는 테스트는 영어로 이름 짓는다.
- (제안) 도메인 명사의 영어 식별자는 `docs/glossary.md` 의 표를 따른다. 새 명사는 표에
  먼저 올린 뒤 코드에 쓴다.
- (제안) Ruff 규칙 집합은 `E, F, I, UP, B, SIM, TID, RUF` 로 시작한다. mypy 는 전역
  `check_untyped_defs`, `app.service.*` 에만 `disallow_untyped_defs` 를 켠다.
  `scripts/check.sh` 는 ruff → mypy → pytest → vitest 순서로 돌고 첫 실패에서 멈춘다.
- (제안) 프론트엔드 화면 컴포넌트는 `화면ID + 영어 역할` 로 이름 짓는다(`A1UploadPage`).
  API 타입은 OpenAPI 에서 생성해 커밋하고 손으로 고치지 않는다.

### 7. `discovered-rules.md` 후보

초안이 이 문서를 좁게 유지한 판단에 동의한다. 다만 아래 둘은 **이미 확정된 제약을 코드
규칙의 말로 옮긴 것**이라 같은 기준으로 올라갈 자격이 있다고 본다(최종 판단은 인터뷰에서):

- ALWAYS 대화·음성 삭제는 `service/privacy/` 의 삭제 유스케이스 한 곳에서 시작하고, DB 행과
  파일 저장소를 모두 정리한다. 파일이 남으면 F07 은 지켜지지 않은 것이다
  `[constraint:TC-05][constraint:TC-14][raid:R3]`
- NEVER 제공자(`httpx`·SDK) 예외를 `providers/` 밖으로 그대로 올려 보낸다. Mock↔live 교체가
  상위 코드에 보이게 되어 TC-06 이 무력화된다 `[constraint:TC-06]`

나머지(도구 선택, Ruff 규칙 집합, 이름 규약)는 `team-practices.md` 에 남기는 데 동의한다.

### 8. 인터뷰에서 물어야 할 것 (내 영역 한정)

1. 계층 규칙을 기계가 강제하게 할 것인가, 리뷰로만 볼 것인가. 강제한다면 Ruff `TID251`
   수준(도구 추가 없음)인가 `import-linter` 수준(역방향까지)인가.
2. SQLAlchemy 를 **동기**로 못박아도 되는가. (권고: 그렇다)
3. 삭제 전파의 잠정 규칙(§1.2 의 순서 + 단일 진입점)을 지금 코드 규약으로 둘 것인가,
   domain-design(2.6)까지 아무 규칙 없이 갈 것인가. 그 사이에도 코드는 쓰인다.
4. 도메인 용어집(`docs/glossary.md`)을 첫 주에 만들 것인가.
5. 마이그레이션을 컨테이너 기동 시 자동 적용할 것인가, 사람이 부를 것인가.
6. 화면 컴포넌트 이름을 `A1` 그대로 둘 것인가, `A1UploadPage` 형태로 할 것인가.

## Positions

- AGREE: `api` → `service` → `repository` 와 Pydantic 응답 모델을 코드 규약으로 올린 것 — TC-14 가 요구한 대체 규칙의 올바른 출발점이고 명세 §5 와 정확히 일치한다.
- AGREE: 계층 경계의 **최종** 정의를 domain-design(2.6)으로 넘기고 그때까지 잠정 규칙으로 간다는 처리 — 단계 분담이 TC-14·R3 의 지정과 맞다.
- AGREE: Ruff 하나로 lint 와 format 을 합친 것 — org 기본값(Black)을 뒤집은 것이 아니라 좁힌 것이라는 논리가 맞고, 맞출 설정 파일이 줄어드는 이득이 R1 에 직접 닿는다.
- AGREE: uv 채택 — 가상환경 활성화 단계를 없애 준다는 점이 Python 초심자 5명에게 Poetry 대비 실질적 이득이다.
- AGREE: Alembic 채택 — SQLAlchemy 와 짝이고 모델에서 마이그레이션 초안을 뽑을 수 있어 대안 대비 비용이 가장 낮다.
- AGREE: SQLAlchemy 2.0 declarative **채택 결정 자체** — `Mapped[]` 선언이 JPA 와 읽는 느낌이 가깝고 mypy 가 그대로 이해해 Java 배경에 유리하다.
- AGREE: 테스트 함수 이름에 한국어를 허용한 것 — 판정 규칙 이름이 한국어라 기준 문서와의 대조 비용이 실제로 줄어든다(경계는 아래 OBJECT 참조).
- AGREE: `discovered-rules.md` 를 확정 제약만으로 좁게 유지하고 취향은 `team-practices.md` 에 남긴 분리 — 무엇이 구속력 있는 규칙인지 흐려지지 않는다.
- AGREE: 이름은 Python snake_case / TypeScript camelCase, 사람이 읽는 것은 한국어(OC-06) — 언어 관용구를 따르라는 org 기본값과 일치한다.
- OBJECT: "계층 규칙과 Pydantic 응답 모델이 R3(삭제 전파 누수)의 자리를 메운다"는 서술 — TC-05 때문에 저장소가 DB 와 파일 둘이라, 계층 규칙을 100% 지켜도 음성 파일은 남는다. 삭제 단일 진입점과 파일·행의 순서 규칙이 추가로 필요하다(§1.1~1.2).
- OBJECT: 계층 규칙에 역방향 금지가 없다 — `service` 가 `fastapi` 를 import 하지 않는다는 문장이 없으면 `HTTPException` 이 `service` 로 내려오고 계층은 한 주 만에 섞인다(§1.3).
- OBJECT: 제공자 인터페이스의 위치가 지정되지 않았다 — Protocol 이 `providers/` 에 있으면 `ANALYSIS_MODE=mock` 인데 live SDK 부재로 죽는 실패가 난다. `service/ports.py` 로 못박아야 한다(§1.3).
- OBJECT: SQLModel 기각 사유가 사실과 다르다 — SQLModel 에서도 table 모델과 응답 모델은 분리 가능하므로 "정면으로 어긋난다"는 과장이다. 결정은 유지하되 근거를 "두 가지 사고 모형", "유지보수 폭", "금지된 것이 기본 경로"로 고쳐야 `inception.md` 의 대안 검토 요건을 만족한다(§2.6).
- OBJECT: SQLAlchemy 의 sync/async 가 지정되지 않았다 — async 로 흘러가면 greenlet 오류와 테스트 복잡도가 따라오는데 이 프로젝트에는 동시성 요구가 없다. 동기로 못박아야 한다(§2.2).
- OBJECT: "mypy 를 non-strict 로 켜되 `service/` 공개 함수는 타입 필수"는 그대로는 강제되지 않는다 — 기본 mypy 는 미어노테이션 함수 본문을 건너뛰므로 타입을 안 붙인 쪽이 오히려 검사에서 빠진다. `check_untyped_defs` 전역 + `app.service.*` 에 `disallow_untyped_defs` 가 필요하다(§2.5).
- OBJECT: Ruff 를 쓴다고만 적고 규칙 집합을 정하지 않았다 — Ruff 기본값은 사실상 문법 오류 검출기라 린트 게이트가 성립하지 않는다. 특히 `I`(import 정렬)가 없으면 5인 병렬에서 import 순서가 병합 충돌을 만든다(§2.4).
- OBJECT: `## Code Style` 에 오류 처리 규약이 없다 — `construction.md` 가 통합 경계마다 오류 처리와 조용한 실패 금지를 요구하는데, 업로드·제공자 호출·LLM 출력 파싱·DB 어디에도 대응 문장이 없다(§4).
- OBJECT: "패키지 구조는 tech-env §6 을 그대로 쓴다"는 문장 — §6 에는 Pydantic 응답 모델과 ORM 모델의 위치, `alembic/`, 설정·세션·앱 조립 파일, `tests/`, 업로드 저장 경로가 없다. 정하지 않으면 5명이 5곳에 만든다(§5.2).
- OBJECT: 한국어 허용 경계가 "테스트 함수 이름 밖의 식별자는 영어"로만 되어 있어 파일 이름과 fixture 이름이 회색지대로 남는다 — fixture 이름은 다른 테스트의 매개변수 이름이 되므로 한국어가 들어오면 그 규칙이 바로 깨진다. 명세 §7.3 과 §7.4 가 이미 두 스타일로 갈려 있다(§3.1~3.2).
- OBJECT: 도메인 용어집이 없다 — AI 보조로 5명이 병렬로 쓰면 "판정"·"기회"의 영어 식별자가 파일마다 갈라진다. 명세 §7.2 의 이름을 씨앗으로 한 표를 첫 주에 만들어야 한다(§3.3).
