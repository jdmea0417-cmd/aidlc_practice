## 각 참여자가 조사·추론한 것

**리드(릴리스 엔지니어).** 작업 공간에 관찰 대상이 있는지부터 확인했다. 이 프로젝트는
그린필드이고 `[state]`, 작업 공간은 **git 저장소가 아니다**. 브랜치 이력·커밋 관행·병합
방식·코드 리뷰 흔적을 읽어낼 대상이 존재하지 않으므로, 브라운필드에서 이 단계가 하는
"이력에서 관행을 읽어내는" 작업은 수행 불가능했다. `[team]` 은 모든 절의 본문이 HTML
주석뿐이라 `rules-reading.md` §1 기준으로 비어 있고, 따라서 되살릴 기존 확정치가 없다.
그래서 출발점을 `[org]` 의 다섯 절로 잡고, 그중 전제가 성립하지 않는 두 지점(저장소를
전제하는 `## Way of Working`, 환경 승격을 전제하는 `## Deployment`)에 무엇이 대신
들어가는지를 초안으로 제안한 뒤 인터뷰에 올렸다.

**품질 담당** `[quality]`. 테스트가 실제로 무엇을 지키는지를 항목별로 따졌다. 가장 큰
기여 셋: (1) 초안이 `custom` 의 근거로 든 가정 A4 가 실은 test-after 서술이라는 정정,
(2) 라인 커버리지가 이 규칙 엔진에서 아무것도 지키지 못한다는 지적 — `[spec:02]` §7.2 의
`summarize()` 는 본체가 전부 조건이라 한 갈래만 타는 테스트 하나로 라인 커버리지가 다
나온다, (3) Mock 픽스처가 `[spec:05]` 의 기대 판정과 어긋나도 SM1·E2E·단위 테스트가 전부
초록인 채로 전 구간이 일관되게 거짓말한다는 구멍. 더해서 `build-and-test`(3.6)가 EXECUTE
라는 사실이 초안에서 누락되었다는 점, `performance-validation`(4.6) SKIP 으로 PM-01~PM-04
를 확인할 주체가 없다는 점, Testcontainers 격리 규약이 없다는 점을 지적했다.

**개발 담당** `[developer]`. "무엇을 지킬지는 적혀 있는데 무엇이 그것을 지키게 하는지가
없다"로 요약했다. 계층 규칙이 R3(F07 삭제 전파 누수)을 대신하지 못한다는 것을 근거와 함께
보였다 — TC-05 때문에 저장소가 DB 와 파일 둘이라 `service` 를 경유해도 파일이 디스크에
남으면 F07 은 깨진 것이다. 역방향 import 금지, 제공자 Protocol 의 위치, SQLAlchemy 의
sync/async 미지정, mypy 가 실제로는 강제되지 않는다는 점, Ruff 규칙 집합 부재, 오류 처리
절 자체의 부재, 명세 §6 이 비워 둔 파일 위치들, 한국어 허용 경계의 회색지대, 도메인
용어집 부재를 지적했다. 그리고 초안의 SQLModel 기각 사유가 사실과 다르다는 정정을 냈다.

**보안 담당** `[devsecops]`. 규제 항목을 이번 범위에서 비워 둔 결정(D-34)을 도구로
되살리지 않는다는 원칙을 먼저 세우고, 깨졌을 때 실제로 무언가를 잃는 것만 제안했다. 가장
시급한 발견은 `.gitignore` 가 **이미 존재한다**는 사실과, 그 파일이 프레임워크 소유 블록
하나뿐이라 `.env` 가 첫 커밋에 들어간다는 것이다. 더해서 TC-08 규칙 문안이 그대로는 강제
불가능하다는 점(데이터가 구분자를 포함할 수 있으면 구분자는 경계가 아니다),
`ANALYSIS_MODE` 가 어긋났을 때의 동작이 없다는 점, 잠금 파일에 대한 언급이 세 문서
어디에도 없다는 점, `react/no-danger` 누락을 지적했다. 의도적으로 하지 않기로 한 것
(DAST, 이미지 스캔, SBOM, 상시 비밀값 스캐너, Dependabot, 서명 커밋, 비밀값 관리 서비스,
별도 위협 모델 문서, 규제 통제 매핑)은 이유와 함께 기여 파일 §9 에 있다 — 빠뜨린 것이
아니라 뺀 것이다.

## 범위 변경 기록 — F07 을 Should 에서 Must 로

`[Q7]` = B 와 `[FU1]` = A 로 F07(정정·삭제)의 **두 기능 모두**가 Must 로 올라갔다. 전사
정정 후 재검토 표시는 이미 Must 인 화면 A3 위에 얹히지만, 삭제 시 연결 항목 처리는
Should 였던 화면 C5 를 열어야 한다. 즉 **화면 하나가 범위 안으로 들어온다.** 이것이 이
결정의 실제 비용이다.

근거는 `[spec:05]` 의 세 번째 합성 대화 S3 다. S3 에 붙은 검증 항목 네 개 중 2번(전사
정정 후 관련 판정 재검토 표시)과 4번(삭제 시 연결 항목 처리)이 F07 에 걸려 있어, Must 만
만들면 SM1 의 "3건이 끊김 없이 이어진다"는 통과하지만 S3 가 원래 확인하려던 것의 절반은
확인되지 않은 채 남는다 `[quality §7]`.

**아래 표가 `scope-document.md` 에서 다시 써야 할 확정 항목 6건의 작업 목록이다.**
`scope-document.md` 는 이 단계에서 고치지 않는다. 다른 문서는 이 표를 가리킨다.

**갱신(2026-09-17)**: scope-definition(1.4)을 다시 실행해 6건 전부를 반영했다
(질문 파일 F3·F4·F5). 반영 과정에서 화면 C5 의 처리가 한 번 바뀌었다 — C5 전체를
Must 로 올리는 안(F3 = B)이 보호자 권한을 Should 로 둔 확정 결정과 부딪혀,
C5 를 쪼개 삭제 관련 부분만 Must 로 올리는 안(F5 = C)으로 확정되었다. 아래 6번의
"C5 의 일부가 Must 로 딸려 올라간다"가 그 방식으로 실현되었다.

### 되돌리기가 어떻게 끝났는가 (2026-09-17)

위 표는 이 단계가 만든 **작업 목록**이고, 여기부터는 그 목록이 실제로 어떻게 닫혔는지에
대한 기록이다 `[FU4]`. 관행 결정은 하나도 바뀌지 않았다 — 바뀐 것은 상위 문서 쪽이며,
이 절은 그 결과를 이 단계의 판단 근거 안에 되돌려 놓는다.

**(1) 이데이션 네 단계를 다시 열어 전부 재승인했다.** 1.1 intent-capture → 1.3
feasibility → 1.4 scope-definition → 1.7 approval-handoff 순으로 다시 실행했고, 네
단계 모두 승인 게이트를 다시 통과했다 `[FU4]`. 위 표의 6건은 전부 반영되어 상태가
"반영됨(2026-09-17)"이다.

**(2) 반영 과정에서 화면 C5 의 처리가 한 번 바뀌었다.** 표 위의 갱신 문단이 그 사실을
적었고, 여기에는 **왜 바뀌었는지**를 남긴다. C5 **전체**를 Must 로 올리는 안은 C5 가
보호자 열람 권한 전환을 함께 담고 있어, Must 가 된 권한 전환이 Should 로 남는 정식
인증에 의존하게 만든다. 즉 Must 항목이 Should 항목에 의존하는 자리를 새로 만드는 안이라
철회되었다 `[log §6]`. 대신 **C5 를 쪼개 삭제 관련 부분만 Must 로 올리는 안**으로
확정되었다 `[scope §3.1][scope §3.2]`. 쪼갠 뒤 등급 경계를 다시 대조한 결과, Must 로
올라간 PU-08 의 의존은 PU-01·PU-03·PU-06 뿐이고 셋 다 Must 이므로 그 자리는 생기지
않았다 `[backlog §3]`.

**(3) 단계 경계 검증을 재실행해 통과했다** `[verify]`. 앞선 산출물이 바뀌었으므로 부분

## 계획 변경 기록 — CI 파이프라인 단계(3.7)를 다시 넣음

`[Q1]` = B 로 병합 전 검사를 GitHub Actions 가 강제하기로 했는데, 그 시점의 계획에서
**ci-pipeline(3.7)이 SKIP 이었다.** 즉 Actions 워크플로 파일을 작성할 단계가 계획에 없는
채로 "Actions 가 강제한다"가 확정될 뻔했다. 건너뛴 단계가 담당하던 일이 주인 없이 남아
있는지를 확인한 결과 `[FU3]`, **ci-pipeline(3.7)을 계획에 다시 넣었다.**

- 실행 단계 수: **20 → 21**. `[state]` 의 `Stages to Execute` 에 3.7 이 들어가고
  `Total Stages` 가 21 이다(반영 완료).
- 이 변경은 클라우드 배포가 없다는 결정과 무관하다. **Actions 는 배포가 아니라 검사다.**
  `[constraint:SC-01]` 과 Operation 단계 SKIP 은 그대로 유지된다.
- 따라서 초안의 "CI 가 없으니 로컬 `scripts/check.sh` 로 대신한다"는 서술은 더 이상 맞지
  않는다. 로컬 `scripts/check.sh` 는 개발자 편의 수단으로 남을 수 있으나 **병합 전 강제
  수단은 GitHub Actions** 다. 세 산출물에서 이 서술을 모두 고쳤다.
- 앞선 R7 이 기록한 증가(19 → 20)에 이어 두 번째 증가다. 마감 2026-11-05 과 R5 는 그대로인
  채 부담이 한 단계 더 늘었으므로, `delivery-planning`(2.9)의 일정 재검증에 이 증가분을
  포함해야 한다 `[raid:R5][raid:R7]`.

### 같은 부담 기록에 얹히는 것 — Must 비율 73% (2026-09-17)

단계 수만 늘어난 것이 아니다. 같은 회차에 **범위 안쪽의 밀도**도 올라갔고, 둘은 같은
일정을 누르므로 한자리에 적는다 `[FU4]`.

- **F07 승격으로 proto-Unit 의 Must 가 7개에서 8개**(PU-08 추가)가 되어, 전체 11개 중

- 프레임워크 지침은 "Must 는 계획 용량의 60% 를 넘지 않는다"인데, 원래도 넘던 것이
  **초과 폭이 더 커졌다**.
- **수치를 맞추려고 내용을 줄이지 않았다.** PU-01~PU-07 은 곧 성공 기준 SM1 의 종단 경로
  자체라 더 줄이면 최소 가치 범위가 무너지고, PU-08(F07)은 그 성공 기준을 판정할
  자료(합성 대화 S3)의 **절반을 확인 가능하게 만드는** 항목이다 `[spec:05]`. 이 둘 중
  어느 쪽을 덜어도 승격의 이유 자체가 사라진다. **따라서 이 초과는 의도된 것으로
  기록되었다** `[backlog §2]`. 경계 검증도 같은 판정이다 — 지침 초과는 모순이 아니며

- **`delivery-planning`(2.9)의 일정 재검증에는 세 가지를 모두 넣어야 한다**: 단계 증가

  보면 축소 여지가 실제보다 크게 보인다 `[verify §6]`.

## 건너뛴 단계로 인한 입력 부재 — 결손이 아니라 범위 밖

`reverse-engineering`(2.1)이 **SKIP** 이다 `[state]`. 이 단계는 브라운필드 코드베이스에서
기존 구조·관행·제약을 읽어내 하위 단계에 넘기는 일을 하는데, 이 프로젝트는 그린필드이고
작업 공간에 기존 코드가 없으므로 넘겨줄 것이 애초에 없다. **따라서
`practices-discovery`(2.2)에 브라운필드 입력이 없는 것은 누락이 아니라 범위 밖이다.**
하위 단계는 이 부재를 결손으로 읽지 않아야 한다.

같은 이유로 이 단계가 관찰할 수 없었던 것들도 결손이 아니다. 작업 공간이 git 저장소가
아니어서 브랜치 전략·커밋 관행·병합 방식·기존 린터 설정·기존 커버리지 수준을 관찰할 대상이
없었고, 그 자리는 전부 인터뷰가 사람의 선택으로 채웠다(`[Q1]`, `[Q3]`, `[Q4]`, `[Q6]`).

다른 SKIP 단계가 남긴 공백 중 이 단계가 받은 것 하나를 기록한다:
`performance-validation`(4.6)이 SKIP 이라 `[constraint]` 의 PM-01~PM-04 를 확인할 단계가
없다. 부하 시험이 필요한 것이 아니라 기존 테스트 안의 단언 한 줄씩이면 되므로,
`team-practices.md` `## Testing Posture` 의 표가 이 공백을 명시적으로 받았다
`[quality §9(d)]`.

## 판정 정확성에 관한 남은 위험 — 사람이 알고 선택한 절충

이것은 결함이 아니다. 사람이 위험을 제시받고 그 위에서 선택했다는 사실을 기록한다.

세 답을 겹치면 판정이 맞는지를 지키는 수단이 한 군데로 모인다.

- `[Q3]` = C: 모든 계층을 구현한 뒤 테스트를 쓴다. 기대 판정표를 테스트로 먼저 고정하지
  않는다.
- `[Q4]` = B: `service/` 라인 80% 하나만. 판정 로직에 분기 바닥이 없다.
- `[Q5]` = B: 종단 실행은 끊김 없이 지나가는지만 본다. 기대 판정과 대조하지 않는다.

각각은 "단순하게 간다"는 일관된 선택이고 그 자체로 모순이 아니다. 다만 셋을 합치면
**판정이 맞는지는 구현 후에 쓰는 단위 테스트에만 달린다.**

품질 담당이 지적한 사실을 그대로 옮긴다 `[quality §3(a)]`: `[spec:02]` §7.2 의
`summarize()` 는 본체가 전부 조건이다(`j.mode == mode`, `opportunity is PRESENT`,
`hold_reason is None`, `len(valid) < min_opportunities`). **이 네 술어를 한 갈래만 타는
테스트 하나로 라인 커버리지가 다 나온다.** 보류가 분모에서 빠지는지, 독립과 도움 후가
안 섞이는지는 전혀 확인되지 않은 채로 바닥을 통과할 수 있다. 즉 라인 바닥은 그 단위
테스트가 실제로 여러 갈래를 보는지를 보장하지 못한다.

여기에 `[Q7]` 이 얹힌다. F07 을 Must 로 올린 이유는 S3 를 원래 의도대로 전부 확인하기
위해서인데, `[Q7]` 표의 검증 항목 3(보류가 실패로 집계되지 않음 — `[spec:05]` 에서는 S2
의 검증 포인트이자 S3 의 보류 3건이 걸린 자리다)은 기능이 있느냐가 아니라 **판정이
맞느냐**를 보는 항목이다. `[Q5]` = B 아래에서는 종단 실행이 이것을 보지 않으므로 이 항목도
같은 단위 테스트에 맡겨진다.

이 위험을 제시받은 뒤 사람은 `[FU2]` 에서 **B** 를 골랐다: 분기 커버리지 바닥을 되돌리지도
(`C`), 종단 실행에 기대 판정 대조를 되돌리지도(`D`) 않고, **기대 판정표를 픽스처 파일로
고정하는 것만 의무로 넣는다.** 테스트 시점은 `[Q3]` 대로 구현 후이고, 기대값의 출처만
문서에서 기계가 읽는 파일로 옮겨 고정된다.

**그래서 남는 위험은 이것이다**: 픽스처가 기대 판정을 정확히 옮겼고 단위 테스트가 그
픽스처의 여러 갈래를 실제로 읽는다는 것이 참이어야만 판정 정확성이 지켜진다. 픽스처는
고정되었으므로 전자의 위험은 줄었고(Mock 픽스처 대조 테스트가 이를 추가로 받는다
`[quality §4]`), **후자는 바닥이 없으므로 테스트를 쓰는 사람의 판단에 남는다.** 알고 한
선택이며, 되돌리고 싶어지면 `[Q4]` 를 A 로 바꾸는 것이 가장 싼 경로다(`--cov-branch` +
`fail_under` 설정 한 줄 `[quality §3(a)]`).

## 초안에서 정정한 사실관계 세 건

`[phase:inception]` 이 요구하는 "대안 검토의 정확성"과 `[project]` 의 "근거만 없는
서술은 지우지 말고 근거를 만든다"에 따라, 검토가 지적한 사실관계 오류를 여기에 남긴다.

**(1) 가정 A4 인용 오류.** 초안 `team-practices.md` 의 Testing Posture 는 A4 가 "원래
테스트 케이스를 그대로 옮겨 통과시킨다"를 확인 방법으로 못박았다는 점을 test-first 의
근거로 들었다. A4 의 원문은 **"이식한 코드에 원래 테스트 케이스(보류·기회없음 분모
제외)를 그대로 옮겨 통과시킨다"** 이므로 `[raid:A4]`, 코드를 먼저 옮기고 나서 테스트를
옮기는 **test-after 서술**이다 `[quality §2]`. 실제 근거는 A4 가 아니라 **기대 판정이
코드와 독립적으로 이미 문서에 존재한다**는 사실이었다(`[spec:05]` 의 3건 기대 판정표,
`[spec:02]` §7.3 의 테스트 예시). `[Q3]` = C 로 test-after 가 채택되었으므로 잘못된 인용은
제거했고, 그 사실(기대 판정의 사전 존재)은 `[FU2]` 의 픽스처 고정 의무를 떠받치는 근거로
자리를 옮겼다.

**(2) SQLModel 기각 근거.** 초안은 "SQLModel 은 ORM 모델과 응답 모델을 같은 클래스로
합치는 방식이라 TC-14 와 정면으로 어긋난다 — 결정적"이라고 썼다. 이건 과장이다.
**SQLModel 에서도 `table=True` 모델과 응답용 모델을 분리해서 쓸 수 있다.** 합치는 것은
강한 관용구이지 구조적 강제가 아니다 `[developer §2.6]`. 결론(SQLAlchemy 2.0 채택)은
`[Q6]` = A 로 확정되었으므로 유지하고, 근거만 아래 표대로 바꿨다.

**(3) `.gitignore` 실존.** 초안은 저장소가 없으니 `.gitignore` 도 없다는 전제로
"`.gitignore` 에 `.env` 를 넣는다"고 썼으나, 파일은 이미 존재한다(저장소 루트, 85줄)
`[devsecops §1]`. 내용은 전부 `# BEGIN AI-DLC:gitignore` / `# END AI-DLC:gitignore`
마커로 감싼 프레임워크 소유 블록이고, 팀에 필요한 항목은 `node_modules` 를 빼면 하나도
없다. 그래서 두 가지가 규칙이 되었다: 팀 항목은 마커 **아래**에 별도 구역으로 넣을 것
(안에 넣으면 프레임워크가 블록을 다시 쓸 때 사라진다), 그리고 순서는 "ignore 규칙 추가 →
`git init` → 첫 `git add`" 일 것. `team-practices.md` `## Way of Working` 에 반영했다.

## 대안을 함께 본 판단

`[phase:inception]` 의 "결정에는 최소 두 개의 대안 검토가 따라야 한다"에 따른다. 아래
네 건은 인터뷰에서 확정되었고, 표는 그 확정의 근거다.

### 1. 테스트 방법론 — test-after 로 확정 `[Q3]` = C

| 선택지 | 근거 | 결과 |
|---|---|---|
| **test-after** (확정) | 방법론이 하나면 어느 쪽인지 헷갈리지 않는다. Python·pytest 가 처음인 팀에 새 습관을 요구하지 않는다 `[raid:R1]` | **채택** |
| `custom` (규칙 모듈만 선행) | 기대 판정이 이미 문서로 존재해 선행 비용이 사실상 0 이다 `[quality §2]` | 초안의 제안이었으나 채택되지 않음. 경계가 산문으로 지목되어 Code Generation 이 읽을 때 사람마다 달라진다는 지적도 있었다 `[quality §1]` |
| `tdd` 전면 | 규칙 엔진에는 잘 맞는다 | 전면 적용은 R1(Python 초심자)과 R5(7주)를 동시에 악화시킨다 |

`custom` 을 버리면서 잃는 것 — 기대 판정표가 구현보다 먼저 존재한다는 보장 — 은 `[FU2]`
의 픽스처 고정 의무가 다른 방식으로 받는다. 시점은 구현 후지만 **기대값의 출처는 구현과
독립적인 문서**로 남는다.

### 2. ORM — SQLAlchemy 2.0(동기)로 확정 `[Q6]` = A

| 선택지 | 장점 | 단점 |
|---|---|---|
| **SQLAlchemy 2.0 declarative, 동기** (확정) | FastAPI 생태계의 사실상 표준, Alembic 과 직결, `Mapped[]` 선언이 JPA 엔티티와 읽는 느낌이 가깝고 mypy 가 그대로 이해한다 `[developer §2.2]` | 보일러플레이트가 있고 학습 곡선이 얕지 않다 |
| SQLModel | 코드가 짧고 Pydantic 과 붙어 있다. **table 모델과 응답 모델을 분리하는 것도 가능하다** | (1) SQLAlchemy 위의 얇은 층이라 조금만 복잡한 질의로 가면 결국 SQLAlchemy 를 직접 쓰게 되어 **두 가지 사고 모형을 동시에 배운다** `[raid:R1]`, (2) 유지보수 폭이 좁아 Pydantic·SQLAlchemy 주요 버전 대응이 늦은 전력이 있고 7주에 한 주를 막히면 복구할 여유가 없다 `[raid:R5]`, (3) 관용구가 TC-14 가 금지한 형태 쪽으로 기울어 있어 **금지된 것이 기본 경로**가 된다 |
| 원시 SQL + asyncpg | 완전한 통제 | 7주 안에 매핑을 손으로 쓰는 비용이 크고 마이그레이션 도구가 따로 필요하다 |

**동기(sync)로 못박은 이유** `[developer §2.2]`: async SQLAlchemy 를 고르면 `await` 전파,
lazy load 금지에서 오는 `MissingGreenlet`, 테스트 픽스처 복잡도, Testcontainers 설정 증가가
따라온다. 이 프로젝트는 로컬 데모에 사용자 5명이라 동시성 요구가 없고
`[constraint:SC-01][constraint:OC-01]`, `[spec:02]` §7.1 의 예시 자체가 이미 동기 `def` 다.
`[questions]` 의 Q6 선택지 문안도 "SQLAlchemy 2.0(동기)"로 되어 있어 사람이 이 형태로
확정했다.

### 3. 패키지 관리자 — uv 로 확정 `[Q6]` = A

| 선택지 | 장점 | 단점 |
|---|---|---|
| **uv** (확정) | `uv run` 을 쓰면 **가상환경 활성화라는 개념 자체가 사라진다** — Python 이 처음인 사람이 첫 주에 가장 많이 넘어지는 자리다 `[developer §2.1]`. 의존성과 도구 설정이 `pyproject.toml` 하나로 모인다 | 비교적 새 도구라 한국어 자료가 적다 |
| Poetry | 자료가 많고 성숙하다 | 가상환경 활성화 단계를 없애지 못한다. 설정과 잠금 처리가 느리다 |
| pip + requirements.txt | 배울 것이 가장 적다 | 잠금이 약해 5인 환경에서 재현성이 흔들린다 |

초안은 "Poetry 경험자가 있으면 뒤집는다"를 인터뷰 질문으로 넣었고, 개발 담당은 그 기준이
너무 낮다고 지적했다 — 뒤집을 근거는 "써 봤다"가 아니라 "잠금 충돌이 났을 때 풀 수
있다"여야 한다 `[developer §2.1]`. 사람은 `[Q6]` 에서 A(uv 유지)를 골랐고 패키지 관리자
변경(선택지 B)을 요청하지 않았다.

### 4. 포매터·린터 — Ruff 하나 (유지)

| 선택지 | 장점 | 단점 |
|---|---|---|
| **Ruff (lint + format + `S` 보안 룰셋)** (유지) | 도구 하나, 설정 하나. Black 과 같은 결과를 내도록 만들어진 구현이라 `[org]` 기본값을 좁힌 것이지 뒤집은 것이 아니다. `S` 룰셋으로 도구를 늘리지 않고 SAST 를 얻는다 `[devsecops §3]` | 아주 드문 Black 옵션 일부가 아직 없다. **규칙 집합을 정하지 않으면 사실상 문법 오류 검출기다** `[developer §2.4]` |
| Black + isort + flake8 | `[org]` 이 직접 이름을 든 조합 | 도구 셋, 설정 셋. Python 초심자에게 맞출 것이 늘어난다 `[raid:R1]` |
| Ruff + 별도 SAST(Semgrep·CodeQL) | 더 깊은 정적 분석 | 규칙 관리와 결과 분류 시간이 이 규모에서 Ruff `S` 가 이미 잡는 것을 크게 넘지 못한다 `[devsecops §3]` |

지적된 단점(규칙 집합 미지정)은 `team-practices.md` `## Code Style` 에서
`E, F, I, UP, B, SIM, TID, RUF, S` 출발 집합으로 닫았다.

## 통합하지 않은 반대 의견과 그 이유

세 기여 파일의 `OBJECT:` 중 이 통합에서 **채택하지 않은 것**과 그 판단이다. 나머지
`OBJECT:` 는 `team-practices.md` 또는 `discovered-rules.md` 에 반영했다.

| 반대 의견 | 왜 채택하지 않았나 |
|---|---|
| `[quality]` 커버리지 지표를 라인이 아니라 **분기**로 바꾸고 `service/assessment/` 에 분기 90% 를 걸자 | 인터뷰가 닫았다. `[Q4]` 에서 그 선택지(A)가 제시되었고 사람이 **B**(라인 80% 하나)를 골랐다. 이 선택이 남기는 위험은 위 "판정 정확성에 관한 남은 위험"에 기록했다 |
| `[quality]` 바닥을 `service/` 한 덩어리가 아니라 하위 패키지별로 걸자 | 같은 이유. `[Q4]` = B 가 "`service/` 전체에 라인 80% 하나만"을 명시적으로 고른 답이다 |
| `[quality]` 배포 성공 정의에 `[spec:05]` 의 기대 판정 대조를 넣자 | 인터뷰가 닫았다. `[Q5]` 에서 그 선택지(A)가 제시되었고 사람이 **B**(끊김 없이 지나가면 성공)를 골랐다. 판정 정확성은 `[FU2]` 의 픽스처 기반 단위 테스트가 받는다 |
| `[developer]` 삭제 단일 진입점과 파일·행 순서를 `discovered-rules.md` 의 `ALWAYS` 로 올리자 | 내용은 채택해 `team-practices.md` `## Code Style` 에 **잠정 규칙**으로 넣었으나, `project.md` 에 영구 도장을 찍지는 않았다. 삭제 전파 경계의 최종 정의는 domain-design(2.6)이 닫기로 되어 있고 `[constraint:TC-14][raid:R3]`, 지금 규칙으로 굳히면 2.6 의 결론과 충돌할 수 있다. 2.6 이 닫은 뒤 승격을 다시 판단한다 |
| `[developer]` 제공자 예외를 `providers/` 밖으로 내보내지 않는 것을 `NEVER` 로 올리자 | 같은 계열 판단. 확정 제약 TC-06 에서 파생된 **코드 규약**이라 `team-practices.md` `## Code Style` 이 단일 출처다. 규칙 절에 복제하면 어느 쪽이 기준인지 흐려진다 |
| `[devsecops]` 잠금 파일 커밋을 `ALWAYS` 로 올리자 | 사람이 직접 고른 하드 제약이 아니라 `[Q6]` 의 도구 확정에서 파생된 운영 규약이다. `team-practices.md` `## Way of Working` 에 넣었다 |
| `[devsecops]` `LlmProvider` 가 `(prompt_id, prompt_version, data)` 를 받게 하자 | 요구 자체(지시문과 데이터의 분리를 인터페이스가 보존할 것)는 TC-08 규칙 문안 강화로 반영했다. 구체적 시그니처는 contract-design(2.8)과 domain-design(2.6)이 닫는 자리라 여기서 못박지 않았다. 다만 "제공자가 미정이라는 사실이 오히려 지금 정해야 하는 이유"라는 지적 `[devsecops §4(b)]` 은 그 두 단계에 넘긴다 |
| `[quality]` `scripts/check.sh` 를 무엇이 강제하는가(리뷰 필수 항목 / `pre-push` 훅 / Actions) | 셋 중 Actions 로 닫혔다 `[Q1][FU3]`. 리뷰 필수 확인은 "Actions 검사 통과 여부"로 남겼고, `pre-push` 훅은 채택하지 않았다 — 권위 있는 게이트가 둘이면 어느 쪽이 기준인지 흐려진다 |

**인터뷰가 저절로 해소한 반대 의견 두 건**도 기록한다. `[quality]` 의 "Playwright 3건이
Must 범위에서 전부 성립하지 않는다"는 `[Q7]` = B / `[FU1]` = A 로 F07·C5 가 Must 가 되면서
해소되었다. `[quality]` 의 "`Ordering` 의 선행 대상 경계가 산문이라 흔들린다"는 `[Q3]` = C
로 방법론이 하나가 되면서 선행 대상 자체가 사라져 해소되었다.

## 인터뷰가 닫지 못하고 남은 미결 사항

이 단계가 닫지 못한 것들이다. 어느 것도 이 단계의 산출물을 막지 않지만, 담당 단계를
적어 둔다.

| 미결 | 왜 열려 있나 | 어디서 닫히나 |
|---|---|---|
| 마이그레이션을 컨테이너 기동 시 자동 적용할지, `scripts/migrate.sh` 를 사람이 부를지 | 인터뷰 질문에 들어가지 않았다. 5인 병렬에서 정하지 않으면 "내 DB 만 다름"이 주간 이벤트가 된다 `[developer §2.3]` | infrastructure-design(3.4) 또는 첫 Bolt |
| 전사 응답이 동기인지 `202` + 폴링인지 | 오래 걸릴 수 있는 호출이라 오류 처리 모양이 완전히 달라진다 `[developer §4.2]` | contract-design(2.8) |
| 삭제 전파의 최종 경계 정의 | 단일 백엔드 전환으로 원래 경계가 사라졌다 `[constraint:TC-14][raid:R3]`. F07 승격으로 중요도가 올라갔다 | domain-design(2.6) |
| 병렬 작업 갈래 수 | 작업 단위가 아직 나오지 않았다 | units-generation(2.7) |
| F07 과 화면 C5 의 Must 부분이 어느 Bolt 에 들어가는가 | 위 "범위 변경 기록" 표의 4번이 남긴 자리다. **2026-09-17 에 범위가 좁아졌다** — 등급과 만드는 시점은 1.4 재실행이 닫았고, 남은 것은 Bolt 경계뿐이다(아래 설명) | delivery-planning(2.9) |
| `live` STT·LLM 제공자 선택 | 외부 결정 `[raid:D2]`. 정해지는 시점에 상시 비밀값 스캐너를 붙일지도 함께 다시 본다 `[devsecops §9]` | live 구현 착수 시점 |
| 시연 리허설을 누구 장비에서 언제 하는가 | 일정 항목이라 관행이 아니다 | delivery-planning(2.9) |
| 접근성 자동 검사(axe)를 시연 전 1회 넣을지 | 품질 담당이 선택 항목으로 제안했으나 인터뷰 질문에 포함되지 않았다 `[quality §9(h)]`. 13–18세 대상 모바일 웹이므로, 결정한 적 없이 빠지는 것과 결정해서 빼는 것은 다르다 | nfr-requirements(3.2) 또는 사용자가 원하는 시점 |

**"F07 과 화면 C5 의 Must 부분" 항목의 갱신 (2026-09-17)** `[FU4]` — 이 항목은 **닫힌
것이 아니라 범위가 좁아졌다.** 무엇이 정해졌고 무엇이 남았는지를 구분해 적는다.

- **정해진 것 — 등급과 만드는 시점.** F07 은 **만드는 순서 3단계(Must 잔여)**, 직접
  녹음과 같은 자리다 `[scope §5][backlog §4]`(D-60). 근거는 F07 의 삭제 전파가 제약
  TC-14 와 위험 R3 의 계층 경계 문제 — 단일 백엔드 전환으로 사라진 데이터 소유 경계를
  계층 규칙으로 다시 세우는 문제 — 에 걸려 있고 `[constraint:TC-14][raid:R3]`, 그
  경계를 **domain-design(2.6)이 닫는다**는 것이다. 4단계까지 미루면 그때 이미 쌓여 있는
  코드 중 고쳐야 할 범위가 넓어진다 `[scope §5]`.
- **정해진 것 — 화면 C5 의 분할선.** C5 는 **삭제 부분만** Must 로 쪼개졌다(기록 삭제
  요청, 연결 항목 미리보기, 원음만 삭제) `[backlog §1 PU-08]`. **보호자 열람 권한 전환·원음
  보관 기간 설정·서비스 안내 다시 보기는 Should 에 남는다** `[scope §3.2]`(S3). 하위
  단계는 C5 를 한 번에 완성하는 화면으로 다루지 않는다.
- **아직 남은 것 — 구체적인 Bolt 경계와 순서.** 만드는 순서의 "3단계"는 Bolt 번호가
  아니다. PU-08 이 어느 Bolt 에 들어가는지, 3단계의 다른 항목(직접 녹음)과 같은 Bolt 인지
  나뉘는지, 그 Bolt 가 몇 번째인지는 **여전히 `delivery-planning`(2.9) 소관**이다
  `[backlog §4][backlog §5]`. 이 문서와 상위 문서는 그 결정에 쓸 재료만 남긴다.

**바꾸지 않은 것 — 관행 결정은 한 건도 바뀌지 않았다.** 이번 회차에 다시 판단한 관행이

- `discovered-rules.md` 의 규칙 **18건**(`## Mandated` 10건, `## Forbidden` 8건) — 항목,
  문구, 근거 태그 모두 동일하다. 확인 게이트가 승인할 승격 대상 집합이 바뀌지 않았다.
- `team-practices.md` 다섯 절의 관행 내용 — 추가된 것은 각 절 끝의 추적 한 줄뿐이고,
  `## Testing Posture` 의 `- **Methodology**:` / `- **Ordering**:` 두 줄은 손대지 않았다.
- 커버리지 수치 — `backend/app/service/` 라인 80% 하나, 저장소 전체 바닥 없음, 분기
  커버리지 바닥 없음 `[Q4]`.
- 도구 선택 — SQLAlchemy 2.0(동기), Alembic, uv, Ruff, mypy, pytest·Vitest·Playwright
  `[Q6][spec:02 §3]`.

**왜 네 파일을 모두 고쳤는가.** 이 단계의 승인 근거가 네 산출물 전부의 갱신을 요구한다.
같은 내용을 다시 저장해 형식만 맞출 수도 있었지만, 그렇게 하면 파일의 수정 시각만 움직이고
읽는 사람에게 남는 것이 없다. 대신 각 파일에 실제로 쓸모 있는 추적 정보를 하나씩 더하는
쪽을 택했다 — 하위 단계가 다섯 절의 관행을 각각 어느 결정으로 되짚을 수 있는지
(`team-practices.md`), 규칙으로 올리지 않은 항목 중 무엇을 언제 다시 판단해야 하는지
(`discovered-rules.md`), 이번 회차에 무엇이 바뀌고 무엇이 그대로인지(이 문서). 갱신 요구를
문서 품질을 올리는 자리로 쓴 판단이다.

이 절은 **추가**다. 위의 `### 되돌리기가 어떻게 끝났는가 (2026-09-17)`, `### 같은 부담
기록에 얹히는 것 — Must 비율 73% (2026-09-17)`, `## 인터뷰가 닫지 못하고 남은 미결 사항`
의 갱신은 모두 앞 회차에 이미 반영된 것이며 이번 회차가 다시 쓰지 않았다.
