## 스토리 계획 (초안)

- **스토리 형식** — "[페르소나]로서 나는 [행동]을 하고 싶다. 그래야 [가치]." 각 스토리는 `US{묶음}.{순번}` ID, 각 수용 기준은 Given/When/Then 형식의 `AC{묶음}.{순번}.{순번}` ID 를 가진다. INVEST 기준을 지키고, 스토리마다 행복 경로와 최소 1개의 오류·경계 경우를 둔다 `[practices]`
- **우선순위** — 스토리의 MoSCoW 등급은 대응하는 요구사항의 등급(`[req]` §3)을 그대로 따른다. 이 단계가 새로 매기지 않는다
- **수용 기준의 재료** — 요구사항의 "확인 기준" 열과 합성 대화 S1·S2·S3 의 기대 결과 `[spec:05]`

**이미 확정되어 다시 묻지 않는 것**

- 무엇을 만드는가와 등급 — `[req]` FR1~FR15 (D-21, D-41~D-46, D-59, D-60, D-62~D-69)
- 대상과 이해관계자 — 13–18세 주 사용자, 보호자는 열람만, 이해관계자는 제품을 쓰는 사람만 `[intent]` (D-13, D-18, D-23, D-25)
- 테스트 방침 — test-after, 기대 판정 픽스처, 수용 기준 추적 마커 `@pytest.mark.ac("AC1.3.2")` `[practices]` (D-57)
- 시나리오 변형 거리 — 시드 데이터는 같은 맥락(SAME_CONTEXT) 변형만 만들고 가까운 맥락(NEAR) 이상은 만들지 않는다 `[spec:06]` §1. 요구사항 검토 지적 R-02 는 이것으로 닫히므로 묻지 않는다
- UI 문구(A-11)와 시나리오 원형(A-12) 재작성 — 3.1·3.5 착수 전 `[req]` OQ3·OQ4

이 단계가 묻는 것은 **스토리를 어떻게 나누고 쓸지 3건**과, 요구사항 승인 때 이
단계로 넘어온 **미정 동작 2건**(열린 질문 OQ1, 검토 지적 R-01)이다.

## Q1. 화면이 없는 요구사항은 스토리로 어떻게 다룹니까?

요구사항 중 일부는 사용자가 화면에서 하는 일이 아닙니다 — Mock 모드에서 파일 이름으로
합성 대화를 연결하는 규칙(FR1.5), 고정 사용자와 데이터 모델(FR11), 그리고 성능·접근성·
보안 같은 비기능 요구사항(NFR1~NFR14)입니다 `[req]`. 한편 이해관계자는 제품을 쓰는
사람(주 사용자, 보호자)만으로 확정되어 있어(D-23) `[intent]`, 개발팀이나 시연 운영자를
페르소나로 세우면 그 결정과 부딪힐 수 있습니다.

- A. 스토리로 만들지 않는다 — 추적표에서 담당 하위 단계(nfr-requirements·domain-design 등)로 넘기거나, 관련 사용자 스토리의 수용 기준 안에 조건으로 녹인다
- B. "시연 운영자" 페르소나를 따로 세워 FR1.5·NFR10 같은 항목을 스토리로 쓴다 — 이해관계자 목록(D-23)은 바꾸지 않고 스토리 작성용으로만 둔다
- C. 사용자가 체감하는 비기능 요구사항(접근성 NFR2, 화면 상태 NFR9, 문구 NFR7)만 사용자 스토리의 수용 기준에 녹이고, 나머지는 A처럼 하위 단계로 넘긴다
- D. 기술 항목을 "시스템으로서…" 형식의 기술 스토리로 따로 쓴다
- X. Other (please specify)

[Answer]: B. "시연 운영자" 페르소나를 따로 세워 FR1.5·NFR10 같은 항목을 스토리로 쓴다 — 이해관계자 목록(D-23)은 바꾸지 않고 스토리 작성용으로만 둔다

## Q2. 스토리를 어떤 축으로 묶습니까?

스토리 묶음(`US{묶음}`)의 축이 곧 이후 작업 단위 분해(units-generation, 2.7)와 제작
순서(delivery-planning, 2.9)의 재료가 됩니다. 만드는 순서는 "얇은 종단 슬라이스 먼저"로
확정되어 있습니다(D-46) `[scope]`.

- A. 사용자 여정 순서로 — 가져오기 → 전사 확인·정정 → 리포트 → 목표 선택 → 모의 대화 → 기록 → 삭제, 그 뒤에 Should 묶음. 성공 기준 SM1 의 여섯 단계와 맞물린다
- B. 기능 ID 순서로 — F01~F07 과 요구사항 FR1~FR15 묶음을 그대로 따른다
- C. 화면 흐름 순서로 — A 흐름(A1~A5), B 흐름(B1~B5), C 흐름(C1~C5), 보호자 화면
- D. A 로 묶되 각 묶음 안에서 "최소 종단 슬라이스 스토리"와 "깊이 채우기 스토리"를 구분해 표시한다
- X. Other (please specify)

[Answer]: A. 사용자 여정 순서로 — 가져오기 → 전사 확인·정정 → 리포트 → 목표 선택 → 모의 대화 → 기록 → 삭제, 그 뒤에 Should 묶음. 성공 기준 SM1 의 여섯 단계와 맞물린다

## Q3. 스토리 하나의 크기를 어느 정도로 잡습니까?

요구사항은 기능 15묶음, 세부 64개입니다 `[req]`. 5인이 7주 동안 나눠 맡으므로
(OC-01~OC-03) 스토리 하나가 한 사람이 며칠 안에 끝낼 크기여야 나누기 좋습니다.

- A. 세부 요구사항 하나당 스토리 하나 — 약 60개, 스토리마다 수용 기준 2~3개
- B. 사용자 행동 하나당 스토리 하나 — 여러 세부 요구사항을 묶어 약 25~35개, 스토리마다 수용 기준 3~6개
- C. 화면 하나당 스토리 하나 — 약 17개, 스토리마다 수용 기준이 많아진다
- D. Must 는 B 크기, Should 는 화면 단위(C 크기)로 거칠게 둔다
- X. Other (please specify)

[Answer]: B. 사용자 행동 하나당 스토리 하나 — 여러 세부 요구사항을 묶어 약 25~35개, 스토리마다 수용 기준 3~6개

## Q4. Must 화면에서 아직 없는 Should 화면으로 가는 버튼은 어떻게 합니까?

요구사항을 쓰면서 발견해 이 단계로 넘긴 열린 질문 OQ1 입니다 `[req]`. 연습 결과
화면(B5, Must)의 "기록 보기"는 연습 기록 상세(C3)로, 나의 기록 화면(C1, Must)의 목록
항목은 목표 상세·연습 기록 상세·실제 대화 기록 상세(C2~C4)로 가도록 명세되어 있는데
`[spec:03]`, C2~C4 는 Should 입니다 `[scope]`. Must 만 만든 시점에 이 버튼을 누르면 갈
곳이 없습니다.

- A. Should 화면이 생기기 전까지 목적지를 Must 화면으로 바꾼다 — B5 "기록 보기"는 C1 로, C1 목록 항목은 누를 수 없는 요약으로 둔다
- B. Should 화면이 생기기 전까지 그 버튼·링크를 화면에 표시하지 않는다
- C. 버튼은 두되 누르면 "곧 볼 수 있어요" 안내를 띄운다
- D. C3·C4 를 읽기 전용 최소 형태로 Must 에 올린다 (화면 등급이 바뀐다 — 선택 시 영향 항목을 따로 확인)
- X. Other (please specify)

[Answer]: C. 버튼은 두되 누르면 "곧 볼 수 있어요" 안내를 띄운다

## Q5. 전사를 고쳐 다시 분석한 뒤, 이전 판정은 기록 추이에 셉니까?

요구사항 승인 때 제품 리드 검토가 짚은 지적 R-01 입니다(감수한 위험으로 기록됨, D-70)
`[log]`. 재분석은 이전 판정을 지우지 않고 새 판정을 추가하고(FR3.5), 이전 판정에는
"재검토 필요"만 표시됩니다(FR3.3) `[req]`. 그런데 기록 추이의 분모 규칙(FR8.3, "관찰
기회가 있고 보류 사유가 없는 판정")은 재검토 필요 판정을 어떻게 셀지 말하지 않아, 같은
장면이 두 번 셀 수 있습니다. 나의 기록 화면(C1)과 삭제 영향 항목의 수용 기준을 쓰려면
이 규칙이 필요합니다. 참고로 합성 데이터 명세의 누적 시나리오는 S3 재분석 결과가 추이에
더해지는 것을 전제합니다 `[spec:05]`.

- A. 재분석 전까지는 이전 판정을 그대로 세고, 재분석으로 새 판정이 생기면 이전 판정은 빼고 새 판정만 센다
- B. "재검토 필요"로 표시되는 순간 이전 판정을 추이에서 뺀다 — 재분석 전에는 그 장면 몫이 비어 있다
- C. 대화마다 가장 최근 분석 회차의 판정만 센다 — 재검토 표시와 관계없이 항상 최신 회차 기준
- D. 이전 판정과 새 판정을 모두 세되, 추이 카드에 "재분석된 대화 포함" 표시를 붙인다
- X. Other (please specify)

[Answer]: A. 재분석 전까지는 이전 판정을 그대로 세고, 재분석으로 새 판정이 생기면 이전 판정은 빼고 새 판정만 센다

- X. Other (please specify)

## Consolidated Summary Confirmation

**스토리 계획**

- 페르소나 3명 — 주 사용자(13–18세), 보호자(열람만, Should 기능), 시연 운영자(스토리 작성용. 이해관계자 목록 D-23 은 바뀌지 않음) [Q1]
- 묶음 — 사용자 여정 순서: 가져오기 → 전사 확인·정정 → 리포트 → 목표 선택 → 모의 대화 → 기록 → 삭제, 그 뒤 시연 운영, Should 묶음(상세 조회·계정·보호자·노트북 레이아웃) [Q2]
- 크기 — 사용자 행동 하나당 스토리 하나, 약 25~35개, 스토리마다 Given/When/Then 수용 기준 3~6개. 등급은 요구사항의 등급을 그대로 따른다 [Q3]

**화면이 없는 요구사항**

- 시연 운영자 스토리 — Mock 파일 이름 연결(FR1.5), 시드 고정 사용자(FR11.1), 분석 모드 기본값·기동 거부(NFR5), `docker compose up` 과 헬스체크(NFR10) 네 항목만 [FU1]
- 사용자 스토리 수용 기준에 녹이는 것 — 화면 폭(NFR1), 접근성(NFR2), 금지 표현(NFR7), 한국어(NFR8), 화면 상태 4종(NFR9) [FU1]
- 추적표에서 하위 단계로 넘기는 것 — NFR3·NFR4·NFR6·NFR11·NFR12·NFR13·NFR14, FR11.2 [FU1]

**미정 동작 2건 닫음**

- Must 화면에서 Should 화면으로 가는 버튼 — B5 "기록 보기", C1 목록 항목, 추천 근거 링크는 버튼을 두고, 누르면 "곧 볼 수 있어요" 안내를 띄운다. 화면 등급은 바뀌지 않는다 (요구사항 열린 질문 OQ1 닫힘) [Q4]
- 재분석 후 집계 — 재분석 전에는 재검토 필요로 표시된 이전 판정도 추이에 센다. 재분석으로 새 판정이 생기면 대체된 이전 판정은 빼고 새 판정만 센다. 이전 판정은 지우지 않는다 (요구사항 검토 지적 R-01 닫힘, FR8.3 보완) [Q5]
