## 근거

- **사용자 화면이 중심이다** — Must 화면 12개(A1~A5, A2-R, B1~B5, C1)와 C5 의 삭제 부분, Should 화면 C2~C4·C5 나머지·보호자 읽기 화면이 있다 `[req]` §7
- **페르소나가 여럿이다** — 주 사용자(13–18세), 보호자(열람만), 시연 운영자(스토리 작성용) `[log]` D-71
- **업무 규칙이 복잡하다** — 관찰 기회 판정, 보류 사유 5종, 분모 규칙, 독립/도움 후 분리, 시도 불변, 정정 전파, 삭제 전파 `[req]` FR4·FR7·FR8·FR10
- **수용 기준을 쓸 단계가 여기뿐이다** — Inception 지침이 Given/When/Then 수용 기준을 요구하는데 이 일을 맡을 단계가 없어 이 단계를 계획에 다시 넣었다 `[log]` D-51. 팀 관행은 수용 기준 ID 를 테스트 마커로 추적한다 `[practices]`
- **5인 병렬 작업의 재료다** — 스토리 묶음이 units-generation(2.7)과 delivery-planning(2.9)의 입력이 된다 `[log]` D-72

## 스토리가 값을 더한 곳

- 합성 대화 S1·S2·S3 의 기대 결과를 수용 기준으로 고정해 성공 기준 SM1 과 판정 단위 테스트를 이었다
- 요구사항에 확인 기준만 있고 흐름이 비어 있던 자리를 닫았다 — 재분석 후 집계(D-74), Should 화면으로 가는 버튼(D-73), 지난 대화 재열람과 삭제 화면 진입(D-75), PARTIAL 표시(D-76), SM1 의 S2·S3 연습 경로(D-77), 다음 코칭 추천 규칙(D-78)
- 명세끼리의 모순과 합성 데이터로 가려낼 수 없는 수용 기준을 찾아 구성 데이터 단위 기준과 열린 질문으로 옮겼다

## 몹 검토 반영 내역

디자이너·개발자·품질 엔지니어가 초안을 서로 보지 않고 검토했다. 사람의 판단이 필요한
반대 의견은 인터뷰 질문(Q6~Q10)으로 올렸고, 사실관계 오류·누락 보완·검증 수단 제안은
리드가 반영했다.
