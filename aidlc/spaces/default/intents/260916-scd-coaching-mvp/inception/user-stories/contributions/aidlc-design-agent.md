## Contribution

관점: 사용자 경험과 페르소나 충실도(P1 13–18세, 사회적 의사소통 어려움, 휴대폰 브라우저 375px).
확정된 결정(Q1~Q5, FU1, D-62~D-74)은 다시 열지 않는다. 아래는 그 결정을 수용 기준으로 옮기는
방식에서 드러난 빈자리이며, 중요도 순으로 적었다. 근거 표기는 초안과 같은 태그를 쓴다.

### 1. Must 안에서 지난 대화로 돌아가는 길과 C5 로 들어가는 길이 정의되어 있지 않다 (가장 중요)

화면 단위와 기능 단위 등급의 교차 검토 결과다. D-73 으로 C1 목록 항목은 "곧 볼 수 있어요"
안내만 띄우고, 지난 대화의 상세(C4)는 Should 다. 그런데 아래 Must 수용 기준은 **지난 대화를
다시 여는 것**을 전제한다.

| 수용 기준 | 전제하는 이동 | 초안에서 그 이동을 여는 Must 화면 |
|---|---|---|
| AC8.3.2 | 원음만 지운 대화의 A3·A4 를 다시 연다 | 없음 (C1 항목은 D-73 안내, C4 는 Should) |
| AC8.1.1, AC8.2.1 | C5 에서 삭제할 대화 **하나를 고른다** | C5 안의 대화 선택 방법이 없다 |
| US8 전체 | C5 에 들어간다 | 하단 탭 4개(홈 / 대화 돌아보기 / 연습 / 기록)에 C5 가 없고, 어느 Must 화면에서도 C5 로 가는 링크가 명세에 없다 `[spec:03]` §1·§2 |
| AC1.2.3 | 하단 탭 "대화 돌아보기"를 누른다 | 이 탭의 목적지가 명세와 초안 어디에도 없다 |

필수 기능인 삭제(F07, Must)를 켜는 유일한 경로가 정의되지 않은 채 남아 있다. 제안:

- **지식으로 닫을 수 있는 부분** — US1.2 에 탭 목적지 AC 하나를 추가한다: "Given 홈에서, When 하단
  탭 대화 돌아보기 / 연습 / 기록을 누르면, Then 각각 A2 / B1 / C1 이 열린다"(목적지는 3.1 이 확정하되
  AC 에 적어 추적되게 한다). US8.1 에 "Given C1(또는 홈), When 자료·삭제 설정 진입점을 누르면, Then
  C5 가 열리고 삭제할 수 있는 실제 대화 목록(날짜·요약 한 줄)이 보인다" AC 를 추가한다. 진입점의 위치는
  3.1 이 정한다.
- **사람의 판단이 필요한 부분** — AC8.3.2 처럼 **지난 대화의 A3·A4 를 다시 여는** 경로를 Must 에 둘지.
  두지 않으면 AC8.3.2 는 "원음 삭제 직후 C5 안에서 전사·리포트가 남아 있음을 표시한다"로 좁혀야
  하고, 사용자는 리포트를 벗어나면 그 리포트를 다시 볼 수 없다(C4 가 생길 때까지). 이는 D-73 을
  바꾸자는 것이 아니라 D-73 의 결과를 짚는 것이다. 산출물 열린 질문에 담당 단계와 함께 적고 승인
  게이트에서 짚기를 권한다.

### 2. S1 의 주제 유지·전환 PARTIAL 판정이 리포트 어디에도 나오지 않는다

S1 기대 판정에는 TOPIC_MAINTENANCE = PARTIAL(근거 u5, u6)이 있다 `[spec:05]`. 그런데 AC4.1.1 은 잘한
장면(응답 관련성)과 어려움 장면(명료화·수리)만 열거하고, FR5.2 의 세 섹션(잘한 / 어려움 / 보류)에도
PARTIAL 의 자리가 정의되어 있지 않다 `[req]` FR5.2, `[spec:03]` A4. 저장은 되는데 화면에서 사라지는
판정이 생기며, "모든 판정은 근거와 함께 보인다"는 원칙과 어긋난다. 또한 SM1 의 첫 E2E(S1) 경로에서
구현자마다 다른 섹션에 넣게 된다.

- PARTIAL 을 어느 섹션에, 어떤 관찰형 표현("일부 보였어요" 류)으로 보일지는 사용자 인식에 직접 닿는
  제품 판단이다. 초안의 열린 질문에 추가하고(담당: 승인 게이트에서 지금 정하거나 functional-design 3.1),
  정해지면 AC4.1.1 에 "주제 유지·전환(근거 u5·u6)이 <섹션>에 보인다"를 붙인다.

### 3. 화면 상태 4종(NFR9)의 수용 기준이 빠진 Must 화면

FU1 로 NFR9 는 사용자 스토리 AC 에 녹이기로 했고, NFR9 의 측정 기준은 "SM1 경로의 화면마다 비어 있음·
실패 상태 테스트"다. 초안이 덮은 곳과 빠진 곳:

| 화면 | 초안에 있는 상태 AC | 빠진 것 → 붙일 스토리 |
|---|---|---|
| A1 | 비어 있음 AC1.2.2 | 최근 기록 불러오기 실패 → US1.2 |
| A2 / A3 | 실패 AC2.1.3, AC3.1.4 | (충분) |
| A4 | 없음 | "이대로 분석하기" 후 **분석 중** 표시, 분석 실패 시 다시 시도 → US4.1 |
| A5 | 부족 AC5.1.3 | 추천 불러오기 실패 → US5.1 |
| B1 | 원형 대체 AC6.1.4 | 목록 불러오기 실패 → US6.1 |
| B3 | 없음 | 상대 응답 대기 표시, **전송 실패 시 입력한 글이 사라지지 않음** → US6.2 |
| B5 | 재시도 없음 AC6.5.4 | 결과 불러오기 실패 → US6.5 |
| C1 | 비어 있음 AC7.1.3 | 불러오기 실패 → US7.1 |
| C5 삭제 | 일부 완료 AC8.1.4 | 일부 완료일 때 사용자가 할 수 있는 다음 행동(남은 항목 다시 삭제 요청 등) → US8.1 |

B3 전송 실패는 특히 중요하다. 이 사용자에게 "쓴 말이 사라지는" 경험은 다시 시도하지 않게 만드는 가장
흔한 이탈 지점이다.

### 4. 되돌릴 수 없는 저장과 중복 입력 — 오류 예방 AC

시도는 수정할 수 없고(FR7.6), 재분석은 매번 새 판정을 추가한다(FR3.5). 그래서 **두 번 눌림**이 곧
데이터 오류가 된다.

- **US6.2** — "Given B3 에서 한글을 입력 중(조합 중)일 때, When Enter 를 누르면, Then 조합 중인 글자가
  전송되지 않고, 한 번의 전송은 시도 하나만 만든다." 한글 IME 조합 중 Enter 가 keydown 을 두 번 일으켜
  마지막 글자가 따로 전송되는 것은 React 입력창에서 잘 알려진 결함이며(`isComposing`), 휴대폰 한글
  키보드가 P1 의 기본 기기다 `[persona]`. AC6.2.4 의 "Enter 로 전송"만으로는 이것을 막지 못한다.
- **US6.2** — "Given 전송 버튼을 빠르게 두 번 눌렀을 때, Then 시도는 하나만 저장된다."
- **US3.3 / US4.1** — "Given 분석이 진행 중일 때, When '이대로 분석하기'를 다시 누르면, Then 두 번째
  분석 회차가 생기지 않는다(버튼은 진행 중 표시로 바뀐다)." 중복 회차가 생기면 D-74 의 "대체된 이전
  판정" 이 어느 것인지 모호해진다.

### 5. 접근성(NFR2) — 키보드·색·포커스 AC 보강

D-68 은 핵심 항목(이름표, 색만으로 전달 금지, 대비 4.5:1, 터치 44px, **키보드로 SM1 여섯 단계 끝까지**)
으로 범위를 정했다. 그 범위를 넘는 항목(200% 확대, 리플로 등)은 제안하지 않는다. 현재 키보드 AC 는
AC1.2.4(홈)와 AC6.2.4(B3) 두 곳뿐이라 "여섯 단계 끝까지"가 증명되지 않는다. 가장 위험한 자리만 고른다.

| 붙일 곳 | 제안 AC 요지 | 이유 |
|---|---|---|
| US2.1 | 녹음 알림 확인 체크, 파일 선택, "대화 내용 확인하기"를 Tab·Space·Enter 로 조작하고, 처리 상태 변화(업로드 중 → 전사 중 → 완료)가 화면 읽기 프로그램에 알려진다(`role="status"`) | 상태가 바뀌어도 알림이 없으면 키보드·화면 읽기 사용자는 완료를 모른다 |
| US2.2 | 마이크 버튼에 접근 가능한 이름과 현재 상태(녹음 중 / 일시정지)가 있다. 경과 시간은 매초 읽어 주지 않는다 | 아이콘만 있는 큰 버튼이 명세의 형태다 `[spec:03]` A2-R |
| US3.2 | 발화별 동작(텍스트 수정·화자 변경·분석에서 빼기)이 키보드로 열리고, 각 동작의 터치 영역이 44px 이상이다 | 발화 목록 안의 작은 동작 버튼이 44px 를 가장 먼저 깨는 자리다 |
| US3.1 | 불명확 구간은 색 강조와 함께 "잘 안 들린 부분" 글자가 있고 그 글자 대비가 4.5:1 이상이다 | 명세 색이 빨강/주황인데, 흰 바탕 주황 글자는 대개 4.5:1 에 못 미친다 |
| US4.3 | "근거 보기"는 스크롤·강조에 더해 **포커스를 첫 근거 발화로 옮기고**, 장면으로 돌아가는 방법이 있다 | 강조만 하면 키보드·화면 읽기 사용자는 어디로 갔는지 모른다 |
| US5.1 | 선택된 목표 카드는 보라 테두리 외에 "선택됨" 글자 또는 선택 상태 속성으로도 표시되고, 화살표·Space 로 고른다 | 명세의 선택 표시가 보라 테두리 하나다 `[spec:03]` A5 — 색만으로 의미 전달 |
| US6.2 | 상대(AI)의 새 발화가 화면 읽기 프로그램에 알려진다(`aria-live="polite"`) | 채팅은 비동기로 내용이 추가되는 화면이다 |
| US6.5 | "목표 행동이 나타난 발화" 강조가 색 외의 표시(글자 라벨·아이콘)를 가진다 | AC6.5.1 이 강조를 요구하지만 수단을 말하지 않는다 |
| US6.5 / US7.1 / US7.3 | "곧 볼 수 있어요" 안내는 화면 전환이 아니며, 포커스를 누른 버튼에 그대로 두고 안내가 화면 읽기 프로그램에 읽힌다 | D-73 동작을 키보드 경로에서 막다른 길로 만들지 않기 위함 |
| US8.1 | 삭제 확인은 포커스가 확인 영역 안에 머물고, Escape·취소로 닫히면 포커스가 삭제 버튼으로 돌아간다. 확인 버튼 이름은 "확인"이 아니라 무엇을 지우는지 말한다 | 되돌릴 수 없는 동작의 확인 패턴 |
| US7.2 | 추이는 색·화살표·그래프만이 아니라 글로도 읽힌다 | 색만으로 전달 금지 |

"여섯 단계 끝까지"의 증명은 E2E 수를 늘리지 않고(팀 관행: E2E 3건 유지), 위 화면별 컴포넌트 테스트의
합으로 본다는 문장을 `작성 규칙`의 공통 조건 옆에 한 줄 적기를 권한다.

### 6. 금지 표현(NFR7) — 문구 위험과 검사 방식

- **AC1.1.4 의 "부정 맥락 예외"는 기계로 검사할 수 없다.** NFR7 의 측정 기준은 예외 없이 "0건"이고,
  "진단이 아니에요"가 부정 맥락인지는 문자열 검사로 판별되지 않는다. 가정표에 적힌 해석은 그대로
  두더라도 **수단**을 바꾸기를 권한다: (a) 허용 문장 목록 파일에 서비스 안내의 정확한 문장만 등록하고
  검사는 그 문장만 건너뛴다, 또는 (b) FR9.2 의 확인 기준은 "네 **내용**이 모두 있다"이지 단어를
  요구하지 않으므로 금지 단어 없이 쓴다(예: "이 결과는 병원 검사 결과가 아니에요"). 어느 쪽이든
  NFR7 과 FR9.2 가 모순으로 읽히지 않게 구분선을 가정표에 함께 적는다. 문장 자체는 A-11(3.1)이 쓴다.
- **실패 상태 문구가 가장 흔한 위반 자리다.** NFR9 는 "실패" 상태를 요구하고 NFR7 은 "실패했어요"를
  금지한다. AC2.1.3·AC3.1.4 에 "실패 안내 문구에 '실패했어요'가 없다(예: '전사를 끝내지 못했어요')"를
  붙인다. 구현자가 가장 자연스럽게 쓰는 문장이 금지 표현이다.
- **Mock 이 만든 문구의 검사 범위.** NFR7 은 Mock·LLM 문구까지 포함하지만, 초안에서 문구 검사 AC 는
  A1 안내(AC1.1.4)와 리포트(AC4.1.5)뿐이다. B3 상대 발화, B4 힌트, B5 결과 문장, A5·C1 추천 이유도
  Mock 픽스처에서 나온다 `[spec:06]` §3. 스토리마다 흩어 붙이기보다 "UI 문구 파일 전체와 Mock 픽스처
  전체를 금지 표현 목록으로 검사해 0건" 하나를 한 스토리(예: US4.1 또는 US9.2)에 두고, `작성 규칙`의
  공통 조건이 그 AC ID 를 가리키게 하기를 권한다.
- **enum 원문과 판단형 라벨.** "NOT_OBSERVED_THIS_TIME", "INVALID_EVIDENCE" 같은 값은 화면에 그대로
  나가지 않고 관찰형 한국어 라벨로 보인다는 AC 를 US4.1·US6.5 에 붙인다. 특히 AC4.1.3 의
  INVALID_EVIDENCE 는 보류 섹션에 보인다고만 되어 있고, 명세의 보류 사유 표시 3종(기회 없음 / 맥락 부족 /
  전사 불명확)에 해당 라벨이 없다 `[spec:03]` A4. 사용자가 자기 잘못으로 읽지 않는 라벨이 필요하다는
  조건만 AC 에 두고 문장은 A-11 로 넘긴다.
- "유효 기회", "분모" 같은 내부 용어가 C1 화면에 나오지 않는다는 조건을 AC7.2.1 에 덧붙인다.

### 7. 페르소나 충실도 — P1 이 실제로 이렇게 쓴다면

- **A2-R 녹음 전 알림 확인이 빠졌다(US2.2).** AC2.1.1 은 파일 업로드에만 확인 체크를 건다. 명세는 확인
  체크를 두 방법(파일 / 새로 녹음)을 모두 담은 A2 화면에 둔다 `[spec:03]` A2. 녹음은 상대의 목소리를
  **지금** 담는 행동이라 확인이 더 필요한 쪽이다. "Given 알림 확인에 체크하지 않았을 때, When 새로
  녹음하기를 누르면, Then 녹음이 시작되지 않고 확인 안내가 보인다"를 US2.2 에 추가한다.
- **AC2.2.2 의 자동 진행.** FR1.2 는 "최대 길이에 도달하면 녹음이 멈춘다"까지만 요구하는데, AC2.2.2 는
  "업로드 단계로 넘어간다"를 더했다. 말하는 도중 예고 없이 끊기고 화면이 스스로 넘어가는 것은 예측
  가능성을 크게 해친다. 제안: "종료 30초 전 남은 시간 안내가 보이고, 5분에 멈추면 '5분이 되어 녹음을
  멈췄어요'와 함께 올리기 / 다시 녹음을 사용자가 고른다." 자동 업로드를 유지하려면 그 근거를 적는다.
- **빈 입력 Enter 가 일시정지가 된다(US6.4).** FR7.7 대로 빈 입력은 PAUSED 다. 그러나 AC6.2.4 의 "Enter 로
  전송"과 합치면, 키보드 사용자가 실수로 누른 Enter 한 번에 세션이 멈춘다. 결정을 바꾸지 않고 표현을
  보강한다: AC6.4.2 에 "일시정지되면 '잠깐 멈췄어요' 상태와 '이어서 하기' 버튼이 보이고 포커스가 그
  버튼으로 가며, 이어서 하면 입력하던 자리로 돌아간다"를 붙인다. AC6.4.1 의 토글 버튼은 상태에 따라
  이름이 바뀐다("잠깐 멈추기" ↔ "이어서 하기").
- **"그만"·"몰라"는 완전 일치로 판별한다(AC6.4.2, AC6.4.3).** 역할극 안에서 "그만 물어봐", "몰라서
  그랬어" 같은 문장은 자연스러운 답이다. 부분 일치로 판별하면 사용자의 진짜 답이 일시정지나 힌트 제안으로
  삼켜진다. 앞뒤 공백을 뺀 완전 일치라는 조건을 AC 에 명시한다(Mock 규칙 `[spec:06]` §3 도 같은 취지로
  읽힌다).
- **첫 시도 전에 힌트를 누르는 경우(US6.3).** B3 에는 첫 응답 전부터 "힌트 받기"가 보이고, "몰라"는 힌트를
  제안한다. 이때 첫 시도는 FR7.5 에 따라 HINTED 가 되고 독립 시도는 없다. 이 경우를 AC 로 고정하기를
  권한다: "Given 첫 시도 전에 힌트를 받았을 때, When 답을 보내면, Then 시도는 HINTED 로 저장되고 B5 의
  '처음 시도' 칸은 비어 있음 상태로 보인다(실패 표현 없음)." 기존 규칙에서 도출되므로 새 결정이 아니다.
- **리포트가 전부 보류인 화면(S3).** FR5.1 의 확인 기준 "S3 에서 분석할 수 있었던 범위가 좁게 표시된다"를
  검증하는 AC 가 없다(US4.1 이 FR5.1 을 참조만 한다). AC4.2.2 옆에 "Given S3, When A4 상단을 보면, Then
  분석할 수 있었던 범위가 좁다는 것이 글로 보인다"를 추가한다. 노랑 박스 세 개만 있는 화면은 이 사용자에게
  "아무것도 못 했다"로 읽힐 위험이 가장 크므로, 전사를 고칠 수 있는 곳(A3)으로의 안내 문구 여부를 3.1
  열린 질문에 함께 넘기기를 권한다.
- **분석에서 빼기의 되돌리기(US3.2).** 원칙 7(사용자가 통제한다)에 비추어 "뺀 발화는 흐리게 처리만이
  아니라 '분석에서 뺐어요' 글자로 표시되고, '다시 넣기'로 되돌릴 수 있다" AC 를 권한다. 되돌리기를 Must 에
  둘지가 요구사항에 명시되어 있지 않으므로, 리드가 FR3.1 의 범위로 읽을 수 없다고 판단하면 열린 질문으로
  넘긴다.
- **AC1.1.2 "눌러도 이동하지 않는다".** 반응 없는 버튼은 이 사용자에게 고장으로 읽힌다. 동의 전에는 하단
  탭을 보이지 않게 하거나, 누르면 "안내를 읽고 동의하면 쓸 수 있어요"가 보이게 한다. 주소를 직접 입력해
  다른 화면으로 가도 안내로 돌아온다는 조건을 함께 둔다(FR9.2 "다른 화면으로 갈 수 없다").

### 8. 시드 사용자의 동의 상태가 두 AC 사이에서 정해져 있지 않다

AC9.2.1 은 "로그인 없이 고정 사용자로 모든 Must 화면을 쓸 수 있다", AC1.1.3 은 "동의를 마친 사용자는 안내
없이 홈으로"다. 시드 사용자가 **동의 전** 상태로 적재되는지, 동의가 서버(사용자)에 저장되는지 브라우저에
저장되는지에 따라 시연 리허설과 E2E 첫 단계가 달라진다(동의 완료로 시드하면 AC1.1.1 은 시연에서 보이지
않고, 브라우저 저장이면 새 clone 과 새 브라우저마다 다르게 동작한다). AC9.2.1 에 "시드 사용자는 동의 전
상태로 시작하고, E2E 는 동의부터 진행한다"처럼 한 문장을 붙이기를 권한다(리드가 정할 수 있는 수준).

### 9. personas.md P1 보강 제안

`주의할 점`에 한 줄 추가를 권한다(작업 가정으로 표시): "명시되지 않은 뜻을 추론하거나 비유·중의적 표현을
이해하는 데 어려움이 있을 수 있다 — 문구는 글자 그대로 읽혀도 뜻이 같아야 하고, 화면이 사용자의 동작 없이
바뀌지 않게 한다." 이는 SCD 의 일반적 특성(DSM-5 SCD 기준 A4: 명시되지 않은 것의 추론, 관용 표현·비유·
중의적 의미 이해의 어려움)에서 온 설계 전제이며, 위 7절의 자동 진행·반응 없는 버튼·모호한 안내 지적의
근거가 된다. D-73 의 "곧 볼 수 있어요"는 결정 그대로 두되, "곧"이 언제인지 글자 그대로 기대하게 만들 수
있다는 점을 A-11 문구 재작성(3.1) 메모로만 넘긴다.
