### 1. 의존 표기가 걷는 뼈대(첫 Bolt)를 막는다

팀 관행은 첫 Bolt 를 "실제 첫 기능(PU-01 업로드)으로 종단 관통"으로 정했다. 그런데 초안의
의존을 따르면 US2.1 앞에 US1.2 → US1.1 이 서고, 정작 업로드가 뭔가를 돌려주는 데 필요한
것(환경·시드 사용자·Mock 파일 이름 연결)은 US2.1 의 의존에 없다.

- **US2.1 의 의존을 "US9.1, AC9.2.1·AC9.2.3"으로 바꾸고 US1.2 는 뺀다.** 홈에서 A2 로 들어가는
  진입은 화면 이동일 뿐 기술 의존이 아니다. US1.2 쪽에 "A2 로 이동(US2.1 이 있으면)"을 두면 된다.
- **US9.2 는 처음과 끝에 동시에 걸려 있다.** AC9.2.1(시드 사용자)·AC9.2.2·AC9.2.3(Mock 파일
  이름 연결)은 뼈대의 전제인데, AC9.2.4(합성 대화 3건 SM1 종단)는 US2~US7 이 전부 끝나야 통과한다.
  그래서 "의존: US9.1, US2.1"이 사실과 다르고, 이 스토리는 마지막 Bolt 까지 닫히지 않는다.
  제안: AC9.2.4 를 새 스토리 **US9.3 "SM1 종단 리허설"**(의존: US7.2, US6.5)로 옮긴다. 담당
  요구사항은 여전히 FR11.1·NFR10 안이므로 D-71 의 "네 항목만" 범위는 바뀌지 않는다.
- 제안하는 핵심 경로(Bolt 순서는 delivery-planning(2.9)이 정하고, 이 표는 의존만 보인다):

| 순서 | 스토리 / 수용 기준 | 이유 |
|---|---|---|
| 0 뼈대 | US9.1, AC9.2.1, AC9.2.3, US2.1 행복 경로(AC2.1.2) | 팀 관행 Walking Skeleton 의 관통 경로 그대로 |
| 1 | US3.1 → US4.1 의 분석 파이프라인(AC4.1.2~AC4.1.4) | US3.3·US4.2·US5.1·US7.2 가 전부 이 위에 선다 |
| 2 | US5.1 → US6.1 → US6.2 → US6.3 → US6.5 | SM1 의 목표·연습 단계 |
| 3 | US7.1 → US7.2, US9.3 | SM1 종단 완성 |
| 넓히기 | US1.1·US1.2, US2.2, US2.3, US3.2·US3.3, US4.2~US4.4, US6.4, US7.3, US8.x | 핵심 경로가 선 뒤 병렬 |

### 2. Mock 경로에서 적힌 그대로는 구현·재현할 수 없는 수용 기준

Mock LLM 은 `conversationKey` 하나에 기대 판정 한 벌을 돌려준다([spec:05]). 전사를 읽지 않으므로
아래 AC 는 추가 규칙 없이는 통과시킬 방법이 없거나, 어떤 구현이 와도 통과한다.

- **AC3.3.3** — S3 를 고친 뒤 재분석하면 응답 관련성이 OBSERVED 여야 하는데, 같은 키에는 같은
  결과만 나온다. 픽스처에 **"정정 후 S3" 판정 한 벌**(세 판정 전부)과 **선택 조건**(예: u2 가
  수정됨 또는 전사 버전 > 1)을 두어야 한다. [spec:05] 는 정정 후 응답 관련성만 적었으므로 나머지
  두 판정 값도 픽스처에서 정해야 한다. AC3.3.3 에 "정정 후 S3 픽스처의 기대 판정으로"를 적는다.
- **AC3.2.2** — 뺀 발화가 근거에 들어가지 않아야 하는데 Mock 픽스처는 근거 ID 를 고정으로 돌려준다.
  새 규칙을 만들 필요는 없다: 서비스가 제공자 응답에서 **제외된 발화 ID 를 근거에서 걷어내고**,
  근거가 비면 기존 규칙 3(근거 없음 → INVALID_EVIDENCE)이 적용된다고 AC 에 적으면 구현 가능해진다.
- **AC4.2.3** — Mock 은 u3 를 읽지 않으므로 이 AC 는 구현과 무관하게 항상 초록이다(팀 관행이
  금지한 "항상 통과하는 테스트"). 팀 관행대로 **프롬프트 빌더 단위 테스트 2건**이 이 속성을
  강제한다고 AC 에 검증 수단을 적거나, Given 을 "프롬프트 빌더가 S3 전사를 렌더링할 때"로 바꾼다.
- **AC2.1.3, AC3.1.4, AC8.1.4** — Mock 에는 전사 실패·삭제 일부 실패를 일으키는 수단이 없다.
  새 Mock 키를 만들면 FR1.5 에 없는 요구사항이 되므로, Given 을 **"STT 제공자(또는 파일 저장소)가
  오류를 내는 테스트 대역을 주입했을 때"**로 적고 검증 수준을 통합·컴포넌트 테스트로 명시한다.
  E2E 3건에 넣지 않는다.
- **AC2.1.2** — "업로드 중 → 전사 중 → 완료"가 화면에서 보이려면 전사가 요청 밖에서 돌고 화면이
  상태를 조회해야 한다(FastAPI BackgroundTasks + TanStack Query `refetchInterval` 등). 동기 처리로
  구현하면 "전사 중"은 관찰할 수 없다. AC 를 "대화의 상태 값이 `UPLOADING / TRANSCRIBING / READY`
  를 거치고 화면이 그 값을 표시한다"로 적으면 방식은 functional-design(3.1)에 남기면서도 검증 가능하다.

### 3. 모순: 근거 필수 규칙과 "기회 없음" 판정

FR4.4 와 [spec:04] 규칙 3 은 "근거가 **없거나** 존재하지 않는 발화 ID 면 INVALID_EVIDENCE"다.
그런데 S2 의 명료화·수리는 opportunity=ABSENT / NO_OPPORTUNITY 이고, 기회가 없으니 근거 발화가
있을 수 없다. 규칙을 글자대로 구현하면 **AC4.2.1 의 "보류(기회 없음)"가 INVALID_EVIDENCE 로 바뀌어**
AC4.1.2 도 함께 깨진다. 또 [spec:05] 는 S2 판정의 근거를 괄호 메모로만, S3 판정의 근거는 아예
적지 않아 AC4.1.2 의 "근거가 모두 일치"를 대조할 값이 없다.

- AC4.1.3 의 Given 을 **"관찰 기회가 PRESENT 또는 UNCERTAIN 인 판정에"**로 좁혀, ABSENT 판정은
  근거 필수 규칙의 예외임을 적는다. S2 기대 결과가 확정 명세이므로 이것이 두 규칙을 함께 만족하는
  유일한 해석이다.
- "S2·S3 판정의 근거 발화 ID 는 픽스처 파일에서 채우고 그 파일이 기준"이라는 한 줄과, 이 해석의
  최종 확인 담당(domain-design(2.6))을 `## Assumptions & Open Questions` 에 넣는다.

### 4. 데이터 모델에 숨은 의존 — 여러 스토리가 같은 구조를 기다린다

- **재분석 대체 관계**(D-74): AC3.3.3(만듦), AC7.2.4(셈), AC8.1.3(지울 때 셈) 세 곳이 "어느 판정이
  어느 판정으로 대체되었는가"를 필요로 하는데 [spec:04] 에는 그 필드도 분석 회차 개념도 없다.
  `superseded_by` 같은 연결이나 분석 회차가 필요하다. **US3.3 이 그 구조를 만든다고 적고**
  US7.2·US8.1 의 의존에 US3.3 을 명시한다(US7.2 는 이미 있음, US8.1 도 있음 — AC 단위로 AC8.1.3 만
  US3.3 에 걸린다고 적으면 US8.1 나머지는 일찍 시작할 수 있다). 재분석은 **대화 단위로 세 판정을
  새로 만들고 이전 세 판정을 모두 대체됨으로 둔다**는 뜻인지 AC3.3.3 에 적어야 AC7.2.4 의 "S3
  재분석 1"과 AC8.1.3 의 "판정 3 + 재분석분"이 같은 수를 가리킨다.
- **삭제 후 "유지"**(US8.2): 팀 관행은 FK 에 `ON DELETE CASCADE` 를 건다. TrainingGoal 이
  `sourceEventId`·`sourceJudgmentId` 로 대화의 사회적 사건·판정을 가리키므로, 그대로 두면 대화를
  지우는 순간 목표가 연쇄 삭제되어 **AC8.2.2 "유지"가 구현 불가능**하다. 이 두 FK 는 `SET NULL` 이어야
  하고, 연습 시도의 판정(Attempt.judgmentId → BehaviorJudgment.socialEventId)이 어느 사건에 매달리는지도
  같은 문제다. 최종 경계는 domain-design(2.6)이 닫지만, AC8.2.2 에 **"유지된 목표는 원본 장면이
  삭제되었다는 표시와 함께 남고 B1 강조 카드가 깨지지 않는다"**를 적어야 삭제 뒤 화면 동작이
  정의된다.
- **첫 방문 동의 저장 위치**(US1.1): User 엔티티에 동의 필드가 없다. 브라우저 저장소에 두면
  Playwright 의 새 컨텍스트마다 안내가 뜨고, 서버에 두면 시드 초기화와 함께 다뤄야 한다. AC1.1.3 에
  "동의는 사용자 단위로 서버에 저장된다"처럼 위치를 적고, FR11.2(스키마를 나중에 바꾸지 않음)를
  고려해 domain-design 입력으로 넘긴다. AC1.1.2 에는 "주소를 직접 입력해도"를 더해 경로 가드를 요구한다.

### 5. 크기와 5인 분담

- 대부분의 스토리는 1인 2~4일 크기로 적절하다. 예외는 **US4.1**(요구사항 10개)이다. INVEST 메모대로
  AC 단위로 나누되, AC4.1.2~AC4.1.4(분석 파이프라인: Mock 호출, 근거 검증, 사회적 사건·판정·버전
  저장)는 **핵심 경로의 병목**이므로 AC4.1.1·AC4.1.5(A4 화면)와 담당을 나눌 수 있게 표시해 두면
  units-generation(2.7)이 그대로 쓸 수 있다.
- **AC4.1.5 는 네 검사가 한 AC 에 묶여 있다**(응답 스키마에 점수 없음 / 금지 표현 / 색+글자 /
  대비 4.5:1). 앞의 것은 backend 스키마 테스트, 뒤 셋은 frontend 검사라 담당이 갈린다. 두 AC 로 나눈다.
- **같은 화면을 여러 스토리가 만진다**: A3(US3.1~US3.3), A4(US4.1~US4.4), C1(US7.1~US7.3). 묶음 안은
  한 사람이 순서대로, 묶음 사이를 병렬로 나누는 것이 충돌이 가장 적다. 묶음 경계가 이미 백엔드 패키지
  이름(`conversation` / `assessment` / `training` / `record` / `privacy`)과 거의 맞으므로, 스토리 지도에
  "주 패키지" 열을 하나 두면 분담이 기계적이 된다(US1·US9 → 공통·플랫폼, US2·US3 → conversation,
  US4·US5.1 → assessment, US5.2·US6 → training, US7 → record, US8 → privacy).
- **US6 을 US4·US5 완료와 떼어 내는 방법**: `scripts/seed.py` 가 "S1 분석 완료 + 목표 선택됨" 상태를
  넣을 수 있으면 모의 대화 담당이 첫 주부터 병렬로 간다. 이를 위해 US6.1 에 **목표 없이 B1 에 들어온
  경우**의 AC(일반 연습 목록만 보임)를 하나 두면, 홈의 "모의 대화 연습하기" 진입(FR9.1)도 함께 덮인다.
- **US5.2 의 앞쪽 의존(US6.5)**: 목표 ID·원본 사건 ID 전달은 연습 세션을 만드는 순간(US6.1)에 구현된다.
  AC5.2.1·AC5.2.3 은 US6.1 에서, AC5.2.2 는 US6.5 에서 만들어지므로, US5.2 를 "연결 확인" 스토리로
  남기되 의존을 US6.1 로 적고 AC5.2.2 를 US6.5 로 옮기면 묶음 5 가 묶음 6 을 기다리지 않는다.

### 6. 검증 수단이 도구와 맞지 않는 수용 기준

Vitest + React Testing Library 는 jsdom 에서 돌고, jsdom 에는 레이아웃 엔진이 없다. 크기·겹침·가로
스크롤·대비는 계산되지 않는다(axe 의 대비 규칙도 jsdom 에서는 동작하지 않는다).

- **AC13.1.1**("잘리거나 겹치지 않는다, 컴포넌트 테스트"), **AC1.2.3**(가로 스크롤 0, 터치 영역 44px),
  **AC4.1.5 의 대비** 는 jsdom 컴포넌트 테스트로는 검증할 수 없다. D-62 가 정한 "컴포넌트 테스트"를
  지키려면 실제 브라우저에서 도는 컴포넌트 테스트(Vitest browser mode + Playwright provider)가 필요하고,
  모바일 폭 항목은 E2E 3건 안에서 페이지마다 axe 검사를 돌리면 E2E 수를 늘리지 않고 확인된다. 어느 쪽인지
  AC 에 검증 수준을 적는다. 도구 선택은 functional-design(3.1)·nfr-design 에서 닫아도 된다.
- **AC1.1.4·NFR7 금지 표현 검사**: JSX 에 흩어진 문구는 기계적으로 검사하기 어렵다. UI 문구를 한 파일
  (메시지 모음)에 모으고, 부정 맥락 예외("진단이 아니에요")는 **명시적 허용 목록**으로 두어 테스트가
  두 파일을 읽게 하면 AC 가 결정적으로 판정된다. 작성 규칙의 "공통 조건" 줄에 붙일 수 있다.
- **기대값이 AC 에 직접 적힌 자리**(AC3.2.1 "우산 가져왔어", AC6.2.1 "걔", AC6.3.2 "내 짝꿍 지우야",
  AC7.2.4 "= 3"): 팀 관행은 기대값을 테스트 코드에 직접 적지 않고 픽스처를 읽게 한다. 게다가 OQ4(A-12)
  재작성으로 이 문구가 바뀐다. 작성 규칙에 **"AC 에 인용한 합성 데이터 값은 픽스처 파일이 기준이고
  테스트는 픽스처를 읽는다"** 한 줄을 두면 재작성 뒤에도 AC ID 가 유지된다.
- 참고(스토리 밖, 3.1 입력): 팀 관행의 PM-01 경계 테스트(4:59 / 5:01)는 서버가 업로드 파일 길이를 알아야
  하는데, MediaRecorder 가 만든 webm 은 헤더에 길이가 비어 있는 경우가 흔하다. 서버에서 재려면 ffprobe 같은
  의존이 backend 컨테이너에 추가된다. 지금 AC 는 녹음 쪽(AC2.2.2)만 요구하므로 스토리는 그대로 두고, 길이
  측정 방식은 functional-design(3.1)에서 정하도록 열린 질문에 적어 두기를 권한다.

### 7. 규칙이 정해지지 않아 결정적으로 구현할 수 없는 AC

- **AC7.3.1 다음 코칭 추천**: FR8.5 는 "반복 어려움, 도움 후 성공 조건, 선택 이력을 반영"만 말하고,
  "반복"이 몇 번인지, 합성 데이터(S1~S3 + S1 연습)에서 **어떤 추천이 나와야 하는지**가 어디에도 없다.
  기대 출력이 없으면 테스트는 "무언가 나온다" 수준이 된다. 요약 확인 뒤에 드러난 빈자리이므로 질문 파일을
  다시 열지 말고, 열린 질문에 담당 단계(functional-design(3.1))와 함께 적고 승인 게이트에서 지금 정할지를
  짚어 달라. 정해질 때 기대 추천은 픽스처에 넣는다.
- **A5 추천이 0개인 경우**: S2 는 어려움 장면이 없어 [spec:05] 에 추천 목표가 없다. US5.1 에 추천 0개일
  때의 AC(비어 있음 상태, NFR9 — 다른 목표를 직접 고를 수 있음)가 없고, 그러면 AC9.2.4 의 "3건 모두
  기록까지 끊김 없이"에서 S2 가 목표 선택 단계를 어떻게 지나는지도 정의되지 않는다. US5.1 에 AC 하나를
  더하고, SM1 종단 스크립트가 대화마다 고르는 선택(예: S2 는 직접 목표 선택)을 픽스처에 적어 둔다. "다른
  목표로 바꾸기"의 후보 목록 출처(시나리오 원형 6개의 연습 목표로 보인다)도 AC5.1.2 에 적는다.

### 8. 작은 보완

- US4.3 의존에 **US5.1** 추가(AC4.3.3 이 A5 선택 상태를 요구).
- US8.1 의존에 **US5.1, US6.1** 추가(AC8.1.1 미리보기가 연결된 연습·추천을 보여야 함).
- AC7.2.1 에 "**실제 대화의** 독립 수행"을 명시. 연습의 첫 시도(ROLEPLAY·INDEPENDENT)를 같이 세면
  유효 기회가 2 가 되어 [spec:05] 누적 시나리오와 어긋난다.
- AC6.4.2 "빈 입력을 보내면": 프론트에서 빈 입력 전송을 막으면 이 AC 는 서버에 도달하지 않는다. 빈 입력
  전송이 허용되어야 한다는 점을 적거나 검증을 API 수준으로 명시한다.
- AC7.3.5(버전 이력 조회)는 "다음 코칭 추천" 가치와 무관하다. FR8.6 추적을 AC4.1.4 옆(판정)과 US6.3
  (시도 판정)으로 옮기면 US7.3 이 추천 하나에 집중한다.
- D-73 의 "곧 볼 수 있어요" 세 자리(AC6.5.3, AC7.1.4, AC7.3.4)는 공통 컴포넌트 하나로 구현된다. 구현
  비용이 작고, Should 화면이 생길 때 바꿀 자리가 한 곳이다.

## Positions

- AGREE: 사용자 여정 순서 묶음과 행동 단위 크기(D-72) — US4.1 을 빼면 스토리가 1인 2~4일 크기이고, 묶음 경계가 백엔드 패키지 5개와 거의 겹쳐 분담에 유리하다.
- AGREE: D-73 "곧 볼 수 있어요" 표현(AC6.5.3·AC7.1.4·AC7.3.4) — 공통 컴포넌트 하나로 구현되고 Should 화면 도입 시 바꿀 자리가 하나다.
- AGREE: US9.1 의 AC — 팀 관행의 fail-closed 규칙(미설정·빈 값·모르는 값 → mock, 키 없는 live → 기동 거부)과 정확히 대응해 그대로 단위 테스트가 된다.
- AGREE: AC4.1.2 를 픽스처 기반 단위 테스트로 분리한 것 — 판정 파이프라인과 화면 담당을 나누는 경계로 그대로 쓸 수 있다.
- OBJECT: US9.2 가 뼈대의 전제(AC9.2.1·AC9.2.3)와 전체 완료 뒤에만 통과하는 SM1 종단(AC9.2.4)을 한 스토리에 묶어 의존이 순환한다. AC9.2.4 를 US9.3 으로 분리하고 US2.1 의 의존을 US9.1·AC9.2.1·AC9.2.3 으로 바꿔야 한다. — 지식 문제(전문가가 정리 가능, 확정 범위 D-71 은 바뀌지 않음).
- OBJECT: AC3.3.3·AC3.2.2·AC4.2.3·AC2.1.3·AC3.1.4·AC8.1.4 는 Mock 경로에서 적힌 그대로는 재현 수단이 없거나 항상 통과한다(정정 후 S3 픽스처와 선택 조건, 제외 발화의 근거 제거, 프롬프트 빌더 테스트, 오류 테스트 대역을 AC 에 적어야 함). — 지식 문제.
- OBJECT: FR4.4 의 근거 필수 규칙을 글자대로 구현하면 S2 의 NO_OPPORTUNITY(AC4.2.1)가 INVALID_EVIDENCE 가 되고, S2·S3 근거 값이 없어 AC4.1.2 를 대조할 수 없다. AC4.1.3 을 PRESENT·UNCERTAIN 판정으로 좁히고 근거 값은 픽스처가 기준이라고 적어야 한다. — 지식 문제(확정 기대 결과와 일관된 해석이 하나뿐), 최종 확인은 domain-design(2.6).

- OBJECT: AC13.1.1·AC1.2.3·AC4.1.5(대비)는 jsdom 기반 컴포넌트 테스트로 검증할 수 없다. 실제 브라우저 컴포넌트 테스트나 E2E 3건 안의 axe 검사로 검증 수준을 적어야 한다(E2E 수는 늘리지 않음). — 지식 문제.
