### 3. E2E 3건 상한을 지키기 위한 검증 층 표기

현재 AC 다수가 S1·S2·S3 화면 흐름으로 쓰여 E2E 처럼 읽힌다. 팀 관행은 E2E 를 3건에서 늘리지
않는다. **AC 마다 검증 층 태그를 붙일 것을 제안한다** — `[unit]` `[integration]`(Testcontainers)
`[component]`(Vitest+RTL+MSW) `[e2e:S1|S2|S3]`(기존 3건 안의 단언) `[rehearsal]`(수동 리허설).
build-and-test(3.6)가 AC 마커와 층을 기계적으로 대조할 수 있게 된다.

- **아래로 내릴 것**: AC3.3.1~AC3.3.3·AC8.1.1~AC8.1.4·AC8.2.x → `[integration]`(DB·디스크 상태), 화면 표시는 `[component]`. AC7.2.x → `[unit]`(집계). AC6.2.1·AC6.3.x → `[unit]`(Mock 규칙) + `[integration]`(시도 불변). AC8.1.4 는 "파일 삭제 실패를 주입한" 통합 테스트로 조건을 적는다.
- **jsdom 에서 측정 불가 — 층을 명시해야 항상 통과를 피한다**: AC1.2.3(가로 스크롤·44px), AC4.1.5 의 대비 4.5:1, AC13.1.1(잘림·겹침). jsdom 은 레이아웃과 색을 계산하지 않는다. 방법 두 가지 중 하나를 적는다 — (a) 기존 E2E 3건 안의 단언으로 넣기(건수 증가 없음), (b) 실제 브라우저 엔진에서 도는 컴포넌트 테스트. D-62 의 "컴포넌트 테스트"를 뒤집는 것이 아니라 그것이 실제로 측정하게 만드는 조건이다. 대비는 색 토큰 쌍의 대비를 계산하는 `[unit]` 도 가능하다.
- **`[rehearsal]` 로 표시할 것**: AC9.1.1, AC9.1.4, AC13.1.3 — CI 자동 테스트가 아니다.
- **AC4.1.5 분리**: 응답 스키마(점수 필드 없음) / 금지 표현 / 색+글자 / 대비 네 검증이 층이 다르다. 마커 하나에 묶으면 한 층만 통과해도 AC 가 초록으로 보인다. AC4.1.5~AC4.1.8 로 나누는 것을 제안한다(US4.1 은 AC 8개가 되므로 AC4.1.2 를 판정 엔진 스토리로 떼는 INVEST 메모와 함께 검토).
- **열린 질문으로 추가**: 수용 기준 마커는 `@pytest.mark.ac` 만 정해져 있다. 프론트엔드 AC(대부분의 화면 AC)를 Vitest·Playwright 에서 어떻게 표시할지 없다 → ci-pipeline(3.7) / build-and-test(3.6).
