## 1. 의도 분석

**사용자가 이루려는 것** — SCD(사회적 의사소통장애)로 의사소통에 어려움을 겪는 13–18세
청소년이 실제 대화를 **근거와 함께 돌아보고**, 거기서 고른 목표를 **그대로 연습으로
이어가는** 흐름을 만든다 `[intent]`. 지금 이들에게는 "잘 안 됐다"는 인상만 남고, 어느
발화에서 무엇이 어긋났는지 짚어주는 수단도, 그것을 연습으로 잇는 수단도 없다.

**이번 작업의 목적** — AI-DLC 워크플로 검증을 겸한 테스트 MVP 다. 실제 사용자 데이터
없이 합성 데이터로 흐름 전체가 성립하는지 확인한다 `[intent]`.

**성공 기준은 하나다** `[intent]` (D-16):

| # | 성공 기준 | 측정 방법 |
|---|---|---|
| SM1 | 합성 대화 3건(`[spec:05]` S1·S2·S3)이 업로드 → 전사 확인 → 리포트 → 목표 선택 → 모의 대화 → 기록까지 끊김 없이 이어진다 | `docker compose up --build` 후 헬스체크 통과, 3건 각각 전 구간 종단 실행 성공 `[practices]` (D-58) |

근거 발화 유효성, 보류가 실패로 집계되지 않는 것, 재시도가 첫 시도를 덮어쓰지 않는
것, 전사 정정 시 재검토 표시와 삭제 전파, 화면의 금지 표현 부재는 성공 기준이 아니라
아래 기능·비기능 요구사항으로 다룬다 `[intent]` (D-16). SM1 통과는 판정 정확성을
보장하지 않으며, 판정 정확성은 픽스처 기반 단위 테스트가 본다 `[practices]` (D-57).

**분류** — 신규 구축(그린필드), 시스템 전체(프론트엔드 + 단일 백엔드 + DB), 표준
복잡도. 도메인 규칙(판정 상태·분모·삭제 전파)은 기존 명세가 이미 정의했고, 이 단계는
그것을 검증 가능한 요구사항으로 옮기고 빈자리 8곳을 사용자 결정으로 채웠다.

## 3. 기능 요구사항

등급은 `[scope]` 를 그대로 따른다. **Must 경로는 미리 만들어 둔 고정 사용자 하나로
돈다** `[scope]` (D-44). Should 로 표시된 항목은 **취소된 것이 아니라 만드는 시점만
뒤로 간 것**이다.
