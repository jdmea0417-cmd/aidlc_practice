## Q1. 어떤 화면 크기와 브라우저에서 동작해야 합니까?

기존 명세는 "모바일 웹, 375px 기준"이라고 적고 있고 `[spec:03]`, 제약 TC-02 도 같은
문장을 담고 있습니다 `[constraint]`. 다만 결정 기록에서는 이 값이 여전히 가정
A-03 으로 남아 있고 `[log]`, 시연(2026-11-05)은 로컬 Docker Compose 로 띄우므로
노트북 브라우저에서 보게 될 가능성이 큽니다. 요구사항에 "어디서 제대로 보여야
하는지"를 적어야 테스트할 수 있습니다.

- A. 모바일 폭(375px) 하나만 보장한다 — 노트북에서는 브라우저 개발자 도구의 모바일 화면 모드로 본다
- B. 모바일 폭을 기준으로 만들고, 노트북 브라우저에서도 가운데 정렬된 모바일 폭 화면으로 깨지지 않게 보인다
- C. 모바일과 노트북 화면을 모두 반응형으로 제대로 지원한다
- D. 화면 크기는 A처럼 두되, 지원 브라우저를 Chrome 최신판 하나로 한정한다고 함께 적는다
- X. Other (please specify)

[Answer]: C. 모바일과 노트북 화면을 모두 반응형으로 제대로 지원한다 — 변경됨 → FU1 (모바일 폭은 Must, 노트북 반응형 레이아웃은 Should 로 나눔)

## Q2. 모의 대화(화면 B3)는 텍스트로만 주고받습니까?

UI 명세의 모의 대화 화면은 채팅 말풍선과 텍스트 입력창으로 그려져 있습니다
`[spec:03]`. 그러나 "모의 대화 매체 = 텍스트 채팅"은 아직 확인되지 않은 가정 A-04 로
남아 있습니다 `[log]`. 음성 코칭(TTS)은 제외 항목이지만 `[intent]`, 사용자가 말로
답하는 입력(음성 입력)은 따로 정해진 적이 없습니다.

- A. 텍스트로만 주고받는다 — 입력도 출력도 글자다
- B. 출력은 텍스트, 입력은 텍스트와 음성(녹음 → 전사) 둘 다 허용한다
- C. 텍스트로만 하되, 음성 입력은 이후 확장 후보로 요구사항의 범위 밖 항목에 적어 둔다
- D. 텍스트로만 하되, 휴대폰 키보드의 음성 받아쓰기로 입력하는 것은 막지 않는다(별도 기능 없음)
- X. Other (please specify)

[Answer]: C. 텍스트로만 하되, 음성 입력은 이후 확장 후보로 요구사항의 범위 밖 항목에 적어 둔다

## Q3. 행동 묶음 3종의 판정 기준을 무엇으로 확정합니까?

리포트의 판정은 행동 묶음 3종 — 응답 관련성, 명료화·대화 수리, 주제 유지·전환 — 각각에
대해 "관찰 기회가 있었는가 → 목표 행동이 나타났는가 → 실패로 보지 않는 경우"로
나뉩니다. 이 정의는 `docs/input/04_domain-model.md` §4 에 "개발용 초안, 공식 척도
아님"으로 적혀 있고, 가정 A-10 으로 남아 있습니다 `[spec:04][log]`. 요구사항이 이
표를 기준으로 삼을지를 정해야 판정 요구사항을 테스트 가능한 문장으로 쓸 수 있습니다.

- A. 초안 표를 그대로 이번 MVP 의 판정 기준으로 확정한다 — 화면과 문서에 "공식 척도가 아님"을 함께 밝힌다
- B. 초안 표를 확정하되, 대상이 13–18세로 바뀐 만큼 "실패로 보지 않는 경우"에 청소년 대화 예를 추가하는 작업을 functional-design(3.1)에 맡긴다
- C. 초안 표를 요구사항에는 그대로 쓰되, 확정이 아니라 "개발용 기준(변경 가능)"으로 표시하고 기준 버전을 붙여 관리한다
- D. 지금은 확정하지 않고 domain-design(2.6)에서 모델링하면서 다시 정한다
- X. Other (please specify)

[Answer]: A. 초안 표를 그대로 이번 MVP 의 판정 기준으로 확정한다 — 화면과 문서에 "공식 척도가 아님"을 함께 밝힌다

## Q4. 리포트의 "분석이 이상해요" 버튼을 누르면 무슨 일이 일어납니까?

리포트 화면(A4)에는 "분석이 이상해요" 수정 요청 버튼이 있습니다 `[spec:03]`. 서비스
원칙 7 은 "분석 수정 요청이 항상 가능하다"고 적고 있습니다 `[spec:01]`. 그런데 그
요청을 받아 볼 사람(전문가)은 MVP 에서 제외되었고 `[intent]`, 요청이 어디로 가서 무엇이
바뀌는지는 어느 문서에도 없습니다.

- A. 요청 내용(어느 장면이 왜 이상한지)을 저장만 한다 — 판정은 바뀌지 않고, 저장된 요청은 기록으로 남는다
- B. 대화 내용 확인 화면(A3)이나 맥락 입력으로 돌려보내 사용자가 전사·맥락을 고치고 다시 분석하게 한다
- C. A와 B 둘 다 — 요청을 저장하고, 고칠 곳이 전사·맥락이면 그 화면으로 안내한다
- D. 해당 판정을 사용자 화면에서 "보류" 섹션으로 옮기고 요청을 저장한다
- X. Other (please specify)

[Answer]: C. A와 B 둘 다 — 요청을 저장하고, 고칠 곳이 전사·맥락이면 그 화면으로 안내한다

## Q5. 전사를 고친 뒤 "다시 분석하기"는 어느 화면에서 합니까?

합성 대화 S3 의 검증 항목 2 는 "전사를 고치면 기존 판정에 재검토 필요가 표시되고,
다시 분석하면 응답 관련성이 OBSERVED 로 바뀐다"입니다 `[spec:05]`. 이 항목은 F07 을
Must 로 올린 이유 자체입니다(D-59) `[scope]`. 그런데 "다시 분석하기" 버튼이 명세에
있는 곳은 실제 대화 기록 상세 화면(C4)뿐이고, C4 는 Should 입니다 `[spec:03][scope]`.
그대로 두면 Must 범위 안에서 S3 의 검증 항목 2 를 끝까지 확인할 수 없습니다.

- A. 대화 내용 확인 화면(A3)에서 고친 뒤 "이대로 분석하기"를 다시 누르면 재분석된다 — 새 판정이 추가되고 이전 판정은 지워지지 않는다
- B. 리포트 화면(A4)에 "재검토 필요" 표시와 "다시 분석하기" 버튼을 둔다
- C. C4 의 "다시 분석하기" 부분만 Must 로 올린다 (C5 처럼 화면을 나눈다)
- D. A와 B 둘 다 — A3 에서 고친 뒤 재분석할 수 있고, A4 에도 재검토 표시와 버튼을 둔다
- X. Other (please specify)

[Answer]: A. 대화 내용 확인 화면(A3)에서 고친 뒤 "이대로 분석하기"를 다시 누르면 재분석된다 — 새 판정이 추가되고 이전 판정은 지워지지 않는다

## Q6. Mock 모드에서 올린 파일이나 녹음은 합성 대화 3건 중 무엇으로 처리됩니까?

기본 실행 경로는 Mock 이고 SM1 도 Mock 으로 검증합니다 `[constraint]` SC-04·SC-05.
Mock 은 `conversationKey`(예: `conv_repair_01`)로 기대 판정을 돌려주는데
`[spec:05]`, 실제로 올린 음성 파일이나 브라우저에서 녹음한 음성이 어느 키로
연결되는지는 정해져 있지 않습니다. 이것이 정해지지 않으면 SM1 의 종단 실행을 어떻게
시작하는지 요구사항에 쓸 수 없습니다.

- A. 파일 이름으로 연결한다 — `conv_repair_01.webm` 처럼 키가 파일 이름에 들어 있으면 그 대화로 처리하고, 키가 없으면 전사 실패로 처리한다
- B. Mock 모드일 때만 가져오기 화면(A2)에 "합성 대화 선택" 칸을 보여 주고, 사용자가 3건 중 하나를 고른다

- D. B와 같되, 브라우저 녹음은 선택 칸 없이 항상 S1 로 처리한다

[Answer]: C. A와 같되, 키가 없는 파일과 브라우저 녹음은 S1(`conv_repair_01`)로 처리한다

## Q7. 접근성은 어느 수준까지 요구합니까?

주 사용자는 의사소통에 어려움이 있는 13–18세 청소년입니다 `[intent]`. 그런데
글자 대비, 화면 낭독기 지원, 키보드 조작 같은 접근성 요구는 어느 문서에도 정해져 있지
않습니다. 측정할 수 있는 기준을 하나 정해야 Construction 에서 확인할 수 있습니다.

- A. 기본만 — 모든 버튼·입력에 이름표를 달고, 색만으로 의미를 전달하지 않는다(보류는 노랑 + 글자 표시)

- C. WCAG 2.1 AA 전체를 목표로 하고 자동 검사 도구(예: axe)로 확인한다
- D. 이번 MVP 에서는 접근성 요구사항을 두지 않고, 범위 밖 항목에 이유와 함께 적는다
- X. Other (please specify)

[Answer]: B. WCAG 2.1 AA 중 핵심 항목만 — A에 더해 글자 대비 4.5:1 이상, 터치 영역 44px 이상, 키보드로 주요 흐름을 끝까지 조작 가능

## Q8. 보호자 열람 권한 "요약만(SUMMARY)"과 "전체(FULL)"는 각각 무엇을 보여 줍니까?

보호자 열람 권한 NONE / SUMMARY / FULL 세 단계는 확정되었고(D-29), 만드는 시점만
Should 로 뒤로 갔습니다(D-44) `[scope]`. 데이터 모델은 이 결정을 처음부터 반영해야
합니다. 그런데 "요약"과 "전체"가 각각 무엇을 보여 주는지, 보호자가 어느 화면에서
보는지는 어느 문서에도 없습니다 — UI 명세의 화면 A/B/C 는 모두 사용자 본인용입니다
`[spec:03]`. 이 경계가 없으면 보호자에게 전사 원문이 보이는지부터 정해지지 않습니다.

- A. SUMMARY = 목표와 목표별 추이(나의 기록 C1 수준) / FULL = 거기에 더해 리포트(A4 수준)까지. 전사 원문과 원음은 두 단계 모두 보이지 않는다
- B. SUMMARY = 목표와 추이 / FULL = 리포트·전사 원문까지 전부. 원음은 보이지 않는다
- C. SUMMARY = 목표와 추이 / FULL = 사용자가 보는 모든 것(원음 포함)
- D. 지금 정하지 않는다 — 요구사항에는 "정의 필요"로 열어 두고 Should 착수 시점에 정한다
- X. Other (please specify)

[Answer]: A. SUMMARY = 목표와 목표별 추이(나의 기록 C1 수준) / FULL = 거기에 더해 리포트(A4 수준)까지. 전사 원문과 원음은 두 단계 모두 보이지 않는다
