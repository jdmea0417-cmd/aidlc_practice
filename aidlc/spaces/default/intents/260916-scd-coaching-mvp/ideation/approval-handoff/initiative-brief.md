## 1. 무엇을 만드는가

SCD(사회적 의사소통장애)로 의사소통에 어려움을 겪는 **13–18세 청소년**이 실제 대화를
돌아보고, 거기서 고른 목표를 그대로 연습으로 이어가는 모바일 웹 서비스다 `[intent]`.

지금 이들에게 남는 것은 "잘 안 됐다"는 인상뿐이고, 어느 발화에서 무엇이 어긋났는지
짚어주는 수단이 없다. 그래서 다음에 무엇을 연습해야 하는지도 이어지지 않는다. 이
서비스는 그 단절을 잇는다 `[intent]`.

```
실제 대화 녹음·전사 ─> 맥락 확인 ─> 근거 붙은 리포트 ─> 목표 선택 ─> 모의 대화 연습 ─> 기록·다음 추천
```

## 2. 왜 지금 만드는가

**AI-DLC 워크플로 검증을 겸한 테스트 MVP** 다. 실제 사용자 데이터 없이 합성
데이터로 흐름 전체가 성립하는지 확인하는 것이 주목적이다 `[intent]`.

이 계기가 범위를 판단하는 기준이 된다. 실제 사용자 데이터 수집과 클라우드 배포는
필요하지 않다. STT·LLM 은 기본 실행과 검증을 Mock 으로 하고, 실제 제공자에 붙는
live 구현체는 선택 경로로만 만든다 `[intent]`.

## 3. 누구를 위한 것인가

| 이해관계자 | 역할 | 무엇을 중요하게 보는가 |
|---|---|---|
| 주 사용자 (13–18세 청소년) | 대화를 올리고, 리포트를 읽고, 모의 대화로 연습한다 | 자기 대화를 이해할 수 있는 말로 돌아보는 것. 실패로 규정당하지 않는 것 |
| 보호자·의사소통 지원자 | 사용자가 허용한 범위에서 결과를 **열람만** 한다 | 허용된 범위의 열람. 데이터 보관과 삭제 통제 |

전문가(언어재활사·특수교사)는 MVP 제외다 `[stake]`.

**결정권자**는 프로젝트를 진행하는 사용자 본인이며 범위와 우선순위를 단독으로
결정한다. 다만 `docs/input/` 의 기존 결정(D-01~D-05)이 우선하며, 이를 뒤집을 때만
별도 확인을 거친다 `[stake]`.

## 4. 성공을 무엇으로 판단하는가

| # | 성공 기준 | 측정 방법 |
|---|---|---|
| SM1 | 합성 대화 3건이 업로드 → 전사 확인 → 리포트 → 목표 선택 → 모의 대화 → 기록까지 **끊김 없이 이어진다** | 합성 대화 3건 각각에 대해 전 구간을 통과하는 종단 실행이 성공한다 |

기준은 이 하나다 `[intent]`. 근거 발화 ID 유효성, 보류 사례가 실패로 집계되지 않는
것, 재시도가 첫 시도를 덮어쓰지 않는 것, 전사 정정 시 재검토 표시와 삭제 전파,
화면의 금지 표현 부재 — 이 다섯은 성공 기준이 아니라 구현 세부사항으로 다룬다.

**2026-11-05 시연 필수선도 SM1 그대로다.** 범위를 줄여야 하면 이 선까지는 지킨다
`[scope]`.

## 5. 범위 경계

| 등급 | 항목 |
|---|---|
| **Must** | F01~F06 (녹음·전사 / 맥락 구조화 / 수행 평가 / 목표·프로필 / 모의 대화 / 기록·다음 추천), **F07 정정·삭제**, 화면 A1~A5 · B1~B5 · C1 · **C5 의 삭제 부분**, 파일 업로드와 브라우저 직접 녹음 두 경로 |
| **Should** | 화면 C2~C4, **C5 중 삭제 부분을 뺀 나머지**(보호자 권한 전환·원음 보관 기간·서비스 안내), 회원가입·로그인 정식 구현, 보호자 열람 권한 NONE/SUMMARY/FULL |
| **Won't have** | 자동진단, 임상 점수, 비디오 평가, Vector RAG·Neo4j, 전문가 대시보드, 음성 코칭(TTS), 결제, 실제 사용자 데이터 수집, 네이티브 앱 |

**Must 경로는 미리 만들어 둔 고정 사용자 하나로 돈다** `[scope]`. 보호자 권한 3단계와
기본값 NONE 이라는 결정은 취소되지 않았고 만드는 시점만 뒤로 갔다. 데이터 모델은 이
결정을 처음부터 반영해 나중에 스키마를 바꾸지 않게 한다.

작업 목록은 proto-Unit 11개(**Must 8 / Should 3**)로 정리되어 있다 `[backlog]`. 임계
경로는 PU-01 → PU-02 → PU-03 → PU-04 → PU-05 → PU-06 이며 SM1 의 여섯 단계와
일치한다.

**F07 은 이번에 Should 에서 Must 로 올라왔다** `[Q5]`. 근거는 합성 대화 S3 의 검증
항목 2·4 가 F07 에 걸려 있어, F07 없이는 성공 기준을 판정할 자료의 절반이 확인되지
않는다는 것이다. 화면 C5 는 두 번에 나뉘어 만들어진다 — 삭제 부분은 Must 시점에,
보호자 권한 전환·원음 보관 기간·서비스 안내는 Should 시점에 만든다. 취소된 것은
없고 만드는 시점만 앞뒤로 움직였다.

이로써 Must 가 전체의 **73%** 가 되어 프레임워크 권고 60% 를 넘는다. 수치를 맞추려
내용을 줄이지 않았다 — PU-01~PU-07 은 성공 기준 SM1 의 종단 경로 자체이고, PU-08
(F07)은 그 성공 기준을 판정할 자료의 절반을 확인 가능하게 만든다. **이 초과는 의도된
것으로 기록한다** `[backlog][Q5]`.

## 6. 기술적으로 가능한가

**실현 가능하다. 단 조건부 2건이 있다** `[feas]`.

| # | 판정 항목 | 결과 |
|---|---|---|
| 1 | MVP 범위 F01~F07 을 로컬 환경에서 구현할 수 있는가 | 가능 |
| 2 | 성공 기준 SM1 을 검증할 수 있는가 | 가능 — Mock 이 기대 판정을 고정 반환해 결정적으로 재현된다 |
| 3 | 선택한 기술 스택을 팀이 다룰 수 있는가 | **조건부** — 위험 R1 |
| 4 | 마감 안에 끝낼 수 있는가 | **조건부** — 위험 R5 |

### 확정된 기술 구성

React 18 + TypeScript 5 + Vite 5 / **Python 3.11 + FastAPI 단일 백엔드** /
PostgreSQL 16 / Docker Compose 3 컨테이너(frontend, backend, postgres). 클라우드
배포 없음 `[feas][constraint]`.

Python 쪽 도구는 ORM **SQLAlchemy 2.0(동기)**, 마이그레이션 **Alembic**, 패키지
관리자 **uv** 로 확정되었다 `[constraint] TC-15`. 제약 TC-15 와 RAID 의 의존 D3 가
이로써 닫혔고, 첫 작업 단위가 바로 실제 스택을 관통할 수 있다 `[Q5]`.

병합 전 검사는 **GitHub Actions** 가 강제하며, 그 워크플로와 품질 게이트는
ci-pipeline(3.7)이 만든다 `[constraint] TC-16`. 이는 클라우드 배포 없음이라는 범위
경계와 충돌하지 않는다 — Actions 는 배포가 아니라 검사다 `[Q5]`.

원래 명세의 Java core + Python analysis 2-서비스 구성은 결정 D-30 으로 폐기되었고,
`docs/input/02_tech-environment.md` 는 이 단계에서 Python 전제로 재작성되었다
`[Q2]`.

## 9. 계획 변경 기록

워크플로 계획이 두 번 바뀌었다.

| # | 항목 | 변경 전 | 변경 후 | 언제 |
|---|---|---|---|---|
| 1 | user-stories (2.4) | SKIP | **EXECUTE** | 이 단계 `[Q3]` |
| 2 | ci-pipeline (3.7) | SKIP | **EXECUTE** | practices-discovery(2.2) 후속 `[Q5]` |
| | EXECUTE 단계 수 | 19 | **21** | |

**1번의 이유**: Inception 지침이 수용 기준을 Given/When/Then 형식으로 요구하는데, 그
일을 맡을 단계가 계획에 없었다. 이대로 가면 요구사항이 검증 기준 없이 Construction
까지 간다 `[Q3]`.

**2번의 이유**: 병합 전 검사를 GitHub Actions 로 강제하기로 정했는데, 그 워크플로
파일을 작성할 단계가 계획에 없었다 `[Q5]`.

두 변경 모두 같은 모양이다 — 건너뛴 단계가 담당하던 일이 주인 없이 남아 있었고,
담당 단계를 다시 넣어 메웠다. 둘 다 별도의 승인 절차를 거쳐 반영되었다.
