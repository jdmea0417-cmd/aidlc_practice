## 1. 한 문단 요약

이번 작업은 SCD(사회적 의사소통장애)로 의사소통에 어려움을 겪는 13–18세 사용자가
**실제 대화를 돌아보고 거기서 고른 목표를 그대로 연습으로 이어가는 흐름**을 만든다
`[intent]`. 이번 범위의 성패는 그 흐름이 끊기지 않고 이어지는지 하나로 판단하며,
정정·삭제와 계정·권한처럼 흐름 밖에 있는 기능은 흐름이 선 뒤에 붙인다 `[Q1][F2]`.

## 2. 최소 가치 범위 (Minimum Viable Scope)

**합성 대화 한 건이 업로드에서 기록까지 끊기지 않고 도착하는 것.** 이것이 이번
작업의 최소 단위이며, 성공 기준 SM1 이 그대로 이 문장이다 `[intent][Q5]`.

여섯 단계 중 하나라도 빠지면 최소 가치 범위가 성립하지 않는다.

```
업로드 ──> 전사 확인 ──> 리포트 ──> 목표 선택 ──> 모의 대화 ──> 기록
 F01        F01·F02       F03        F04          F05          F06
 A2/A2-R    A3            A4         A5           B1~B5        C1
```

## 3. 범위 경계

### 3.1 Must — 이번에 반드시 만든다

| # | 항목 | 근거 |
|---|---|---|
| M1 | F01 녹음·전사 — 파일 업로드와 브라우저 직접 녹음 **두 경로 모두** | `[intent]`, `[Q3]` |
| M2 | F02 맥락 구조화 — 관계·장소·목적·사용자 목표, 모르는 정보는 "미상"으로 저장 | `[intent]`, `[spec:01]` |
| M3 | F03 수행 평가 — 행동 묶음 3종에 대한 기회 판정 → 행동 판정 → 근거·보류 사유 | `[intent]`, `[spec:01]` |
| M4 | F04 목표·프로필 — 추천 목표와 추천 이유, 원인 사건 표시, 사용자 선택 저장 | `[intent]`, `[spec:01]` |
| M5 | F05 모의 대화 — 시나리오 원형과 제한적 변형, 첫 시도·3단계 힌트·재시도·중단 기록 | `[intent]`, `[spec:01]` |
| M6 | F06 기록·다음 추천 — 실제/모의 구분, 조건별 추이, 기록 부족 시 "비교 불충분" | `[intent]`, `[spec:01]` |
| M7 | 화면 A1~A5 (홈·가져오기·녹음·전사확인·리포트·목표선택) | `[Q2]`, `[spec:03]` |
| M8 | 화면 B1~B5 (연습목록·준비·모의대화·도움·결과) | `[Q2]`, `[spec:03]` |
| M9 | 화면 C1 (나의 기록) | `[Q2]`, `[spec:03]` |
| M10 | F07 정정·삭제 — 전사 정정 시 재검토 표시(화면 A3), 삭제 요청 시 연결 항목 미리보기와 전파 처리, 원음만 삭제(화면 C5 의 삭제 부분) | `[F3][F5]` |

Must 경로는 미리 만들어 둔 **고정 사용자 하나**로 전 화면이 돌아간다 `[F1][F2]`.

**M10 은 이번 회차에 Should 에서 올라온 것이다.** 근거는 합성 대화 S3
(`docs/input/05_synthetic-test-data.md`)의 검증 항목 2(전사 정정 후 관련 판정 재검토
표시)와 4(삭제 시 연결 항목 처리)가 F07 에 걸려 있어, F07 없이는 S3 가 원래
확인하려던 것의 절반을 확인할 수 없다는 것이다 `[F3][F5]`. 종전 근거였던 "SM1 의
여섯 단계 어디에도 들어가지 않는다"는 등급 판단의 근거로 더 이상 쓰지 않는다.

**화면 C5 는 두 번에 나뉘어 만들어진다.** M10 이 여는 것은 C5 의 삭제 관련
부분뿐이다 — 기록 삭제 요청, 연결 항목 미리보기, 원음만 삭제. 같은 화면의 보호자
열람 권한 전환, 원음 보관 기간 설정, 서비스 안내 다시 보기는 아래 S3 에 남아 Should
시점에 만든다. 하위 단계는 C5 를 한 번에 완성하는 화면으로 다루지 않는다 `[F3][F5]`.

### 3.2 Should — 종단 흐름이 선 뒤에 만든다

| # | 항목 | 왜 Should 인가 | 근거 |
|---|---|---|---|
| S2 | 화면 C2~C4 (목표 상세·연습 기록 상세·실제 대화 기록 상세) | 상세 조회 화면이며 종단 경로에 필요하지 않다 | `[Q2]` |
| S3 | 화면 C5 중 **삭제 부분을 뺀 나머지** — 보호자 열람 권한 전환, 원음 보관 기간 설정, 서비스 안내 다시 보기 | 권한 전환은 S4·S5 에 딸린 것이고, 나머지는 종단 경로에 필요하지 않다. C5 의 삭제 부분은 M10 으로 올라갔다 | `[Q2][F3][F5]` |
| S4 | 회원가입·로그인 정식 구현 | 합성 데이터 전용이라 고정 사용자로도 종단 실행이 성립한다 | `[F2]` |
| S5 | 보호자 열람 권한 NONE / SUMMARY / FULL 동작 | S4 가 선행되어야 하고, 권한을 켜는 화면 부분(C5 의 권한 전환)도 S3 로 Should 에 남아 있다 | `[F1][F5]` |

**S4·S5 에 대한 주의**: 보호자 열람 권한을 3단계로 둔다는 결정과 계정은 사용자가
만들고 권한 기본값은 NONE 이라는 결정은 `[intent]` 에서 확정된 것이고 **취소되지
않았다**. 만드는 시점만 뒤로 갔다 `[F1][F2]`. 데이터 모델은 이 결정을 처음부터
반영해야 하며, 나중에 스키마를 바꾸지 않아도 되게 설계한다.

### 3.3 Won't have (this time) — 이번에 만들지 않는다

`[intent]` 에서 확정된 제외 9건을 그대로 유지한다: 자동진단, 임상 점수, 비디오 평가,
Vector RAG·Neo4j, 전문가 대시보드, 음성 코칭(TTS), 결제, 실제 사용자 데이터 수집,
네이티브 앱.

여기에 이번 단계에서 추가된 항목은 없다.

## 4. 시연 필수선 (2026-11-05)

범위를 줄여야 할 때 **마지막까지 지키는 선**은 SM1 그대로다 `[Q5]`: 합성 대화 3건이
업로드부터 기록까지 끊김 없이 이어지는 것.

즉 축소 압박이 오면 Should 를 먼저 버리고, Must 안에서도 SM1 여섯 단계를 지킨다.
직접 녹음(M1 의 두 번째 경로)은 Must 이지만 SM1 이 요구하지 않으므로, 여섯 단계와
직접 녹음 중 하나를 골라야 하는 상황이 오면 여섯 단계가 우선한다 `[Q3][Q5]`.

**F07(M10)은 더 이상 먼저 버리는 대상이 아니다.** Should 에서 Must 로 올라갔기
때문이다 `[F3][F5]`. 다만 F07 역시 SM1 여섯 단계 자체에는 들어가지 않으므로, 직접
녹음과 같은 자리에 선다 — 여섯 단계와 F07 중 하나를 골라야 하는 상황이 오면 여섯
단계가 우선한다. 이렇게 되면서 Should 에 남은 것은 S2(화면 C2~C4), S3(C5 의 삭제
부분을 뺀 나머지), S4(정식 인증), S5(보호자 권한) 넷이고, 축소 여지가 그만큼
줄었다 `[F5]`.

## 5. 만드는 순서

**얇은 종단 슬라이스 먼저** `[Q6]`. 업로드부터 기록까지를 최소 형태로 한 번
관통시킨 뒤 각 기능의 깊이를 채운다.

이 순서를 고른 이유는 `[raid]` 의 두 위험에 동시에 대응하기 때문이다. 팀의 Python
경험이 일부라는 위험(R1)은 전체 스택을 일찍 한 번 통과시켜야 드러나고, 7주 일정
위험(R5)은 종단 경로가 언제 서는지를 일찍 알아야 관리할 수 있다.

```
1단계  종단 슬라이스 — 여섯 단계가 최소 형태로 한 번 이어진다
2단계  각 단계의 깊이 채우기 — 판정 규칙, 힌트 3단계, 추이 집계
3단계  Must 잔여 — 직접 녹음, F07 정정·삭제(C5 의 삭제 부분 포함)
4단계  Should — C2~C4, C5 의 나머지, 인증, 보호자 권한
```

<!-- Text fallback: 네 단계 순서. 먼저 종단 슬라이스로 여섯 단계를 최소 형태로 잇고, 다음에 각 단계의 깊이를 채우고, 그다음 Must 에 남은 직접 녹음과 F07 정정·삭제를 만들고, 마지막에 Should 항목을 만든다. -->

F07 이 3단계에 놓인 것은 이번 회차의 변경이다 `[F4]`. F07 의 삭제 전파는 제약 TC-14 와 위험 R3 — 단일 백엔드 전환으로 사라진 데이터 소유 경계를 계층 규칙으로 다시 세우는 문제 — 에 걸려 있고, 그 경계는 domain-design(2.6)이 닫는다. 4단계까지 미루면 이미 쌓인 코드를 고쳐야 할 범위가 넓어진다.

## 6. 병렬 작업 갈래

**이 단계에서 정하지 않는다** `[Q7]`. 5인 전원 풀스택으로 작업 단위별로 나눈다는
것만 확정되어 있고 `[constraint] OC-03`, 몇 갈래로 나눌지는 작업 단위 분해

## 7. 가치 흐름 지도

```
[사용자가 겪는 일]                    [이 서비스가 하는 일]              [남는 것]

실제 대화를 하고 나서              →  대화를 가져와 전사하고            →  무슨 말이
"잘 안 됐다"는 인상만 남는다          맥락을 확인한다 (F01·F02)            오갔는지

어느 발화에서 무엇이               →  근거 발화가 붙은 리포트를          →  왜 그렇게
어긋났는지 모른다                     만든다 (F03)                         봤는지

다음에 뭘 연습할지                 →  리포트에서 목표를 고르고           →  연습할
이어지지 않는다                       그대로 연습으로 넘긴다 (F04·F05)     목표 하나

나아지는지 알 수 없다              →  독립/도움 후를 나눠 기록하고       →  다음에
                                      다음 코칭을 추천한다 (F06)           할 것
```

<!-- Text fallback: 사용자가 겪는 네 가지 불편이 각각 서비스의 기능과 짝지어진다. 인상만 남는 문제는 F01과 F02의 전사·맥락 확인이, 어긋난 지점을 모르는 문제는 F03의 근거 리포트가, 연습으로 이어지지 않는 문제는 F04와 F05의 목표 선택·모의 대화가, 나아지는지 모르는 문제는 F06의 기록·추천이 받는다. -->

이 지도는 `[intent]` 의 문제 서술과 F01~F06 을 잇는다. F07(정정·삭제)은 이 흐름의
어느 칸도 채우지 않는다. 그러나 그것이 F07 의 등급을 정하지는 않는다 — F07 은 M10
으로 Must 다 `[F3][F5]`. 이 지도가 덮는 것은 사용자가 겪는 불편과 기능의 대응이고,
F07 의 근거는 다른 곳에 있다: 합성 대화 S3 의 검증 항목 2·4 가 F07 에 걸려 있어,
F07 없이는 성공 기준을 판정할 자료의 절반이 확인되지 않는다. 즉 F07 은 사용자 가치
흐름이 아니라 **검증 가능성**에서 근거를 얻는다.

## 8. 이 단계에서 정하지 않은 것

- **작업 단위(Unit)의 구체적 경계와 개수** — units-generation(2.7)
- **병렬 갈래 수** — `[Q7]` 에 따라 units-generation(2.7)
- **Bolt 순서와 소유권** — delivery-planning(2.9)
- **Should 항목의 착수 시점** — 종단 흐름이 선 뒤의 실제 잔여 일정에 달려 있다. F07 은 이 목록에서 빠졌다. Must 로 올라가 3단계에 놓였기 때문이다 `[F4][F5]`
