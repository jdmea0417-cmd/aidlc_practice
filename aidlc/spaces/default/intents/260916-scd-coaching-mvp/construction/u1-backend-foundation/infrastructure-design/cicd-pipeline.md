## 이 문서의 역할 — 요구 명세이지 워크플로 파일이 아니다

**GitHub Actions 워크플로 파일 자체는 ci-pipeline(3.7)이 만든다** (D-56). 이 문서는 그 단계가 읽을 **요구
명세**다 `[Q4]` — 파이프라인이 무엇을 검사해야 하고, 각 검사가 무엇을 통과 기준으로 삼으며, 무엇이 병합을
막는가.

| 이 문서가 정하는 것 | 3.7 이 정하는 것 |
|---|---|
| 검사 항목과 통과 기준 | 워크플로 파일의 실제 문법과 구성 |
| 무엇이 병합을 막는가 | 작업 분할, 병렬 실행, 캐시 전략 |
| 순서상의 제약 | 실행기 종류, 버전 고정 방식 |
| 비밀값을 파이프라인에서 어떻게 다루는가 | 저장소 설정의 실제 등록 |

두 문서가 어긋나 보이면 **검사 내용은 이 문서가, 실행 방법은 3.7 이 기준**이다.

## 1. 전제 — 이 프로젝트의 "배포"가 무엇인가

| 사실 | 근거 |
|---|---|
| 배포 대상은 개발자 각자의 로컬 컨테이너뿐이다. 자동 배포가 없다 | `[practices]` Deployment, `[constraint:SC-01]` |
| "배포 성공"은 `docker compose up --build` 후 헬스체크 통과 + 합성 대화 3건 종단 통과다 | D-58 |
| 따라서 파이프라인의 일은 **배포가 아니라 병합 전 검사**다 | D-55 |
| 유일한 릴리스 사건은 2026-11-05 시연이며, 그것은 태그 고정 + 새 clone 리허설이다 | `[practices]` Deployment |

**일반적인 전달 파이프라인의 절반(환경 승격, 배포 전략, 무중단 전환)은 대상이 없다.** 이 문서는 그 절반을
비워 두고 나머지를 정확히 적는다.

## 2. 검사 단계와 통과 기준

순서는 **빠르고 값싼 것부터**다 — 형식 오류로 20분짜리 검사를 돌리지 않기 위해서다.

| # | 단계 | 무엇을 검사하는가 | 통과 기준 | 근거 |
|---|---|---|---|---|
| 1 | 비밀값 검사 | 커밋에 키·자격증명이 들어갔는지 | 0건 | `[nfr]` NFR6.3. 한 번 들어가면 되돌리기가 가장 비싸다 |
| 2 | 형식·린트 | 코드 형식과 린터 규칙(`E, F, I, UP, B, SIM, TID, RUF, S`) | 위반 0건 | `[practices]` Code Style. `S` 규칙이 하드코딩된 비밀값 후보도 잡아 1번을 보강한다 |
| 3 | 계층 경계 | `api` 가 `repository` 를 직접 import 하지 않는지 | 위반 0건 | `[constraint:TC-14]`. 린터 규칙으로 표현되므로 2번과 같은 실행에서 끝난다 |
| 4 | 타입 검사 | 타입 오류. `app.service.*` 는 타입 필수 | 오류 0건 | `[practices]` Code Style (D-54) |
| 5 | 단위 테스트 | 통합·종단 표시가 없는 전부 | 전부 통과 | `[practices]` Testing Posture |
| 6 | 커버리지 | `backend/app/service/` 라인 커버리지 | **80% 이상** | `[nfr]` NFR14.2, D-57. **통과시키려고 낮추지 않는다** |
| 7 | 통합 테스트 | 실제 저장소를 띄워 도는 것 — 응답 시간 단언 포함 | 전부 통과, 세 엔드포인트 200ms 이내 | `[nfr]` NFR3.1~3.3 |
| 8 | 프론트엔드 검사 | 형식·린트·단위 테스트 | 전부 통과 | u2 가 들어오면 채워진다 |
| 9 | 종단 시험 (빠른 루프) | 합성 대화 S1 하나 | 통과 | `[practices]` Testing Posture — 병합 전에는 S1 만 |

### 별도 주기로 도는 것

| 검사 | 언제 | 근거 |
|---|---|---|
| 종단 시험 3건 전체 | 작업 단위 완료 시점 · 주 1회 고정 시각 · 태그·리허설 전 | `[practices]` Testing Posture |

## 3. 무엇이 병합을 막는가

| 규칙 | 내용 |
|---|---|
| 필수 통과 | §2 의 1~9 **전부**. 하나라도 실패하면 병합하지 않는다 `[practices]` Way of Working (D-55) |
| 사람 확인 | 그 작업 단위를 만들지 않은 사람 1인의 리뷰. **필수 확인 항목은 하나 — 해당 PR 의 검사가 통과했는가** |
| 새 의존성 | 리뷰어가 **새 패키지 이름 각각을 공식 문서와 배포 페이지에서 확인**한다 `[practices]` |
| 잠금 파일 | 매니페스트와 잠금 파일이 **같은 커밋에** 들어가야 한다. 설치는 잠금에서만 |
| 계약 변경 | 필드 이름 변경·삭제는 그 계약을 쓰는 단위 담당자의 승인이 추가로 필요하다 (D-100) |
| 컬럼 변경 | 스키마 컬럼을 바꾸는 작업은 U1 담당을 리뷰어로 넣는다 (D-98) |

**"검사가 통과했는가"가 리뷰의 필수 확인 항목인 이유** — 주장이 아니라 확인 가능한 사실이기 때문이다
`[practices]`. 리뷰어가 코드를 어떻게 읽었는지는 사람마다 다르지만, 검사 통과 여부는 같다.

## 4. 파이프라인에서의 비밀값

| 항목 | 설계 | 근거 |
|---|---|---|
| 필요한 비밀값 | **없다** | 기본 실행 경로가 `mock` 이라 파이프라인이 외부 제공자를 부르지 않는다 `[constraint:SC-04]` |
| 네트워크를 타는 시험 | **기본 실행에서 제외한다** | `[practices]` Testing Posture — 제공자가 미정인 동안 키가 필요한 시험을 쓰면 기본 스위트가 실행 불가능해진다 |
| `live` 경로 | 인터페이스 준수 계약 시험만. 실제 호출 없음 | 같음 |
| 나중에 키가 생기면 | 저장소의 비밀값 저장소에 넣고, 그 키를 쓰는 시험은 별도 표시를 달아 기본 실행에서 뺀다 | 3.7 이 등록을 맡는다 |

**지금 파이프라인에 비밀값이 하나도 필요 없다는 것이 이 설계의 성질이다** — 파이프라인이 유출 경로가 되지
않는다.

---

## 5. 되돌리기

배포가 없으므로 되돌리기도 배포 되돌리기가 아니다 `[practices]` Deployment.

| 상황 | 절차 |
|---|---|
| 코드를 되돌린다 | 그 커밋을 되돌리고 다시 올린다 |
| 스키마까지 되돌린다 | 볼륨을 비우고 마이그레이션을 처음부터 적용한 뒤 시드를 다시 넣는다 — 데이터가 전부 합성이라 잃는 것이 없다 |
| 마이그레이션 자체 | **전진 방향만** 쓴다. 되돌리기 스크립트를 만들지 않는다 |

## 6. 시연 릴리스 절차

유일한 릴리스 사건이다 `[practices]` Deployment.

1. `main` 을 태그로 고정한다.
2. 그 태그에서 **새로 clone 한 상태로** 처음부터 한 번 올린다.
3. `docker compose up --build` → 세 컨테이너 + 헬스체크 통과 (AC9.1.1)
4. 헬스체크의 분석 모드가 `mock` 임을 **단언**한다 (AC9.3.4)
5. 새 clone 트리에 실제 값이 든 환경 파일이 **없다**를 확인한다 (AC9.1.4)
6. 합성 대화 3건을 끝까지 돌린다 (D-58)
7. 종단 시험 3건 전체를 돌린다 `[practices]`

**2번이 핵심이다** — 각자 노트북에만 남아 있는 설정에 의존하고 있지 않은지는 이 방법으로만 드러난다.

자리다.

## Assumptions & Open Questions

### 가정

- §2 의 단계 순서가 "빠른 것부터"인 것은 일반적인 실행 시간 감각에 기댄다. 실제로 재 보고 3.7 이 순서를 조정할
  수 있으며, 그것은 이 문서를 어기는 것이 아니다 — 이 문서가 고정하는 것은 항목과 기준이지 순서가 아니다.
- §4 의 "비밀값이 필요 없다"는 기본 실행 경로가 `mock` 이라는 확정 결정 위에 있다. 그 결정이 바뀌면 이 절을
  다시 쓴다.

### 열린 질문

없다. 실행 방법에 관한 결정은 의도적으로 ci-pipeline(3.7)에 남겼으며, 이는 재위임이 아니라 D-56 이 정한 역할
분담이다.
