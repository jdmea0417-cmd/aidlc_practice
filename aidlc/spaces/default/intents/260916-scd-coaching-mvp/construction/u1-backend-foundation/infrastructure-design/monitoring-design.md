**이 문서의 위치** — 앞 단계(`observability-design.md`)가 "무엇을 어떻게 관찰하는가"의 **전략**을 정했다. 이

**정직하게 먼저 적는다** — 이번 범위에는 지표 수집기도, 경보 체계도, 대시보드도 없다 `[design]` §5. 따라서

도구를 적지 않았다.

## 1. 무엇을 보는가 (Metrics & KPIs)

상시 수집기가 없으므로 각 항목은 **확인 시점이 정해진 값**이다.

| Metric | Source | Threshold | Why it matters |
|---|---|---|---|
| 헬스체크 상태 | `GET /api/v1/health` · 컨테이너 상태 | `ok` 가 아니면 이상 | 저장소까지 붙었는지를 알려 주는 **유일한 지점** `[design]` §4 |
| 현재 분석 모드 | 같은 헬스체크 응답 | 시연 리허설에서 `mock` 이어야 함 | 실제 외부 호출로 흐르는 것을 막는 마지막 확인 (AC9.3.4) |
| 세 엔드포인트 응답 시간 | 통합 테스트의 경과 시간 단언 | 200ms (p95) | 저장소 확인 질의가 느려지는 것을 일찍 잡는다 `[nfr]` NFR3.1~3.3 |
| 재기동 후 헬스체크 통과까지 | 리허설에서 잰다 · 컨테이너 헬스체크 재시도 횟수 | 60초 | 컨테이너 헬스체크가 12회(60초) 안에 통과하지 못하면 곧 목표 미달이다 `[Q1]` |
| 연결 수 | 통합 테스트 반복 실행 후 확인 | 늘지 않아야 함 | 연결 풀이 5라 누수가 있으면 빨리 고갈되어 보인다 `[Q3]` |
| 작업 실패 건수 | 로그에서 실패 줄을 센다 | 시연 리허설에서 0 | 전사·분석이 조용히 실패하지 않았는지 `[design]` §3 |

## 2. 무엇이 알려 주는가 (Alerts)

**자동 경보를 두지 않는다** `[design]` §5 — 받을 사람과 절차가 이번 범위에 없다. 그 자리를 대신하는 것을 같은
형식으로 적는다.

| Alert | Condition | Severity | Routes to |
|---|---|---|---|
| 컨테이너가 멈춤 | 컨테이너 상태가 멈춤 | 진행 불가 | 사람 — 화면이 응답하지 않는다. 자동 재시작을 걸지 않았으므로 멈춘 채로 남는다 `[Q2]` |
| 헬스체크 실패 지속 | 12회 재시도 후에도 통과 못 함 | 진행 불가 | 사람 — 컨테이너가 비정상으로 표시된다 |
| 기동 거부 | `live` 인데 키 없음 | 진행 불가 | 사람 — 컨테이너가 뜨지 않고 로그에 어떤 키가 없는지 남는다 `[nfr]` NFR5.2 |
| 작업 실패 | 전사·분석 실패 | 사용자에게 보임 | 화면의 실패 표시 + 로그 `[design]` §3 |
| 응답 시간 초과 | 통합 테스트 단언 실패 | 병합 차단 | GitHub Actions 검사 — `cicd-pipeline.md` |

**"경보를 두지 않는다"가 무책임한 선택이 아닌 이유**: 위 다섯 중 셋은 **컨테이너가 멈추거나 안 뜨는 것**이라
사람이 즉시 안다. 넷째는 화면에 뜬다. 다섯째는 병합을 막는다. 상시 감시가 메울 빈자리가 실질적으로 없다.

## 3. 목표와 측정 (SLIs / SLOs)

| SLI | SLO target | Measurement window |
|---|---|---|
| 세 엔드포인트 응답 시간 | 200ms (p95) | 통합 테스트 1회 실행 |
| 재기동 → 헬스체크 통과 | 60초 이내 | 리허설 1회 |
| 합성 대화 3건 종단 통과 | 3건 모두 끊김 없음 | 리허설 1회 (D-58) |

**가동률 목표(SLO)는 두지 않는다** `[design]` — 상시 떠 있어야 하는 대상이 아니고, 가동률을 잴 기간도 장치도
없다. 위 세 줄이 이번 범위에서 "목표"라 부를 수 있는 전부다.

## 4. 로그와 추적

### 로그 수집

| 항목 | 이 환경에서의 실제 |
|---|---|
| 출력 | 표준 출력 — 앱이 파일·회전·보관 정책을 갖지 않는다 `[design]` §1.1 |
| 보는 방법 | `docker compose logs backend` (특정 요청을 볼 때는 식별자로 거른다) |
| 보관 | 컨테이너 수명 동안. 컨테이너를 내리면 사라진다 |
| 형식 | 한 줄에 한 건, 필드 여섯 개 `[design]` §1 |
| 중앙 수집 | 없음 — 각자 자기 노트북에서 본다 |

**보관이 컨테이너 수명이라는 것의 대가**: 시연 뒤에 그날 로그를 되짚어 볼 수 없다. 받아들이는 근거는 리허설이
시연 전에 같은 경로를 돌아 보므로, 확인이 필요한 시점이 시연 **전**이라는 것이다 `[practices]` Deployment.

### 추적

분산 추적을 두지 않는다 `[design]` §5 — 서비스가 하나다. 그 자리를 **두 식별자**가 대신한다.

| 잇고 싶은 것 | 어떻게 잇는가 |
|---|---|
| 한 요청 안의 모든 로그 | 요청 식별자로 거른다 |
| 요청 → 그 뒤에 도는 작업 | 작업 로그가 원래 요청의 식별자를 함께 담는다 `[design]` §1.2 |
| 한 작업의 모든 줄 | 작업 식별자로 거른다 |
| 사용자가 본 오류 → 로그 | 오류 봉투의 식별자가 같은 값이다 `[nfr]` NFR12.5 |

네 가지 모두 `docker compose logs` 에 문자열 거르기 하나로 된다. 도구가 필요 없다.

### 대시보드

두지 않는다. **헬스체크 응답 하나가 이번 범위의 상태판**이다 — 정상 여부와 분석 모드 두 가지를 한 번에 알려
준다 `[design]` §4.

## 5. 시연 리허설에서 확인하는 것

관찰 가능성이 실제로 값을 내는 유일한 순간이다 `[practices]` Deployment.

1. 새로 받은 트리에서 `docker compose up --build` → 세 컨테이너가 뜨고 헬스체크 통과 (AC9.1.1)
2. 헬스체크 응답의 분석 모드가 `mock` 임을 **단언**한다 — 눈으로 보지 않는다 (AC9.3.4)
3. 새 트리에 실제 값이 든 환경 파일이 **없다**를 확인한다 (AC9.1.4)
4. 합성 대화 3건을 끝까지 돌린다 (D-58)
5. 그동안 로그에 **작업 실패 줄이 없는지** 확인한다

다섯 항목 모두 명령이나 단언으로 확인된다 — 사람의 인상에 기대는 항목이 없다.

## Assumptions & Open Questions

### 가정

- "경보가 메울 빈자리가 없다"는 판단은 사람이 옆에 있는 로컬 환경을 전제로 한다. 무인으로 도는 상황이 생기면
  §2 를 다시 본다.
- 로그 보관이 컨테이너 수명이라는 것을 받아들인 근거는 확인 시점이 시연 전이라는 것이다. 시연 중 문제를 사후
  분석해야 한다면 그때는 로그를 따로 저장해야 한다.
