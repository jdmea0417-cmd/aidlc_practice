## Q1. 저장소가 아직 안 떴을 때 백엔드를 어떻게 다룹니까? (OQ-F3 · OQ-N4)

앞 단계들은 "떠 있되 헬스체크만 실패"를 전제로 썼습니다 `[design]` reliability-design.md §5. 다만 그것을 확정한
적이 없고, 컨테이너 헬스체크의 **주기와 재시도 횟수**도 정해지지 않았습니다. `docker compose up --build` 한 번으로
세 컨테이너가 뜨고 헬스체크가 통과해야 합니다(AC9.1.1).

- A. **저장소가 준비될 때까지 backend 를 시작하지 않는다** — 컨테이너 의존 선언으로 저장소가 준비된 뒤 backend 를
  띄운다. 뜬 순간부터 정상이라 헬스체크 실패 구간이 없다. 대신 저장소가 영영 안 뜨면 backend 는 시작조차 안 해
  로그가 없고, 원인을 저장소 쪽에서 찾아야 한다
- B. **backend 는 바로 뜨고, 저장소가 붙기 전까지 헬스체크만 실패한다** — 앞 단계들이 전제한 모양이다. backend 의
  기동 로그가 바로 남아 무엇이 문제인지 보인다. 컨테이너 헬스체크가 몇 초 간격으로 재시도하다 통과한다. 대신
  "떴는데 아직 못 쓰는" 구간이 잠깐 존재한다
- C. **둘 다** — 의존 선언으로 순서를 주되 저장소 준비를 기다리지는 않고, 헬스체크 재시도로 흡수한다. 실질적으로
  B 에 순서 힌트만 더한 것이다
- X. Other (please specify)

**함께 정할 것**: 고른 방식에서 컨테이너 헬스체크의 **주기와 재시도 횟수**. 답에 함께 적어 주시거나, 제 제안
(5초 간격, 12회 재시도 = 최대 60초 대기 — 재기동 목표 NFR10.1 과 같은 값)을 그대로 쓰셔도 됩니다.

[Answer]: B. **backend 는 바로 뜨고, 저장소가 붙기 전까지 헬스체크만 실패한다** — 앞 단계들이 전제한 모양이다. backend 의 기동 로그가 바로 남아 무엇이 문제인지 보인다. 컨테이너 헬스체크는 **5초 간격, 12회 재시도(최대 60초 대기)** 로 둔다 — 재기동 목표 NFR10.1 과 같은 값이다

## Q2. 컨테이너 자동 재시작을 켭니까? (OQ-D1)

앞 단계는 **두지 않기로** 했습니다 — 사람이 옆에 있는 로컬 환경에서 자동 재시작은 실패를 숨기고 반복을 알아채기
어렵게 한다는 이유입니다 `[design]` reliability-design.md §6. 다만 "시연 당일에만 켜는 선택지"를 이 단계로
넘겼습니다.

- A. **켜지 않는다 (앞 단계 결정 유지)** — 죽으면 멈춘 채로 둔다. 멈춘 컨테이너 자체가 신호다. 시연 당일에도
  같다 — 리허설로 미리 확인하는 쪽에 기댄다
- B. **저장소만 켠다** — 저장소는 죽어도 원인이 보통 자원 문제이고 다시 뜨면 상태가 보존된다. backend 는 켜지
  않아 애플리케이션 오류가 숨지 않는다. 두 컨테이너의 정책이 달라 설명이 한 줄 필요하다
- C. **시연용 설정을 따로 둔다** — 평소 구성에는 안 켜고, 시연 때 쓰는 별도 구성 파일에서만 켠다. 원하는 것을
  정확히 얻지만 구성 파일이 둘이 되고, 시연 당일 쓰는 것이 평소 검증한 것과 달라진다
- X. Other (please specify)

[Answer]: A. **켜지 않는다 (앞 단계 결정 유지)** — 죽으면 멈춘 채로 둔다. 멈춘 컨테이너 자체가 신호다. 시연 당일에도 같다 — 리허설로 미리 확인하는 쪽에 기댄다

## Q3. 연결 풀 크기와 컨테이너 자원 한도를 정합니까? (OQ-D2)

앞 단계는 "동시 1명 기준이라 기본값으로 충분하나 함께 확인할 값"으로 넘겼습니다 `[design]`
performance-design.md §3.

- A. **둘 다 정하지 않는다** — 연결 풀은 기본값, 컨테이너 자원 한도는 걸지 않는다. 사용자 5명이 각자 노트북에서
  돌리므로 노트북 사양이 제각각이고, 한도를 걸면 사양이 낮은 쪽에서 오히려 문제가 된다
- B. **연결 풀만 명시한다** — 작은 값(예: 5)으로 명시해 연결 누수가 빨리 드러나게 한다. 자원 한도는 걸지 않는다.
  누수가 있으면 로컬에서도 금방 고갈되어 보인다
- C. **둘 다 명시한다** — 연결 풀과 컨테이너 메모리·CPU 한도를 모두 적는다. 환경이 균일해지지만, 노트북 사양
  차이 때문에 누군가는 한도 때문에 느려지고 그 원인을 찾기 어렵다
- X. Other (please specify)

[Answer]: B. **연결 풀만 명시한다** — 작은 값(5)으로 명시해 연결 누수가 빨리 드러나게 한다. 자원 한도는 걸지 않는다. 누수가 있으면 로컬에서도 금방 고갈되어 보인다

## Q4. 이 단계가 만드는 파이프라인 문서는 무엇을 담습니까?

이 단계의 산출물에 `cicd-pipeline.md` 가 있습니다. 그런데 **GitHub Actions 워크플로 자체는 ci-pipeline(3.7)이
만든다**고 이미 정해져 있습니다(D-56). 두 단계가 같은 것을 두 번 만들지 않도록 이 문서의 역할을 정해야 합니다.

- A. **요구 명세로 둔다** — "파이프라인이 무엇을 검사해야 하는가"(단계 목록, 각 단계의 통과 기준, 병합 차단
  조건)를 적고, 실제 워크플로 파일은 3.7 이 이 문서를 읽고 만든다. 두 단계의 역할이 겹치지 않는다
- B. **초안 워크플로까지 적는다** — 실제 설정 파일 초안을 여기 넣고 3.7 이 다듬는다. 3.7 이 할 일이 줄지만,
  이 단계의 제약(구현 코드 금지)과 부딪히고 두 문서가 어긋날 자리가 생긴다
- C. **로컬 검사만 적고 원격 파이프라인은 3.7 에 전부 맡긴다** — 이 문서는 `check.sh` 같은 로컬 확인 수단만
  다룬다. 겹침이 가장 적지만, 3.7 이 참고할 요구가 문서로 남지 않는다
- X. Other (please specify)

[Answer]: A. **요구 명세로 둔다** — "파이프라인이 무엇을 검사해야 하는가"(단계 목록, 각 단계의 통과 기준, 병합 차단 조건)를 적고, 실제 워크플로 파일은 3.7 이 이 문서를 읽고 만든다. 두 단계의 역할이 겹치지 않는다
