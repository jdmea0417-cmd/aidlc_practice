## 1. Deployment

| Facet | Choice | Rationale |
|---|---|---|
| 컴퓨트 모델 | 컨테이너 3개 — frontend, backend, postgres | `[constraint:TC-04]`, `[nfr]` NFR10.6. 한 명령으로 전부 뜨는 것이 수용 기준이다(AC9.1.1) |
| 실행 위치 | 개발자 각자의 노트북. 공유 서버 없음 | 5인이 각자 환경을 올린다 `[constraint:OC-03]`. 이것이 이 프로젝트의 실질적 격리 장치다 `[design]` logical-components.md §1 |
| 네트워크 | Compose 기본 네트워크 하나. 외부로 여는 것은 frontend 와 backend 의 포트뿐 | 로컬 전용이라 분리할 신뢰 구역이 없다. postgres 포트는 호스트로 열지 않는다 |
| 기동 순서 | backend 는 **바로 뜨고** 저장소가 붙기 전까지 헬스체크만 실패한다 `[Q1]` | backend 기동 로그가 바로 남아 무엇이 문제인지 보인다. OQ-F3·OQ-N4 를 이 답이 닫는다 |
| 컨테이너 헬스체크 | **5초 간격, 12회 재시도, 한 번당 제한 3초, 시작 유예 0초** `[Q1]` | 재기동 목표(NFR10.1)와 같은 60초에 맞췄다 — 통과하지 못하면 목표도 못 지킨 것이다. 한 번당 제한 3초는 앱이 저장소에 거는 1초 제한(NFR10.15)보다 크게 두어, 앱이 "정상 아님"이라고 **답할 시간**을 남긴다(제한이 1초 이하이면 앱의 응답 대신 시간 초과가 먼저 난다). 시작 유예를 0으로 둔 것은 실패 구간을 감추지 않기 위해서다 — backend 가 먼저 뜨는 것이 이 구성의 의도다 |
| 자동 재시작 | **걸지 않는다** `[Q2]` | 사람이 옆에 있는 환경에서 자동 재시작은 실패를 숨긴다. 멈춘 컨테이너 자체가 신호다 `[design]` reliability-design.md §6. OQ-D1 을 이 답이 닫는다 |
| 자원 한도 | **걸지 않는다** `[Q3]` | 노트북 사양이 제각각이라 한도가 사양 낮은 쪽에서 오히려 문제를 만든다. OQ-D2 의 절반을 이 답이 닫는다 |
| 환경 구분 | 없음 — 로컬 하나뿐 | staging/production 이 존재하지 않는다 `[practices]` Deployment. "환경 승격"은 이번 범위에 없다 |
| 인프라 정의 방식 | `docker-compose.yml` 하나. 별도 인프라 코드 도구 없음 | 대상이 컨테이너 셋이다. 도구를 늘릴 이유가 없다 |
| 스키마 적용 | 기동 흐름 밖의 **별도 명령** (`scripts/migrate.sh`) | `[spec]` W1. 기동마다 적용하면 컨테이너 동시 기동 시 경쟁이 생긴다 |

### 2.1 연결 풀 5 가 실제 동시 사용 패턴을 덮는가

풀 크기를 "작으면 누수가 빨리 드러난다"는 이유만으로 정하면 반대 방향(정상 동작이 고갈되는 것)을 놓친다.
이 단위의 설계가 실제로 몇 개의 연결을 동시에 쓰는지 세어 본다. 셋을 세는 근거는
`../nfr-design/reliability-design.md` §2 의 작업 단위 장치 흐름이다 `[nfr]` NFR10.13·NFR10.14.

| 동시에 열릴 수 있는 연결 | 언제 | 개수 |
|---|---|---|
| 요청 경로의 연결 | 사용자가 화면에서 무언가 할 때마다 1개 | 1 |
| 상태 조회의 연결 | 화면이 1초 간격으로 상태를 조회한다 `[contract]` 공통 규칙 — 앞 요청과 겹치지 않는 짧은 연결 | 1 |
| 응답 이후 작업의 연결 | 전사·분석이 도는 동안 1개 `[nfr]` NFR10.3 | 1 |
| 실패 기록용 별도 연결 | 작업이 실패해 되돌린 **직후에만**, 짧게 1개 `[nfr]` NFR10.14 | 1 |

**한 작업만 볼 때의 상한은 2다.** `../nfr-design/reliability-design.md` §2 의 작업 단위 장치는 **작업 연결을
닫은 뒤에** 실패 기록용 연결을 연다 `[nfr]` NFR10.13·NFR10.14. 따라서 위 표의 3번째와 4번째 줄은 **결코 동시에
열리지 않는다**. 한 대화의 작업 하나만 도는 순간의 최악은 상태 조회(1) + 작업 연결 **또는** 실패 기록 연결(1)
= **2개**다.

**상한이 3이 되려면 서로 다른 두 대화의 작업이 겹쳐야 한다.** 그런 겹침을 막는 규칙은 이 단위의 설계 어디에도
없다 — W5 도 상태 기계도 "한 번에 작업 하나"를 강제하지 않는다. 화면 하나가 요청을 잇따라 보내거나 같은
사용자가 두 화면을 열면 두 작업이 동시에 돌 수 있다. 그 경우의 최악은 상태 조회(1) + 첫 작업의 연결(1) +
둘째 작업의 연결(1) = **3개**다.

**따라서 이 절이 쓰는 상한은 3이며, 그 3은 "동시에 도는 작업 2개"를 전제한 보수적 값이다.** 한 작업만 도는
실제 기본 경로에서는 2다. 아래 판단은 더 큰 쪽인 3을 기준으로 한다.

| 판단 | 근거 |
|---|---|
| **5는 상한 3보다 크다 — 유지한다** | 여유 2개가 남는다. 정상 동작이 고갈될 경로가 이 설계에는 없다 |
| 그래도 작다 — 누수 감지 효과는 그대로 | 연결을 닫지 않는 경로가 하나라도 있으면 몇 번의 요청 만에 5를 채워 즉시 드러난다 |
| **5 미만으로 줄이지 않는다** | 3이면 상한과 같아져, 누수가 아니라 정상 동작이 대기하는 순간이 생긴다. 그러면 이 값이 잡으려던 신호와 구분되지 않는다 |

**두 방향을 모두 계산한 결과가 같은 값(5)이라는 점이 이 절의 결론이다.** 처음에는 한쪽(누수 감지)만 보고
정했고, 반대 방향을 세어 본 뒤에도 값이 유지되었다.

**동시에 도는 작업이 늘면 다시 본다**: 한 작업은 어느 순간에도 연결을 1개만 점유하므로(작업 연결과 실패 기록
연결이 겹치지 않는다) 상한은 `1 + 동시에 도는 작업 수` 다. 작업 4개가 동시에 돌면 5에 닿는다. 그 상황이
생기면 그때 조정한다 — 동시 사용자가 1명인 측정 조건 `[nfr]` 아래에서는 작업 2개를 넘길 근거가 없다.

| 합성 대화 픽스처 | u1-backend-foundation | Mock, 백엔드 테스트, 프론트 모의 응답, 종단 시험 | 단일 출처 `[nfr]` NFR14.1 |

U1 담당이 리뷰어), 이 문서는 소유를 표로 고정만 한다.

## 4. 비밀값 취급

| 항목 | 설계 | 근거 |

## Assumptions & Open Questions

### 가정

- 헬스체크 12회 재시도가 첫 기동(캐시 있는 경우)을 덮는다는 것은 로컬 컨테이너 기동이 대체로 수십 초 안에
  끝난다는 전제에서 나왔다. 첫 빌드는 목표를 두지 않았으므로 `[nfr]` NFR10.1 이 값과 무관하다.
- 연결 풀 5가 충분하다는 것은 §2.1 에서 동시 점유 상한을 3으로 센 계산에 기댄다. 그 3은 **동시에 도는 작업이 2개까지**라는 보수적 전제 위에 있다(한 작업만 돌면 2다). 동시 사용자 1명이라는 측정 조건 아래에서 작업 2개를 넘길 경로는 보이지 않으나, 겹침을 금지하는 규칙이 설계에 있는 것은 아니다.
- 헬스체크 한 번당 제한 3초는 앱의 1초 질의 제한에 여유를 더한 값이다. 실측 근거가 아니라 두 값의 순서(앱이 먼저 답한다)를 지키는 최소 여유다.

### 열린 질문

없다. **이 단계로 넘어온 열린 질문 네 개(OQ-F3, OQ-N4, OQ-D1, OQ-D2)는 모두 이 문서에서 닫혔다.**
