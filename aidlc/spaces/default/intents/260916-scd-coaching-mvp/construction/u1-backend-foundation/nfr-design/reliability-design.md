## 1. 실패가 사라질 수 있는 자리를 세어 본다

```
요청 --> 접수 응답(202) --> [요청 문맥 종료]
                                |
                          작업 시작
                                |
                    +-----------+-----------+
                    |                       |
              작업이 성공                작업이 실패
                    |                       |
              상태를 완료로            (A) 상태를 실패로 적어야 한다
                                            |
                                     되돌림이 일어나면
                                            |
                                     (B) 그 기록도 함께 사라진다
```

<!-- Text fallback: 요청은 접수 응답을 내고 끝나고 요청 문맥이 종료된다. 이후 작업이 시작되어 성공하면 상태를 완료로 적는다. 실패하면 상태를 실패로 적어야 하는데(A), 트랜잭션 되돌림이 일어나면 그 기록도 함께 사라진다(B). -->

(A)와 (B)가 이번 범위에서 실패가 조용히 사라지는 두 자리다. §2 의 작업 단위 장치가 둘 다 막는다.

## 2. 작업 단위 장치 — 실패 기록이 빠질 수 없는 구조

`[spec]` W5 가 흐름을 정했고, 요구사항이 "한 장치가 맡는다"를 정했다 `[nfr]` NFR10.14. 설계는 그 장치의 모양을
정한다.

```
작업 시작
   |
   +-- 자기 작업 식별자 발급, 요청 식별자와 함께 문맥에 담기
   |
   +-- [작업 단위 장치 열기]  <- 여기서 연결을 새로 연다 (요청 연결을 쓰지 않는다)
   |        |
   |        +-- 작업 내용 수행
   |        |
   |        +-- 성공 --> 한 번 확정 --> 닫기
   |        |
   |        +-- 예외 --> 되돌리기 --> 닫기
   |                        |
   |                        +-- [별도 연결을 새로 열어] 상태를 실패로 적고 확정 --> 닫기
   |
   +-- 어느 경로든 로그를 남긴다 (컴포넌트 + 두 식별자)
```

<!-- Text fallback: 작업이 시작되면 자기 식별자를 발급해 요청 식별자와 함께 문맥에 담는다. 작업 단위 장치를 열어 연결을 새로 얻고(요청 연결을 쓰지 않는다) 작업을 수행한다. 성공하면 한 번 확정하고 닫는다. 예외가 나면 되돌리고 닫은 뒤, 별도 연결을 새로 열어 상태를 실패로 적고 확정한 뒤 닫는다. 어느 경로든 컴포넌트와 두 식별자가 붙은 로그를 남긴다. -->

| 설계 결정 | 무엇을 구조적으로 막는가 | 요구사항 |
|---|---|---|
| 장치가 **연결을 직접 연다** — 작업 함수가 연결을 인자로 받지 않는다 | 요청 연결이 실수로 흘러들어오는 일 `[contract]` 공통 규칙 | NFR10.3 |
| 성공 경로의 **확정이 장치 안에 있다** | 작업마다 확정을 빠뜨리거나 두 번 하는 일 | NFR10.14, `[rules]` BR5.3 |
| 실패 기록이 **별도 연결**에서 일어난다 | 되돌림과 함께 실패 기록이 사라지는 일 (§1 의 B) | NFR10.14 |
| 실패 기록 자체가 실패하면 **로그에 남기고 넘어간다**(다시 되돌리지 않는다) | 실패 기록 실패가 무한 되돌림이 되는 일 | — (이 단계가 새로 정함) |
| 닫기가 **어느 경로에서든** 일어난다 | 연결 누수 | NFR10.3 |

마지막에서 둘째 줄은 이 단계가 새로 정한 것이다. 요구사항은 "별도 연결로 적는다"까지만 정했고, **그 기록마저
실패하면 어떻게 하는가**는 비어 있었다. 무한히 되돌리는 대신 로그에 남기고 넘어간다 — 그러면 상태는 진행 중으로
남지만, 로그에는 실패가 남아 사람이 도달할 수 있다.

## 3. 외부 호출의 저항 설계

요구사항이 값을 정했다(연결 5초 / 읽기 60초 / 재시도 1회) `[nfr]` NFR13.3·NFR13.4. 설계는 **그 값들이 어떻게
맞물리는가**를 정한다.

### 3.1 최악의 경우 얼마나 기다리는가

| 경우 | 최대 대기 | 계산 |
|---|---|---|
| 연결이 안 됨 → 재시도 → 또 안 됨 | **약 10초** | 5 + 5 |
| 연결은 되고 응답이 안 옴 → 재시도 → 또 안 옴 | **약 130초** | (5+60) × 2 |
| 4xx 응답 | **즉시** | 재시도하지 않는다 |

130초는 짧지 않다. 그러나 이 경로는 **응답 이후에 도는 작업** 안에서만 일어나므로(`[spec]` W5) 사용자의 화면이
그동안 멈추지 않는다 — 화면은 1초 간격으로 상태를 조회하고 있고 `[contract]` 공통 규칙, 작업이 끝나면 실패
상태를 본다. **이 구조가 긴 타임아웃을 감당 가능하게 만든다.**

### 3.2 회로 차단기를 두지 않는 이유

일반적인 저항 설계는 반복 실패 시 호출을 끊는 장치를 둔다. 이번 범위에는 두지 않는다.

| 근거 |
|---|
| 기본 실행 경로가 Mock 이라 외부 호출이 아예 일어나지 않는다 `[nfr]` NFR5.1 |
| 사용자 5명 로컬이라 반복 실패가 자원을 고갈시킬 규모가 아니다 |
| 제공자가 미정이라 차단 기준(몇 번 실패에 몇 초 끊을지)을 정할 근거가 없다 `[raid:D2]` |
| 재시도 1회 상한이 이미 폭주를 막는다 |

**나중에 필요해지면 어디에 붙이는가**: §2 의 공용 감싸기 장치 하나에 붙인다(`security-design.md` §2). 모든 호출이
그 자리를 지나므로 한 곳만 고치면 된다 — 지금 그 장치를 두는 두 번째 이유가 이것이다.

## 4. 실패 사유가 회복 경로를 고른다

`[rules]` BR7.5 가 규칙을 정했다. 설계는 그 갈림이 어디서 일어나는지를 정한다.

```
전사 실패
   |
   +-- 사유를 상태와 함께 적는다 (STORAGE / TRANSCRIPTION)
   |
[사용자가 다시 시도]
   |
   +-- 재시도 경로가 사유를 읽는다
   |     |
   |     +-- STORAGE        --> 저장부터 다시 (상태: UPLOADING)
   |     +-- TRANSCRIPTION  --> 전사만 다시 (상태: TRANSCRIBING)
```

<!-- Text fallback: 전사가 실패하면 사유를 상태와 함께 적는다. 사용자가 다시 시도하면 재시도 경로가 그 사유를 읽어, STORAGE 면 저장부터 다시 하고 상태를 UPLOADING 으로, TRANSCRIPTION 이면 전사만 다시 하고 상태를 TRANSCRIBING 으로 만든다. -->

| 설계 결정 | 근거 |
|---|---|
| 사유를 **상태와 같은 트랜잭션에서** 적는다 | 상태는 실패인데 사유가 없는 순간이 생기지 않는다 |
| 갈림이 **재시도 경로 한 곳**에서 일어난다 | 호출하는 쪽이 사유를 해석할 필요가 없다 |
| 사유는 **응답에 싣지 않는다** | 내부 회복 경로용 값이다 `[nfr]` NFR12.1 의 정신, `entities.md` §4 |

U1 은 이 구조와 값의 목록을 만들고, 실제 전사·재시도 코드는 u3-f01-capture 가 쓴다.

## 5. 기동 실패는 조용하지 않다

| 실패 | 설계된 행동 | 근거 |
|---|---|---|
| 설정이 모르는 값 | mock 으로 뜨되 **그 사실을 로그에 남긴다** | `[rules]` BR1.1, NFR5.4 |
| `live` 인데 키 없음 | **기동 중단** + 어떤 키가 없는지 로그 | `[rules]` BR1.2, NFR5.4 |
| 스키마 미적용 | 기동은 되지만 첫 저장소 접근에서 실패한다 | `[spec]` W1 — 스키마 적용은 기동 밖 단계다 |
| 저장소 미기동 | 헬스체크가 통과하지 않는다 | `[rules]` BR3.1, NFR10.5 |

세 번째 줄이 이번 설계에서 드러난 자리다 — 스키마를 기동 흐름에서 뺀 대가로, **스키마가 없는 상태로 뜰 수 있다.**
이것을 받아들이는 근거: 헬스체크의 저장소 확인 질의가 스키마 없이도 성공할 수 있으므로 헬스체크로는 안 잡히지만,
첫 실제 요청에서 즉시 드러나고 로컬 환경에서는 그 시차가 짧다. 기동 때마다 마이그레이션을 도는 대안이 만드는
문제(컨테이너 동시 기동 시 경쟁)가 더 크다 `[spec]` W1.

## 6. 자동 재시작을 두지 않는 설계

| 설계 결정 | 근거 |
|---|---|
| 컨테이너 자동 재시작 정책을 걸지 않는다 | 사람이 옆에 있는 로컬 환경에서 자동 재시작은 실패를 숨기고 반복을 알아채기 어렵게 한다 `[nfr]` |
| 프로세스가 죽으면 멈춘 채로 둔다 | 멈춘 컨테이너 자체가 신호다 |

이것은 **되돌릴 수 있는 결정**이다. 시연 당일에만 재시작 정책을 켜는 선택지가 남아 있고, 그 판단은 인프라
설계(3.4)가 컨테이너 구성을 정할 때 함께 본다.
