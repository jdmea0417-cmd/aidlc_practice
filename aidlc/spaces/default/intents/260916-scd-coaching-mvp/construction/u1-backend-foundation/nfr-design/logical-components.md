**이 문서가 하는 일** — 앞의 다섯 설계 문서가 정한 장치들을 **하나의 배치도로 모으고**, 인프라 설계(3.4)가 받을
수 있는 형태로 넘긴다. 실행 단위·장애 도메인·공유 자원이 어디인지가 이 문서의 내용이다.

**플랫폼 관점에 대한 참고** — 이 단계를 함께 본 플랫폼 지식은 클라우드 서비스를 전제로 한다(가상 네트워크,
관리형 서비스, 자동 확장, 비용 최적화). 이 프로젝트는 클라우드 배포가 없으므로 `[constraint:SC-01]` 그중
적용되는 것만 옮겼다 — 컨테이너 점검 항목, 상태 확인 지점, 환경 전략의 로컬 부분이다. 적용되지 않는 부분을
억지로 대응시키지 않았다.

## 1. 실행 단위와 장애 도메인

```
+-------------------- 개발자 노트북 (Docker Compose) --------------------+
|                                                                        |
|  +----------------+      +----------------+      +----------------+    |
|  |  frontend      |      |  backend       |      |  postgres      |    |
|  |  (u2 소유)      |----->|  (U1 이 만듦)   |----->|                |    |
|  +----------------+      +--------+-------+      +----------------+    |
|                                   |                                    |
|                                   v                                    |
|                          +----------------+                            |
|                          |  파일 볼륨      |                            |
|                          |  (음성 저장)    |                            |
|                          +----------------+                            |
+------------------------------------|-----------------------------------+
                                     |  live 에서만
                                     v
                          +----------------------+
                          |  외부 STT/LLM 제공자   |
                          +----------------------+
```

### 장애 도메인 네 개

| # | 도메인 | 죽으면 무엇이 멈추는가 | 감지 | 회복 |
|---|---|---|---|---|
| 1 | backend 컨테이너 | 전부 | 화면이 응답하지 않음 · 컨테이너 상태 | 사람이 다시 올린다(자동 재시작 없음) |
| 2 | postgres 컨테이너 | 전부 | **헬스체크가 통과하지 않음** `[rules]` BR3.1 | 다시 올린다. 볼륨이 남아 상태 보존 |
| 3 | 파일 볼륨 | 음성 저장·읽기 | 전사 실패, 사유 `STORAGE` `[rules]` BR7.5 | 사유별 재시도 경로(`reliability-design.md` §4) |
| 4 | 외부 제공자 | `live` 에서만, 전사·분석 | 타임아웃 후 앱 오류 | 재시도 1회 후 실패 상태 |

**기본 실행 경로에서 도메인 4는 존재하지 않는다** — `mock` 이면 외부로 나가는 객체 자체가 없다
(`security-design.md` §1). 이것이 이 배치도에서 가장 중요한 성질이다.

### 폭발 반경

| 무엇이 실패하면 | 어디까지 영향이 가는가 |
|---|---|
| 한 대화의 전사 | 그 대화만. 다른 대화와 다른 사용자에게 영향 없음 |
| 저장소 | 전부 — 단일 저장소다. 이번 범위에서 받아들인 것이다 `[nfr]` |
| backend 프로세스 | 전부 — 단일 프로세스다. 같음 |
| 한 개발자의 환경 | 그 사람만. 5인이 각자 환경을 올린다 `[constraint:OC-03]` |

마지막 줄이 이 프로젝트의 실질적인 격리 장치다 — 환경이 공유되지 않으므로 한 사람의 실패가 남에게 가지 않는다.

## 2. backend 안의 논리 구성

U1 이 만드는 것과 다른 단위가 채울 자리를 구분해 그린다.

```
backend
|
+-- api/            <- 요청 검증, 응답 모델, 오류 봉투로의 번역
|     +-- (U1) 헬스체크, 현재 사용자, 동의
|     +-- (기능 단위들이 자기 경로를 더한다)
|
+-- service/        <- 업무 규칙, 확정은 여기 경계에서 한 번
|     +-- ports.py  <- (U1) 제공자 인터페이스 — 구현과 분리
|     +-- (기능 단위들이 자기 유스케이스를 더한다)
|
+-- repository/     <- 저장소 접근
|     +-- (U1) 모델 20개, 초기 리비전
|     +-- (기능 단위들이 자기 질의를 더한다)
|
+-- providers/      <- (U1) Mock 구현 + live 자리 + 공용 호출 감싸기
|
+-- common/         <- (U1) 이 단위가 만드는 공통 장치들
      +-- 설정 객체 (평면 + 접두사 규칙)
      +-- 로깅 (컴포넌트 + 두 식별자)
      +-- 요청 식별자 미들웨어
      +-- 예외 정의와 공통 예외 처리기
      +-- 작업 단위 장치 (연결 수명 + 실패 기록)
```

U1 은 common 과 providers 전부, 그리고 나머지 세 구역의 기반을 만든다. -->

### U1 이 만드는 공통 장치 다섯

| 장치 | 무엇을 지키는가 | 어느 설계 문서 |
|---|---|---|
| 설정 객체 | 기동 시 한 번 결정, 실행 중 불변 | `security-design.md` §1 |
| 로깅 | 여섯 필드, 두 식별자 자동 부착 | `observability-design.md` §1 |
| 요청 식별자 미들웨어 | 요청·응답·로그가 같은 값을 공유 | `observability-design.md` §1.2 |
| 공통 예외 처리기 | 내부 정보 비노출, 한국어 기본 메시지, `details` 규칙 | `security-design.md` §4.1 |
| 작업 단위 장치 | 연결 수명 + 실패가 반드시 기록됨 | `reliability-design.md` §2 |
| 공용 호출 감싸기 | 타임아웃·재시도·시간 측정·로그 | `security-design.md` §2 |

**여섯 장치 전부가 "규칙을 사람이 아니라 구조가 지키게" 하려고 존재한다.** 기능 단위 13개가 각자 같은 규칙을
지키려 애쓰는 대신, 장치를 지나기만 하면 지켜진다.

## 3. 공유 자원과 그 소유

| 자원 | 소유 | 다른 단위가 쓰는 방법 | 제약 |
|---|---|---|---|
| 초기 스키마 (테이블 20개) | U1 | 자기 테이블의 컬럼을 새 리비전으로 더한다 | 병합된 리비전은 수정 금지 `[contract]` C15 |
| 시드 상태 | U1(앞 3개) + 갈래 4(뒤 6개) | 이름으로 지정해 넣는다 | 값은 픽스처에서 읽고 다시 적지 않는다 `[contract]` C16 |
| 합성 대화 픽스처 | U1 | Mock·단위 테스트·프론트 모의 응답·종단 시험이 모두 읽는다 | 단일 출처 `[nfr]` NFR14.1 |
| 제공자 인터페이스 | U1 | `service/ports.py` 를 통해서만 참조 | 구현체를 직접 import 하지 않는다 `[contract]` C14 |
| 공통 장치 여섯 | U1 | import 해서 쓴다 | 우회하는 경로를 만들지 않는다 (§2) |
| 파일 볼륨 | U1 이 경로 규칙, u3 이 내용 | 설정값 경로를 통해서만 | 저장소 밖으로 나가지 않는다 |

**충돌이 생길 자리** — 초기 스키마와 시드는 여러 단위가 같은 파일을 만진다 `[contract]` C15·C16. 그 규칙은
이미 계약이 정했고(리비전 갈라지면 병합, 컬럼 추가 시 U1 담당이 리뷰어), 이 문서는 그 자리를 표시만 한다.

## 4. 인프라 설계(3.4)에 넘기는 것

이 문서가 정하지 않고 다음 단계로 넘기는 항목이다. 각각 **왜 여기서 정하지 않았는지**를 적는다.

| 항목 | 왜 여기가 아닌가 |
|---|---|
| 컨테이너 기동 순서와 의존 선언 | 컨테이너 구성의 값이다. 이 문서는 "저장소가 안 뜨면 헬스체크가 실패한다"까지만 정했다 (OQ-F3, OQ-N4) |
| 컨테이너 헬스체크의 주기·재시도 횟수 | 같음. 앱이 거는 1초 시간 제한과는 독립이다 `[nfr]` NFR10.15 |
| 자동 재시작 정책 | 지금은 두지 않기로 했으나 시연 당일만 켜는 선택지가 남아 있다 (OQ-D1) |
| 연결 풀 크기, 컨테이너 자원 한도 | 동시 1명 기준이라 기본값으로 충분하나 함께 확인할 값이다 (OQ-D2) |
| 볼륨 구성과 무시 규칙 | 저장 경로가 설정값이라는 것까지가 이 문서의 몫이다 |
| 이미지 구성(기반 이미지, 다단계 빌드, 비루트 사용자) | 컨테이너 점검 항목이며 이 문서는 논리 배치만 다룬다 |

## 5. 이 배치가 나중에 무엇을 허용하는가

| 나중의 변화 | 지금 배치가 허용하는가 | 근거 |
|---|---|---|
| 프로세스를 여러 개 띄우기 | **조건부** — 무상태는 확보했으나 응답 이후 작업의 중복 실행 장치가 필요하다 | `scalability-design.md` §5 |
| 저장소를 외부로 옮기기 | 허용 — 연결 설정이 설정값이다 | §3 |
| 파일 저장소를 공유 저장소로 | 허용 — 경로가 설정값이고 구현 교체 지점이 분리되어 있다 | §3 |
| 인증을 넣기 | 허용 — 현재 사용자 결정 지점이 한 곳이다 | `security-design.md` §6 |
| 제공자를 바꾸기 | 허용 — 인터페이스와 감싸기 장치가 분리되어 있다 | `security-design.md` §2 |
| 회로 차단기·빈도 제한 추가 | 허용 — 모든 호출이 감싸기 장치를 지난다 | `reliability-design.md` §3.2 |

**여섯 중 다섯이 "허용"이고 그 이유가 모두 같다** — 바뀔 수 있는 것을 설정값이나 장치 뒤에 두었기 때문이다.

## Assumptions & Open Questions

### 가정

- §1 의 장애 도메인 네 개는 이번 범위의 배포 형태(로컬 3 컨테이너)를 전제로 한다. 배포 형태가 바뀌면 다시 센다.
- §5 의 "허용" 판정은 구조가 막지 않는다는 뜻이지, 그 변화가 공짜라는 뜻이 아니다.

### 열린 질문

§4 의 여섯 항목이 그대로 인프라 설계(3.4)로 넘어간다. 그중 OQ-D1(자동 재시작)과 OQ-D2(연결 풀·자원 한도)는 이
단계가 새로 연 것이고, OQ-F3·OQ-N4 는 앞 단계에서 넘어온 것이다.
