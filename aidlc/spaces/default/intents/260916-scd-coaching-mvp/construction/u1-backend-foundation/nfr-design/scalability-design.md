## 1. 이 문서가 설계하는 것

요구사항 문서가 **확장성 목표를 두지 않기로** 했다 `[nfr]`. 따라서 이 문서는 확장 구조를 설계하지 않는다.
설계하는 것은 하나다 — **나중에 확장이 필요해졌을 때 다시 쓰지 않아도 되는 성질을, 지금 비용 없이 확보하는 것.**

요구사항이 그 성질 셋을 정했다(NFR10.2 무상태, NFR10.3 연결 수명, NFR10.4 비차단). 이 문서는 각각이 **어느
구조로** 확보되는지를 적는다.

## 2. 무상태 (NFR10.2)

```
요청 A --+
         |--> [backend 프로세스] --> 저장소 (모든 상태가 여기 있다)
요청 B --+          |
                    +-- 프로세스 안에 요청 사이를 잇는 값이 없다
```

<!-- Text fallback: 여러 요청이 같은 backend 프로세스를 지나지만, 프로세스 안에는 요청 사이를 잇는 값이 없다. 모든 상태는 저장소에 있다. -->

| 설계 결정 | 근거 |
|---|---|
| 요청 사이를 잇는 값을 프로세스 메모리에 두지 않는다 | 프로세스를 여러 개 띄우는 선택지를 남긴다. 지금도 재시작이 안전해진다 |
| 요청·작업 식별자는 **문맥에 담고 요청이 끝나면 사라진다**(`observability-design.md` §1.2) | 문맥은 요청 수명 안에서만 산다 — 상태가 아니다 |
| 설정 객체는 기동 시 한 번 만들어 **읽기만** 한다 | 읽기 전용 값은 프로세스가 늘어도 문제가 되지 않는다 |
| 프롬프트·픽스처는 읽기 전용으로 불러 둔다 | 같음 |

**예외 하나**: 응답 이후에 도는 작업은 이번 범위에서 같은 프로세스 안에서 돈다 `[spec]` W5. 프로세스를 늘리면
같은 작업이 두 번 돌 수 있다 — 그것이 §5 의 첫 항목이다.

## 3. 연결 수명 (NFR10.3)

`reliability-design.md` §2 의 작업 단위 장치가 이 성질도 함께 확보한다. 같은 장치가 두 가지를 지킨다 —
실패가 기록으로 남는 것(신뢰성)과 연결이 새지 않는 것(확장성).

| 설계 결정 | 근거 |
|---|---|
| 연결을 여는 자리가 **요청 경로의 주입 지점**과 **작업 단위 장치** 둘뿐이다 | 세는 자리를 둘로 제한하면 감사 가능하다 |
| 어느 경로에서든 닫기가 장치 안에서 일어난다 | 예외 경로에서 빠뜨릴 수 없다 |
| 작업 함수가 연결을 인자로 받지 않는다 | 요청 연결이 흘러들어와 수명이 꼬이는 일을 막는다 `[contract]` 공통 규칙 |

## 4. 비차단 (NFR10.4)

```
[요청] --> 검증 --> 작업 예약(식별자만 넘김) --> 접수 응답 202  (여기서 요청 끝)
                          |
                          +--> 작업이 따로 돈다 --> 상태를 갱신
                                                      ^
[화면] --1초 간격 상태 조회----------------------------+
```

<!-- Text fallback: 요청이 오면 검증하고 작업을 예약하며 식별자만 넘긴 뒤 접수 응답 202 를 내고 끝난다. 작업은 따로 돌며 상태를 갱신한다. 화면은 1초 간격으로 상태를 조회해 결과를 본다. -->

| 설계 결정 | 근거 | 요구사항 |
|---|---|---|
| 오래 걸리는 작업(업로드 뒤 전사, 분석, 재분석)은 **접수 응답 + 상태 조회** 모양으로만 한다 | 화면이 멈추지 않는다. 제공자 타임아웃이 130초여도 감당된다(`reliability-design.md` §3.1) | `[contract]` 공통 규칙 (D-96) |
| 예약할 때 **식별자만** 넘긴다 | 열린 연결이나 큰 객체가 작업으로 흘러가지 않는다 | `[rules]` BR5.1 |
| 요청 경로에서 제공자를 부르지 않는다 | 요청 응답 시간이 외부에 좌우되지 않는다 | NFR10.4 |

U1 은 이 모양을 만들어 두고, 실제 전사·분석 작업은 u3·u5 가 채운다.

## 5. 지금 남겨 두는 것 — 확장이 필요해지면 여기부터

요구사항 문서가 인계 메모로 네 항목을 적었다 `[nfr]`. 설계 관점에서 **각각이 지금 어떤 상태로 남아 있는지**를
덧붙인다.

| 순서 | 항목 | 지금 상태 | 확장 시 할 일 |
|---|---|---|---|
| 1 | 응답 이후 작업의 실행 방식 | 같은 프로세스 안에서 돈다 | 프로세스를 늘리면 **같은 작업이 두 번 돌지 않게 하는 장치**가 필요해진다. 작업 예약 지점이 한 곳이라(`[spec]` W5) 그 자리만 바꾸면 된다 |
| 2 | 저장소 연결 수 | 연결 풀 기본값 | 프로세스 수 × 풀 크기가 저장소 한도를 넘지 않게 조정 |
| 3 | 파일 저장소 | 로컬 볼륨, 경로는 설정값 | 경로가 설정값이라 공유 저장소로 바꿀 때 코드 변경이 아니라 설정·구현체 교체가 된다 |
| 4 | 제공자 요청 한도 | 제한 없음 | 공용 감싸기 장치 한 곳에 빈도 제한을 붙인다(`security-design.md` §2) |

**네 항목 중 셋이 "한 자리만 고치면 된다"로 끝난다.** 이것이 지금 공용 장치들을 두는 값이다 — 확장을 위한
설계가 아니라, 확장할 때 흩어진 코드를 찾아다니지 않게 하는 설계다.

## 6. 두지 않는 것

| 항목 | 이유 |
|---|---|
| 자동 확장 규칙·임계값 | 확장 대상이 없다 `[nfr]` |
| 부하 분산 | 프로세스가 하나다 |
| 데이터 분할 | 데이터가 수십 건 규모다 |
| 큐 기반 분리 | 작업 예약이 같은 프로세스 안에서 끝난다. 브로커를 더할 이유가 없다 `[nfr]` |
| 용량 계획 | 재는 대상도 늘어날 근거도 없다 |

## Assumptions & Open Questions

### 가정

- "프로세스를 늘릴 수 있다"는 성질을 지금 확보해 두는 것이 값이 있다는 판단은, 이 프로젝트가 시연 이후에도
  이어질 수 있다는 전제에 기댄다. 시연으로 끝난다면 이 성질들의 값은 재시작 안전성뿐이다 — 그것만으로도 비용
  대비 이득이 있다.

### 열린 질문

없다. 이 문서의 결정은 이번 범위 안에서 닫혀 있다.
