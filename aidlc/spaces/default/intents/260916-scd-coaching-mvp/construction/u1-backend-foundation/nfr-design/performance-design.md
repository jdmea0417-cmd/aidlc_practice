## 1. 200ms 예산을 어디에 쓰는가

세 엔드포인트가 모두 200ms(p95) 목표를 공유한다 `[nfr]` NFR3.1~3.3. 가장 무거운 것은 헬스체크다 — 저장소 확인
질의가 들어 있기 때문이다.

| 구간 | 예상 | 비고 |
|---|---|---|
| 요청 파싱·검증 | 1ms 미만 | 본문이 없거나 작다 |
| 현재 사용자 결정 | 저장소 질의 1회 | 식별자 조회 — 인덱스를 탄다 |
| 업무 처리 | 1ms 미만 | 이 세 경로에는 계산이 없다 |
| 저장소 질의 | 대부분 | 헬스체크는 확인 질의, 동의는 갱신 1회 |
| 응답 직렬화 | 1ms 미만 | 필드가 적다 |

**실질적으로 200ms 는 저장소 왕복 한두 번의 예산이다.** 로컬 컨테이너 사이에서 이것은 넉넉하다. 이 목표를
어기게 만들 수 있는 것은 성능 최적화의 부재가 아니라 **구조적 실수**이며, 아래가 그 목록이다.

---

## 2. 성능이 조용히 나빠지는 네 자리와 그 차단

| # | 어떻게 나빠지는가 | 차단 설계 | 요구사항 |
|---|---|---|---|
| 1 | **N+1 질의** — 객체 관계를 따라가다 질의가 요청당 수십 개로 늘어난다. 로컬에서는 느려도 티가 안 나다가 데이터가 쌓이면 드러난다 | 관계의 기본값을 **즉시 예외로 터지게** 둔다 `[practices]` — 조용한 N+1 대신 즉시 실패가 된다 | NFR3.1~3.3 |
| 2 | **연결 고갈** — 연결을 닫지 않는 경로가 하나라도 있으면 시간이 지나며 느려지다 멈춘다 | 연결 수명을 장치 하나가 맡는다(`reliability-design.md` §2). 작업 함수가 연결을 직접 열지 않는다 | NFR10.3 |
| 3 | **요청 경로에서 외부 호출** — 제공자 호출이 요청 안에서 일어나면 200ms 목표가 130초가 된다 | 오래 걸리는 작업은 **접수 응답 후 별도 작업**으로만 돈다 `[contract]` 공통 규칙, `[spec]` W5 | NFR10.4 |
| 4 | **기동이 무거워짐** — 기동 시 하는 일이 늘면 재기동 60초 목표를 넘긴다 | 기동 흐름에 **스키마 적용을 넣지 않는다** `[spec]` W1. 제공자는 결정된 모드의 것만 만든다 | NFR10.1 |

**네 가지 모두 "빠르게 만드는" 설계가 아니라 "느려질 수 없게 하는" 설계다.** 목표가 넉넉한 프로젝트에서 성능
설계의 형태는 이렇다.

## 3. 자원 재사용

| 자원 | 설계 | 근거 |
|---|---|---|
| 저장소 연결 | 연결 풀을 쓴다. 요청당 하나를 풀에서 빌려 쓰고 돌려준다 `[practices]` | 요청마다 새로 연결하면 왕복 비용이 200ms 예산을 잠식한다 |
| 제공자 호출 | HTTP 연결을 재사용한다(호출마다 새 클라이언트를 만들지 않는다) | 연결 수립 비용이 반복된다 |
| 설정 객체 | 기동 시 한 번 만들어 주입한다 `[rules]` BR1.3 | 매 요청 환경변수 파싱은 낭비이자 값이 갈릴 위험이다 |
| 프롬프트 파일 | 기동 시 또는 첫 사용 시 한 번 읽는다 | 호출마다 디스크를 읽을 이유가 없다 |

**연결 풀 크기는 이 단계에서 정하지 않는다** — 동시 사용자 1명 기준이라 기본값으로 충분하고, 근거 없는 수치를
박는 것보다 낫다. 인프라 설계(3.4)가 컨테이너 자원을 정할 때 함께 본다.

## 4. 두지 않는 것

| 일반적인 성능 설계 | 이번 범위 | 이유 |
|---|---|---|
| 캐시 계층 | 없음 | 저장소 질의 한 번이 이미 목표 안이다. 캐시는 무효화라는 새 문제를 들여온다 |
| 읽기 전용 복제본 | 없음 | 읽기 부하가 없다 |
| 데이터 분할 | 없음 | 데이터가 수십 건 규모다 |
| 내용 전송망 | 없음 | 로컬이다 |
| 부하 시험 도구 | 없음 | 통합 테스트의 경과 시간 단언으로 대신한다 `[nfr]` |

---

## 5. 목표를 지키는지 어떻게 아는가

상시 감시가 없으므로 **테스트가 성능 회귀를 잡는 유일한 장치**다 `[nfr]`.

| 확인 | 어디에 |
|---|---|
| 헬스체크·사용자 조회·동의가 각각 200ms 이내 | 세 통합 테스트에 경과 시간 단언 한 줄씩 |
| 재기동 후 헬스체크 통과까지 60초 이내 | 리허설에서 잰다 |
| N+1 이 생기지 않음 | 관계 기본값이 즉시 예외로 터지므로, 실수한 코드는 테스트에서 **실패로** 드러난다 |
| 연결이 새지 않음 | 통합 테스트 반복 실행 후 연결 수가 늘지 않는지 확인 |

세 번째 줄이 이 설계의 핵심이다 — 성능 문제를 성능 시험이 아니라 **기능 테스트가 잡는다**.
