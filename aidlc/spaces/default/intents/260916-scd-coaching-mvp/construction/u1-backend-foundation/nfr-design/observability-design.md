## 1. 로그 한 줄의 모양

`[Q2]` 의 답에 따라 모든 로그 줄이 공통으로 갖는 필드는 **여섯 개**다.

| 필드 | 무엇 | 언제 빈 값이 되는가 |
|---|---|---|
| 시각 | 사건이 일어난 시각 | 없음 — 항상 있다 |
| 수준 | 오류 / 경고 / 정보 / 진단 | 없음 |
| 메시지 | 사람이 읽는 한 문장 | 없음 |
| 컴포넌트 | `conversation`, `assessment`, `training`, `record`, `account`, `privacy`, `common`, `providers` 중 하나 | 없음 — 모든 로그 호출이 넘긴다 |
| 요청 식별자 | 이 줄을 낳은 요청의 식별자 | 요청 밖에서 도는 작업의 로그에서는 그 작업을 낳은 요청의 값 |
| 작업 식별자 | 응답 이후에 도는 작업의 자기 식별자 | 요청 경로의 로그에서는 비어 있다 |

**두 식별자를 나눈 이유**는 요구사항이 정했다 `[nfr]` NFR12.6 — 작업 한 번이 한 묶음이 되면서도 원래 요청으로
거슬러 갈 수 있다. 이 설계는 그것을 **필드 두 개**로 표현한다.

### 1.1 컴포넌트 필드가 필수인 이유

`[Q2]` 의 B 를 고른 대가는 "모든 로그 호출이 컴포넌트를 넘겨야 한다"는 것이다. 이 비용을 구조로 줄인다.

```
common/logging.py
    |
    +-- get_logger(component="conversation")  <- 모듈마다 한 번 부른다
            |
            v
        그 로거로 남긴 모든 줄에 컴포넌트가 자동으로 붙는다
```

<!-- Text fallback: 공통 로깅 모듈이 컴포넌트 이름을 받아 로거를 만들어 주고, 각 모듈은 그 로거를 한 번 만들어 쓴다. 그 로거로 남긴 모든 줄에 컴포넌트 필드가 자동으로 붙으므로, 로그 호출마다 컴포넌트를 적을 필요가 없다. -->

| 설계 결정 | 근거 |
|---|---|
| 컴포넌트는 **로거를 만들 때 한 번** 넘기고, 이후 호출마다 넘기지 않는다 | 모든 호출에 적게 하면 빠뜨리는 자리가 생긴다 |
| 허용값을 여덟 개로 고정한다 | 자유 문자열이면 `conv`/`conversation`/`Conversation` 으로 갈라진다 — 팀 관행이 경계하는 이름 분기다 `[practices]` |

### 1.2 두 식별자가 자동으로 붙는 구조

```
[요청 도착]
   |
   +-- 미들웨어가 요청 식별자를 발급해 요청 문맥에 넣는다
   |
   +-- 이 요청 안의 모든 로그 줄에 그 값이 자동으로 붙는다
   |
   +-- 응답에도 같은 값을 싣는다 (오류 봉투의 request_id)
   |
[응답 나감 — 요청 문맥 종료]
   |
   +-- 예약된 작업이 시작
         |
         +-- 작업이 자기 식별자를 발급해 작업 문맥에 넣는다
         +-- 자신을 낳은 요청의 식별자를 함께 담는다
         |
         +-- 이 작업 안의 모든 로그 줄에 두 값이 자동으로 붙는다
```

<!-- Text fallback: 요청이 도착하면 미들웨어가 요청 식별자를 발급해 요청 문맥에 넣고, 그 요청 안의 모든 로그와 오류 응답에 같은 값이 붙는다. 응답이 나가면 요청 문맥이 끝난다. 이후 예약된 작업이 시작되면 자기 식별자를 새로 발급하고 자신을 낳은 요청의 식별자를 함께 담아, 그 작업 안의 모든 로그 줄에 두 값이 자동으로 붙는다. -->

| 설계 결정 | 근거 | 요구사항 |
|---|---|---|
| 식별자를 **문맥에 넣고 로그가 자동으로 읽는다**. 로그 호출마다 넘기지 않는다 | 넘기게 하면 빠뜨리는 자리가 생기고, 빠뜨려도 드러나지 않는다 | NFR12.5, NFR12.6 |
| 작업은 요청의 값을 **인자로 받아** 자기 문맥에 담는다 | 요청 문맥은 이미 끝나 있어 읽을 수 없다 `[spec]` W5 | NFR12.6 |
| 오류 봉투의 `request_id` 는 같은 문맥에서 읽는다 | 사용자가 본 값과 로그의 값이 어긋날 수 없다 | NFR12.5 |

## 2. 전사 본문이 로그에 들어갈 수 없게 한다

요구사항은 "남기지 않는다"를 정했다 `[nfr]` NFR12.8. 설계는 **넣을 수 있는 자리를 없앤다**.

| 설계 결정 | 근거 |
|---|---|
| 제공자 감싸기 장치가 **요청 본문을 로그에 넘기지 않는다** — 메타데이터만 받는다(`security-design.md` §2) | 전사가 로그 함수에 도달하는 경로가 없어진다 |
| 오류를 로그에 남길 때 **예외 객체를 통째로 넘기지 않고** 메시지와 종류만 넘긴다 | 제공자 예외가 요청 본문을 품고 있을 수 있다 |
| 진단 수준(기본 꺼짐)에서도 전사를 남기지 않는다 | "개발 중에만 켠다"가 시연 환경에서 켜져 있을 수 있다 |

## 3. 반드시 로그가 남는 자리 — 설계된 위치

요구사항이 일곱 지점을 정했다 `[nfr]`. 설계는 **각 지점이 어느 코드 자리에 붙는지**를 정한다.

| 시점 | 어느 자리가 남기는가 | 컴포넌트 |
|---|---|---|
| 분석 모드 결정 | 기동 흐름의 모드 결정 지점 (`security-design.md` §1.1) | `common` |
| live 기동 거부 | 같은 지점 | `common` |
| 기동 완료 | 앱 조립이 끝난 직후 | `common` |
| 요청 수신·완료 | 요청 식별자를 발급하는 **같은 미들웨어** | `common` |
| 응답 이후 작업 시작·성공·실패 | 작업 단위 장치(`reliability-design.md` §2) | 그 작업이 속한 컴포넌트 |
| 제공자 호출 | 공용 호출 감싸기 장치 | `providers` |
| 처리되지 않은 예외 | 공통 예외 처리기 | `common` |

**일곱 자리 중 다섯이 U1 이 만드는 공통 장치 안에 있다.** 기능 단위는 자기 업무 로그만 더하면 되고, 위 다섯은
공짜로 얻는다 — 이것이 기반 단위가 관찰 가능성에 기여하는 방식이다.

## 4. 헬스체크 설계

```
GET /api/v1/health
   |
   +-- 저장소에 가벼운 확인 질의 (시간 제한 1초)
   |      |
   |      +-- 응답  --> status: ok
   |      +-- 시간 초과 / 실패 --> status: ok 아님
   |
   +-- 응답에 현재 분석 모드를 함께 싣는다
```

<!-- Text fallback: 헬스체크 요청이 오면 저장소에 1초 시간 제한을 건 가벼운 확인 질의를 보낸다. 응답이 오면 정상, 시간을 초과하거나 실패하면 정상이 아니라고 답한다. 어느 경우든 응답에 현재 분석 모드를 함께 싣는다. -->

| 설계 결정 | 근거 | 요구사항 |
|---|---|---|
| 확인 질의에 **1초 시간 제한**을 건다 | 저장소가 매달릴 때 헬스체크까지 매달리면 컨테이너 준비 확인이 멈춘다 | NFR10.15 |
| 분석 모드는 **설정 객체에서 읽는다**(다시 판별하지 않는다) | 기동 시 정해진 값과 알리는 값이 같아야 한다 | NFR10.11, `[rules]` BR1.3 |
| 헬스체크는 **인증을 요구하지 않는다** | 컨테이너 확인이 부를 수 있어야 한다 | `[contract]` C1 |
| 헬스체크 자체의 로그는 **남기지 않는다**(실패할 때만 남긴다) | 주기적으로 불리므로 매번 남기면 로그가 그것으로 덮인다 | — |

마지막 줄은 이 단계가 새로 정한 것이다. 요구사항은 헬스체크 로그를 다루지 않았다.

## 5. 이번 범위에서 만들지 않는 것 — 그리고 그 자리에 무엇을 두는가

이 프로젝트에는 클라우드도, 상시 감시도, 경보 받을 사람도 없다 `[nfr]`. 지원 관점으로 함께 본 플랫폼 지식은
클라우드 서비스를 전제로 하므로 그대로는 적용되지 않는다. 적용되는 부분만 옮긴다.

| 일반적인 관찰 가능성 요소 | 이번 범위 | 그 자리를 무엇이 대신하는가 |
|---|---|---|
| 지표 수집·대시보드 | 없음 | 통합 테스트의 경과 시간 단언(`performance-design.md`) |
| 경보 | 없음 | 화면의 실패 표시 + 사람이 옆에 있음 |
| 분산 추적 | 없음 | 요청·작업 식별자 두 값 (§1.2) — 서비스가 하나라 이것으로 충분하다 |
| 로그 중앙 수집·보관 정책 | 없음 | 표준 출력 + 컨테이너 로그 |
| 상태 확인 | **있음** | 헬스체크 (§4) — 컨테이너 준비 확인이 실제로 쓰는 유일한 지점 |
| 구조화 로그 | **있음** | §1 — 나중에 수집기를 붙이면 그대로 읽힌다 |

**나중을 막지 않는 선택**: 로그를 구조화해 표준 출력에 내는 것은 수집기를 붙이는 날 앱을 고치지 않아도 되게
한다. 이것이 이번 범위에서 비용 없이 남겨 두는 선택지다.

## 6. 되짚기 시나리오가 실제로 통하는지 — 설계로 재확인

요구사항 문서가 시나리오를 적었다 `[nfr]` §4. 설계가 그 다섯 단계를 실제로 가능하게 하는지 대조한다.

| 시나리오 단계 | 이 설계의 어느 부분이 가능하게 하는가 |
|---|---|
| 1. 헬스체크로 모드·저장소 확인 | §4 |
| 2. 업로드 요청 로그 찾기 | §1.2 미들웨어가 요청마다 남긴다, §3 |
| 3. 요청 식별자로 전사 작업 로그 잇기 | §1.2 — 작업이 요청 식별자를 함께 담는다 |
| 4. 실패 사유 갈라 보기 | §3 — 작업 단위 장치가 실패를 남긴다, `[rules]` BR7.5 의 사유 값 |
| 5. 제공자 호출의 모델명·시간 보기 | `security-design.md` §2 의 감싸기 장치 |

다섯 단계 전부 **U1 이 만드는 공통 장치 안에서** 해결된다. 기능 단위가 따로 할 일이 없다.

## Assumptions & Open Questions

### 가정

- 요청 문맥과 작업 문맥에 값을 넣고 로그가 자동으로 읽는 구조는 사용하는 언어·프레임워크가 그런 문맥 저장을
  제공한다는 전제에서 나왔다. 제공하지 않으면 코드 작성 단계에서 명시적 전달로 바꾸되, 그 경우 빠뜨림을 막는
  수단을 함께 정한다.

### 열린 질문

없다. 이 문서의 결정은 이번 범위 안에서 닫혀 있다.
