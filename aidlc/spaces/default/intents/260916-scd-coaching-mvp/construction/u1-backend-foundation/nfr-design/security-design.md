## 1. 안전한 기본값을 구조로 만든다

이 단위의 보안은 "전사가 밖으로 나가지 않게 하는 것"으로 수렴한다 `[nfr]`. 그것을 지키는 설계는 **분석 모드
결정을 한 곳에 모으고, 그 결정이 끝난 뒤에만 제공자 객체가 존재하게 하는 것**이다.

### 1.1 제공자 선택 흐름

```
기동
 |
 +-- 설정 읽기 (한 번)
 |
 +-- 분석 모드 결정 ------+-- 값 없음 / 빈 값 / 모르는 값 --> mock  (그 사실을 로그에 남김)
 |                        |
 |                        +-- "mock" --------------------> mock
 |                        |
 |                        +-- "live" --> 키 확인 --+-- 있음 --> live
 |                                                 |
 |                                                 +-- 없음 --> 기동 중단 (어떤 키가 없는지 로그)
 |
 +-- 결정된 모드의 제공자 객체만 만든다
 |
 +-- 앱 조립 (요청 받기 시작)
```

<!-- Text fallback: 기동하면 설정을 한 번 읽고 분석 모드를 결정한다. 값이 없거나 비었거나 모르는 값이면 mock 으로 정하고 그 사실을 로그에 남긴다. "mock" 이면 mock 이다. "live" 면 키를 확인해, 키가 있으면 live 제공자를, 없으면 기동을 중단하고 어떤 키가 없는지 로그에 남긴다. 결정된 모드의 제공자 객체만 만든 뒤 앱을 조립하고 요청을 받기 시작한다. -->

### 1.2 이 구조가 막는 것

| 설계 결정 | 무엇을 구조적으로 불가능하게 하는가 | 요구사항 |
|---|---|---|
| 분석 모드 결정이 **기동 시 한 번, 한 곳에서만** 일어난다 | 실행 중에 모드가 갈리는 일. 헬스체크가 알린 값과 실제 동작이 어긋나는 일 | NFR5.1, `[rules]` BR1.3 |
| 결정된 모드의 **제공자 객체만 만든다** | `mock` 모드에서 `live` 구현이 불러와지는 일 | NFR5.3 |
| 인터페이스를 `service/ports.py` 에 두고 구현체를 `providers/` 에 둔다 `[practices]` | `service` 가 `providers` 를 import 하면서 `live` 구현이 딸려 들어오는 일 | NFR5.3, `[contract]` C14 |
| `live` 키 부재는 **기동 중단** | 키 없이 떠서 첫 사용자 요청에서 터지는 일 | NFR5.2 |

**핵심**: `mock` 모드로 뜬 프로세스 안에는 **외부로 나가는 경로를 가진 객체가 존재하지 않는다.** 실수로
호출할 대상 자체가 없다.

## 2. 제공자 호출을 한 자리로 모은다

`[Q1]` 의 답에 따라, 모든 제공자 호출은 U1 이 제공하는 **공용 감싸기 장치** 하나를 지난다.

```
service 계층
    |
    | 인터페이스(SttProvider / LlmProvider)로만 부른다
    v
providers/ 의 어댑터
    |
    | 반드시 이 장치를 지난다
    v
+---------------------------------------------+
|  공용 호출 감싸기                            |
|  1. 소요 시간 재기 시작                      |
|  2. 연결 타임아웃 5초 / 읽기 타임아웃 60초    |
|  3. 실제 호출                                |
|  4. 타임아웃·연결 실패면 1회만 재시도         |
|  5. 4xx 는 재시도하지 않음                   |
|  6. 제공자 예외 -> 앱 오류로 변환             |
|  7. 로그: 모델명·프롬프트 버전·소요 시간·식별자 |
+---------------------------------------------+
    |
    v
외부 제공자 (live 에서만)
```

<!-- Text fallback: service 계층은 인터페이스로만 제공자를 부른다. providers 의 어댑터는 반드시 공용 호출 감싸기 장치를 지나며, 그 장치가 소요 시간 측정, 연결 5초·읽기 60초 타임아웃, 실제 호출, 타임아웃·연결 실패 시 1회 재시도, 4xx 재시도 안 함, 제공자 예외를 앱 오류로 변환, 모델명·프롬프트 버전·소요 시간·식별자 로그를 담당한다. -->

| 설계 결정 | 근거 | 요구사항 |
|---|---|---|
| 네 가지(타임아웃·재시도·시간 측정·로그)를 한 장치에 모은다 | 같은 규칙을 네 어댑터에 쓰면 한 곳이 빠뜨려도 드러나지 않는다 `[Q1]` | NFR13.3~13.5, NFR12.7 |
| 제공자 예외를 **이 장치의 경계에서** 앱 오류로 바꾼다 | 위쪽 코드가 제공자를 모르게 되어 Mock↔live 교체가 보이지 않는다 `[contract]` C14 | NFR13.5 |
| 어댑터가 이 장치를 거치는지 **검사로 지킨다** — 어댑터가 HTTP 도구를 직접 import 하지 못하게 린터 규칙으로 막는다 | "반드시 거친다"가 사람의 주의력이 아니라 검사가 된다 | NFR13.3 |

**로그에 전사 본문이 들어가지 않는 것도 이 자리에서 구조로 지킨다** — 감싸기 장치는 요청 본문을 받지 않고
**메타데이터(모델명·프롬프트 버전·식별자)만** 로그에 넘긴다 `[nfr]` NFR12.1.

## 3. 프롬프트에서 전사를 격리한다

TC-08 은 Mock 경로에서 살아남는 유일한 보안 속성이다 — Mock 은 전사를 읽지 않으므로, 시연이 통과해도 이
속성이 지켜졌다는 증거가 되지 않는다 `[practices]`. 그래서 **구조와 테스트 둘 다로** 지킨다.

### 3.1 프롬프트 조립 구조

```
프롬프트 파일 (app/prompts/assess_v1.md)
    |  지시문 영역 — 고정, 사람이 쓴 것
    |
    +-- [데이터 블록 시작 구분자]
    |       전사 발화들  <- 여기에만 들어간다
    |   [데이터 블록 끝 구분자]
    |
    +-- 지시문 영역은 데이터 블록 뒤에 다시 열리지 않는다
```

<!-- Text fallback: 프롬프트 파일은 사람이 쓴 고정 지시문 영역과, 구분자로 감싼 데이터 블록 하나로 이루어진다. 전사 발화는 그 데이터 블록 안에만 들어가고, 데이터 블록 뒤에 지시문 영역이 다시 열리지 않는다. -->

| 설계 결정 | 근거 | 요구사항 |
|---|---|---|
| 전사를 넣기 전에 **구분자 시퀀스를 이스케이프**한다 | 데이터가 구분자를 포함할 수 있으면 그 구분자는 경계가 아니다 `[practices]` | NFR6.6 |
| 지시문 영역이 데이터 블록 **하나뿐**이고 그 뒤에 다시 열리지 않는다 | 전사 안의 지시문처럼 생긴 문장이 지시로 읽힐 자리를 없앤다 | NFR6.6 |
| 프롬프트 버전을 **파일 이름에서 뽑는다**(`assess_v1.md` → `assess`, `v1`) `[practices]` | 코드가 버전 문자열을 따로 들면 저장하는 값과 어긋난다 | `[contract]` C14 |
| 조립 함수는 **전사를 인자로 받는 순수 함수**로 둔다 | 테스트가 외부 호출 없이 조립 결과만 검사할 수 있다 | NFR6.6 의 확인 방법 |

### 3.2 이 속성을 지키는 테스트 두 건

요구사항이 이미 정한 두 건이다 `[nfr]` NFR6.6. 설계가 그것을 **가능하게** 만든 것이 §3.1 의 마지막 줄이다.

1. 전사에 주입 문구가 들어간 경우 → 렌더 결과에서 그 문장이 데이터 블록 **안**에 있고 지시문 영역이 하나뿐임을 단언
2. 전사에 구분자 문자열 자체가 들어간 경우 → 렌더 결과에 구분자가 여는 것·닫는 것 각 1회만 남거나 이스케이프된 형태로만 남음

## 4. 신뢰하지 않는 입력의 경계

```
[브라우저]
    |  (1) 요청
    v
+------------------------+
| API 계층                |  <- 검증이 일어나는 유일한 자리
|  요청 모델로 파싱·검증   |
|  실패 -> 422 + details  |
+------------------------+
    |  검증을 통과한 타입 있는 값만 내려간다
    v
service 계층 (다시 검증하지 않는다)
    |
    v
repository 계층
```

<!-- Text fallback: 브라우저의 요청은 API 계층에서 요청 모델로 파싱·검증되고, 실패하면 422 와 details 를 돌려준다. 검증을 통과한 타입 있는 값만 service 계층으로 내려가며, service 와 repository 는 다시 검증하지 않는다. -->

| 설계 결정 | 근거 | 요구사항 |
|---|---|---|
| 검증은 **경계에서 한 번**. 통과한 값은 안에서 다시 검증하지 않는다 | 도메인 코드가 검증으로 어지러워지지 않고, 검증 규칙이 한 자리에 모인다 | NFR6.8 |
| 모든 라우트에 **응답 모델을 선언**한다 `[practices]` | ORM 객체가 응답으로 새는 일을 구조적으로 막는다 | `[practices]` 금지 규칙 |
| 외부 제공자의 출력도 **같은 경계 취급** — 저장 전에 응답 모델로 검증하고, 맞지 않으면 강제 변환하지 않고 거부 | 제공자 출력은 신뢰하지 않는 입력이다 | NFR6.7 |

### 4.1 오류 봉투의 `details`

`[Q4]` 의 답에 따라 `details` 는 **입력 검증 실패에만** 쓰고, 그 밖의 오류에서는 빈 배열이다.

| 상황 | `code` | `details` |
|---|---|---|
| 입력 검증 실패 (422) | `VALIDATION_ERROR` | `[{"field": "<입력 이름>", "reason": "<한국어 사유>"}]` — 틀린 항목마다 한 줄 |
| 그 밖의 모든 오류 | 각 상황의 영어 고정 토큰 | `[]` (빈 배열) |

- 이 선택이 좁히는 것: **내부 정보가 새어 나갈 통로**. 검증 실패는 클라이언트가 보낸 값에 대한 것이라 돌려줘도
  새로 드러나는 내부 정보가 없다 `[Q4]`.
- `reason` 은 사람이 읽는 문구이므로 한국어다 `[practices]`. `field` 는 화면이 분기하는 값이라 입력 이름
  그대로다.
- 처리되지 않은 예외(500)는 `details` 가 비고, `message` 는 U1 이 채우는 한국어 기본 문구이며 내부 메시지를
  담지 않는다 `[nfr]` NFR6.9, NFR8.1, NFR7.1.

## 5. 비밀값이 존재하지 않게 한다

가장 강한 보안 설계는 지킬 비밀값을 만들지 않는 것이다.

| 설계 결정 | 근거 | 요구사항 |
|---|---|---|
| 제공자가 미정인 동안 **어느 환경 파일에도 실제 키를 넣지 않는다.** `live` 구현체는 만들되 키 없이 둔다 | 키가 존재하지 않는 기간에는 유출될 키도 없다 `[practices]` | NFR6.5 |
| 예시 환경 파일의 값 자리는 비우거나 `<발급받은-키>` 로 둔다. **실제 키를 닮은 더미를 넣지 않는다** | 나중에 붙일 스캐너가 매번 그 줄에서 걸려 경보가 무시되기 시작한다 `[practices]` | NFR6.4 |
| 저장소 준비 순서를 지킨다 — 무시 규칙 추가 → 저장소 만들기 → 첫 추가 `[practices]` | 한 번 커밋에 들어간 키는 무시 규칙으로 지워지지 않는다 | NFR6.3 |
| 린터의 보안 규칙(`S105`/`S106`)이 하드코딩된 비밀값 후보를 잡는다 `[practices]` | 도구를 늘리지 않고 정적 검사를 얻는다 | NFR6.3 |

## 6. 인증이 없는 지금, 나중을 위해 남기는 것

Must 경로는 인증 없이 고정 사용자로 돈다 `[nfr]` NFR6.1. 이것은 로컬 전용이라는 전제 위에서 **받아들인
위험**이지 빠뜨린 것이 아니다. 설계가 할 일은 **나중에 인증이 들어올 때 고칠 자리를 하나로 모아 두는 것**이다.

```
요청 --> [현재 사용자 결정 지점] --> 나머지 코드는 "사용자"만 안다
              |
              +-- 지금:    시드 고정 사용자를 돌려준다
              +-- u11 이후: 세션을 확인해 로그인한 사용자를 돌려준다
```

<!-- Text fallback: 모든 요청은 "현재 사용자 결정 지점" 하나를 지나고, 그 뒤의 코드는 사용자만 안다. 지금은 그 지점이 시드 고정 사용자를 돌려주고, 계정·로그인 단위가 들어오면 세션을 확인해 로그인한 사용자를 돌려주도록 바뀐다. |-->

| 설계 결정 | 근거 | 요구사항 |
|---|---|---|
| 현재 사용자를 결정하는 자리가 **코드에서 한 곳**이다 | u11 이 들어올 때 고칠 자리가 하나다 | NFR6.2 |
| 클라이언트가 보낸 사용자 식별자를 **읽지 않는다** | 지금 읽지 않으면 나중에 신뢰하게 될 일도 없다 | NFR6.1 |
| 나머지 코드는 그 지점이 돌려준 사용자만 안다 | 인증 방식이 바뀌어도 나머지가 영향을 받지 않는다 | NFR6.2 |

## 7. 이번 범위에서 설계하지 않는 것

| 항목 | 이유 |
|---|---|
| 권한 모델(역할 기반 등) | 사용자가 한 명이고 보호자 열람은 u12 의 몫이다 `[nfr]` |
| 전송 구간 암호화 | 로컬 전용이다. `localhost` 의 보안 컨텍스트 취급은 첫 Bolt 에서 확인한다 `[raid:A1]` |
| 저장 데이터 암호화 | 합성 데이터뿐이고 로컬 볼륨이다 |
| 요청 빈도 제한 | 사용자 5명 로컬이라 막을 대상이 없다 |
| 보안 헤더(HSTS 등) | 화면은 u2 가 만들고, 로컬 전용이라 해당 헤더가 의미를 갖지 않는다 |

## Assumptions & Open Questions

### 가정

- §1 의 "결정된 모드의 제공자 객체만 만든다"는 설계는 `live` 구현체가 import 시점에 외부 의존성을 요구할 수
  있다는 전제에서 나왔다. 그 의존성이 없어도 import 가 성공한다면 이 설계는 여전히 유효하되 위험이 줄어든다.
- §2 의 린터 규칙(어댑터가 HTTP 도구를 직접 import 하지 못하게)은 기존 규칙 집합(`TID`)으로 표현 가능하다는
  전제에서 나왔다. 표현이 어려우면 코드 작성 단계에서 대체 수단을 정한다.

### 열린 질문

없다. 이 문서의 결정은 이번 범위 안에서 닫혀 있다.
