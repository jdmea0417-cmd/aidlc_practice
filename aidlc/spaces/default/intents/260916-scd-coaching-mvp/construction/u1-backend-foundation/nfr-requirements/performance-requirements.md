목표를 쓰기 전에 어떤 조건에서 재는지를 고정한다. 조건 없는 수치는 지킬 수도 어길 수도 없다.

| 항목 | 값 |
|---|---|
| 환경 | 개발자 노트북의 Docker Compose 3 컨테이너(frontend, backend, postgres) `[req]` NFR10 |
| 부하 | 동시 사용자 1명 — 로컬 데모이며 5명이 동시에 쓰는 상황을 상정하지 않는다 `[constraint:SC-01]` |

| 백분위 | p95 — 컨테이너 첫 요청의 예열 효과가 평균을 흔들기 때문이다 |
| 재는 방법 | 통합 테스트의 경과 시간 단언. 별도 부하 시험 도구를 쓰지 않는다 `[Q2]` |

## 3. 목표를 두지 않는 것

| 항목 | 왜 두지 않는가 |
|---|---|
| 처리량(초당 요청 수) | 동시 사용자 1명 기준이라 처리량이 제약이 된 적이 없다. 목표를 두면 검증할 수 없는 수치만 남는다 |
| 첫 빌드 시간 | 네트워크와 캐시 상태에 좌우되어 지킬 수 없는 목표가 된다 `[Q5]` |
| 자원 사용량(CPU·메모리) | 로컬 노트북마다 다르고, 이번 범위에서 자원이 부족해질 시나리오가 없다 |
| live 경로 응답 시간 | 제공자가 미정이다 `[raid:D2]`. 정해지면 이 문서에 줄을 더한다 |

## 4. 성능이 나빠지면 무엇이 먼저 드러나는가

목표를 어겼을 때 사람이 알아채는 자리를 적어 둔다. 이번 범위에는 상시 감시 장치가 없기 때문이다.

1. 헬스체크가 느려지면 → 통합 테스트의 경과 시간 단언이 먼저 깨진다(NFR3.1).
2. 기동이 느려지면 → 리허설에서 60초를 넘긴다(NFR10.1). 매일 올리는 사람이 체감한다.
3. 저장소 확인 질의가 느려지면 → 헬스체크가 통과하지 못하고 컨테이너가 준비되지 않은 것으로 보인다 `[rules]` BR3.1.

## Assumptions & Open Questions

### 가정

- 동시 사용자 1명을 측정 조건으로 둔 것은 로컬 데모 전제에서 나왔다. 시연에서 여러 명이 동시에 각자 환경을
  올리는 것은 서로 독립된 환경이므로 동시 부하가 아니다.
- 200ms 는 로컬 저장소 확인 질의 한 번을 포함한 값으로 넉넉하게 잡은 것이다. 실측이 크게 밑돌면 이후 단계에서
  조일 수 있다.
