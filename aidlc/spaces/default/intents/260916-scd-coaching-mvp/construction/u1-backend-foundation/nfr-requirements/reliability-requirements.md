## 1. 이번 범위에서 가용성 목표(SLO)를 두지 않는다

**결정**: 가동률 목표, 복구 시간 목표(RTO), 복구 시점 목표(RPO), 다중화, 자동 장애 조치를 두지 않는다 `[Q3]`.

**이유** — 서비스가 상시 떠 있어야 하는 대상이 아니다. 개발자가 필요할 때 올리고 내리는 로컬 컨테이너이고
`[constraint:SC-01]`, 유일한 릴리스 사건은 2026-11-05 시연 하나다 `[constraint:OC-01]`. 가동률을 재는 기간도,
장애를 감지할 상시 장치도, 복구를 수행할 Operation 단계도 없다 `[practices]` Deployment.

**대신 이 문서가 다루는 것** — 이번 범위에서 실제로 일어나는 실패와, 그때 시스템이 어떻게 행동하는가.
로컬 데모에서 신뢰성은 "안 죽는 것"이 아니라 **"죽었을 때 사람이 바로 알고, 다시 올리면 같은 상태가 되는 것"**
이다.

### 2.5 NFR10 밑에 붙은 요구사항의 범위 — 구분선

상위 `requirements.md` 의 **NFR10 은 글자 그대로는 좁다** — "`docker compose up --build` 로 3 컨테이너가 뜨고
헬스체크 응답에 분석 모드가 포함된다". 그런데 이 문서와 확장성 문서는 NFR10.2~NFR10.4, NFR10.13~NFR10.15 처럼
그 문장을 넘어서는 요구사항을 NFR10 밑에 붙였다. 모순으로 읽히지 않게 구분선을 여기 적는다.

- **NFR10 을 이 단위가 읽는 방식**: "로컬 실행 환경에서 이 시스템이 어떻게 행동하는가". 한 명령 기동과
  헬스체크는 그 행동 중 상위 문서가 **수용 기준으로 못박은 두 가지**이고, 아래 표의 나머지는 같은 주제에
  속하지만 상위 문서가 수치로 적지 않은 것들이다.
- **상위 문장을 넓힌 것이지 바꾼 것이 아니다.** NFR10 의 두 수용 기준(AC9.1.1, AC9.3.4)은 그대로 살아 있고
  NFR10.1·NFR10.5·NFR10.6·NFR10.11·NFR10.12 가 그것을 직접 받는다.
- **넓힌 것들의 실제 출처**는 상위 NFR 이 아니라 아래다. `traceability.json` 의 NFR10 행에도 같은 사실을 적었다.

| ID | 실제 출처 |
|---|---|
| NFR10.2 (무상태) · NFR10.3 (연결 수명) | 계약 공통 규칙의 "백그라운드 작업의 DB 세션", 이 단위의 `[rules]` BR5.1~BR5.3 |
| NFR10.4 (비차단) | 계약 공통 규칙의 "오래 걸리는 작업은 접수 응답 + 상태 조회" (D-96) |
| NFR10.13 · NFR10.14 (작업 실패 기록) | `[spec]` W5 7단계, `[rules]` BR5.2·BR7.5 |
| NFR10.15 (헬스체크 질의 시간 제한) | 이 단계가 새로 정했다 — 아래 §2.6 |

**NFR13 은 넓히지 않는다.** 상위 문서가 NFR13 을 "신뢰성 — **외부 호출**"로 명시했으므로, 이 문서에서 NFR13
밑에 붙는 것은 제공자 호출에 특정된 NFR13.3~NFR13.5 뿐이다. 응답 이후 작업 일반의 실패 기록은 위 표대로
NFR10 쪽으로 옮겼다. 이 구분이 없으면 build-and-test(3.6)가 "외부 호출 시험만 있으면 NFR13 이 덮인다"고
잘못 판단하게 된다.

### 2.6 헬스체크 확인 질의의 시간 제한 — 이 단계가 닫는다

이 단위의 `functional-spec.md` 가 열린 질문 **OQ-F4("헬스체크 확인 질의의 시간 제한 값")를 이 단계에 배정**
했다. 여기서 닫는다.

- **값: 1초** (NFR10.15). 설정으로 노출한다.
- **근거**: 같은 헬스체크의 응답 목표가 200ms(p95)다(`performance-requirements.md` NFR3.1). 1초는 그 다섯 배로,
  저장소가 잠깐 느린 것과 **실제로 붙지 못한 것**을 가르기에 충분히 여유 있으면서, 컨테이너 준비 확인이
  매달리지 않을 만큼 짧다.
- **왜 인프라 설계로 넘기지 않았는가**: 이 값은 애플리케이션이 저장소에 거는 제한이지 컨테이너 구성의 값이
  아니다. 인프라 설계가 정하는 것은 컨테이너 헬스체크의 **주기와 재시도 횟수**이며(OQ-N4), 그 둘은 이 값과
  독립이다.

## 3. 이번 범위의 실패 목록과 대응

일어날 수 있는 실패를 세어 보고, 각각 무엇이 일어나는지 적었다. 표에 없는 실패는 이번 범위에서 상정하지 않은
것이다.

| 실패 | 무슨 일이 일어나는가 | 사람이 어떻게 아는가 |
|---|---|---|
| 저장소 컨테이너가 안 뜸 | 헬스체크가 통과하지 않는다 (NFR10.5) | 컨테이너 상태와 헬스체크 |
| 분석 모드 설정이 잘못됨 | 모르는 값이면 mock 으로 계속 동작, 키 없는 live 면 기동 거부 (NFR5.4) | 로그 · 컨테이너가 안 뜸 |
| 파일 저장 실패 | 전사 상태가 실패로 바뀌고 사유가 `STORAGE` 로 남는다 `[rules]` BR7.5 | 화면의 실패 표시 · 로그 |
| 전사 실패 | 전사 상태가 실패로 바뀌고 사유가 `TRANSCRIPTION` 으로 남는다 `[rules]` BR7.5 | 화면의 실패 표시 · 로그 |
| 제공자 호출이 매달림 | 타임아웃 후 최대 1회 재시도, 그 뒤 앱 오류 (NFR13.3~NFR13.5) | 화면의 실패 표시 · 로그 |
| 응답 이후 작업이 죽음 | 상태가 실패로 적히고 남는다 (NFR10.13, NFR10.14) | 화면의 실패 표시 |
| 백엔드 프로세스가 죽음 | 컨테이너가 멈춘다. 자동 재시작을 두지 않는다 | 화면이 응답하지 않음 · 컨테이너 상태 |
| 노트북이 꺼짐 | 다시 올리면 저장소 볼륨이 남아 있어 같은 상태로 돌아온다 (NFR10.6~NFR10.8) | — |

**자동 재시작을 두지 않는 것도 결정이다.** 사람이 옆에 있는 로컬 환경에서 자동 재시작은 실패를 숨기고,
같은 실패가 반복되는 것을 알아채기 어렵게 만든다.

## 4. 시연 하루의 신뢰성

유일한 릴리스 사건이 시연 하나이므로, 신뢰성의 실질적 목표는 그날 하루로 수렴한다 `[practices]` Deployment.

1. 시연 전에 `main` 을 태그로 고정하고, **새로 받은 트리에서** 처음부터 한 번 올려 성공 정의를 통과시킨다.
2. 그 확인에 헬스체크의 분석 모드가 `mock` 임을 **단언**으로 포함한다 (AC9.3.4). 눈으로 보는 것에 기대지 않는다.
3. 새로 받은 트리에 실제 값이 든 환경 파일이 **없다**는 것도 함께 확인한다 (AC9.1.4).

이 세 가지가 이번 범위에서 가용성 목표를 대신한다.

## Assumptions & Open Questions

### 가정

- 자동 재시작을 두지 않는 것은 "사람이 옆에 있다"는 전제 위에 있다. 무인 환경에서 도는 상황이 생기면 다시 본다.
- 볼륨이 남아 있으면 상태가 보존된다는 것은 로컬 Docker 의 기본 동작에 기댄다. `down -v` 는 의도적 초기화다.
