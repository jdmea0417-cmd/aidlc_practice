## 1. 이 단위의 신뢰 경계

```
[브라우저]  --(1)-->  [backend 컨테이너]  --(2)-->  [postgres 컨테이너]
                            |
                            +--(3)-->  [파일 저장소(볼륨)]
                            |
                            +--(4)-->  [STT·LLM 제공자]   ※ live 에서만
```

| # | 경계 | 이번 범위에서의 성격 |
|---|---|---|
| (1) | 브라우저 → backend | **신뢰하지 않는 입력.** 인증은 없고(Must 경로는 고정 사용자) 입력 검증이 유일한 방어다 |
| (2) | backend → 저장소 | 컨테이너 네트워크 내부. 자격 증명은 환경변수로만 전달한다 |
| (3) | backend → 파일 저장소 | 로컬 볼륨. 경로는 설정값이고 저장소 밖으로 나가지 않는다 |
| (4) | backend → 외부 제공자 | **전사 텍스트가 제3자에게 나가는 유일한 경로.** 기본 경로에서는 쓰지 않는다 |

## 2. 요구사항

### 2.1 인증·권한

| ID | 상위 | 요구사항 | 확인 방법 |
|---|---|---|---|
| NFR6.1 | NFR6 | Must 경로는 인증을 요구하지 않고 서버가 시드 고정 사용자로 처리한다. 클라이언트가 보낸 사용자 식별자를 신뢰하지 않는다 `[rules]` BR2.3 | 사용자 식별자를 요청에 실어도 무시되는지 통합 테스트 |
| NFR6.2 | NFR6 | 계정·로그인(u11)이 들어오면 이 자리가 세션 확인으로 바뀐다. U1 은 그 교체 지점을 한 곳으로 유지한다 `[contract]` 공통 규칙 | 사용자 결정 지점이 코드에서 한 곳인지 검토 |

이번 범위에 권한 모델(역할 기반 등)은 없다. 사용자가 한 명이고 보호자 열람은 u12 의 몫이다.

### 2.2 비밀값

| ID | 상위 | 요구사항 | 확인 방법 |
|---|---|---|---|
| NFR6.3 | NFR6 | API 키와 저장소 자격 증명은 backend 컨테이너의 환경변수로만 다룬다. 코드·저장소에 넣지 않는다 `[rules]` BR6.4 | 저장소 검색으로 키 패턴 0건 |
| NFR6.4 | NFR6 | 저장소에는 예시 환경 파일만 두고, 값 자리는 비우거나 설명 문구로 둔다. **실제 키를 닮은 더미를 넣지 않는다** `[practices]` | 새로 받은 트리에 실제 값이 든 환경 파일 없음 (AC9.1.4) |
| NFR6.5 | NFR6 | 제공자가 미정인 동안 어느 환경 파일에도 실제 키를 넣지 않는다. `live` 구현체는 만들되 키 없이 둔다 `[practices]` Deployment | 리허설 확인 |

### 2.3 안전한 기본값 (fail closed)

| ID | 상위 | 요구사항 | 확인 방법 |
|---|---|---|---|
| NFR5.1 | NFR5 | 분석 모드가 미설정·빈 값·모르는 값이면 `mock` 으로 동작한다. 절대 `live` 로 흘러가지 않는다 `[rules]` BR1.1 | 세 경우 단위 테스트 (AC9.1.2) |
| NFR5.2 | NFR5 | `live` 인데 필요한 키가 없으면 **기동을 거부**한다. 조용히 `mock` 으로 되돌아가지 않고 첫 요청까지 미루지 않는다 `[rules]` BR1.2 | 기동 거부 단위 테스트 (AC9.1.3) |
| NFR5.3 | NFR5 | `mock` 모드에서 `live` 구현이 불러와지지 않는다. 인터페이스를 구현체와 같은 자리에 두지 않는다 `[spec]` W1 4단계, `[contract]` C14 | live 의존성이 없는 환경에서 mock 기동이 성공하는지 확인 |

### 2.4 신뢰하지 않는 입력

| ID | 상위 | 요구사항 | 확인 방법 |
|---|---|---|---|
| NFR6.6 | NFR6 | 전사 텍스트는 프롬프트에서 구분자로 감싼 데이터 블록으로만 전달한다. 넣기 전에 전사에서 구분자 시퀀스를 제거하거나 이스케이프한다 `[contract]` C14 | 프롬프트 조립 단위 테스트 2건 — (a) 주입 문구가 데이터 블록 안에 있고 지시문 영역이 하나뿐, (b) 구분자를 포함한 전사에서 구분자가 여는 것·닫는 것 각 1회만 남거나 이스케이프됨 |
| NFR6.7 | NFR6 | 외부 제공자의 출력은 신뢰하지 않는 입력이다. 저장 전에 응답 모델로 검증하고, 맞지 않으면 강제 변환하지 않고 거부한다 `[practices]` Code Style | 계약 위반 응답을 넣었을 때 거부되는지 단위 테스트 |
| NFR6.8 | NFR6 | 모든 경계 입력은 처리 전에 검증한다 — 형식, 길이, 허용값. U1 은 이 규칙이 적용될 자리(요청 모델, 설정 파싱)를 만든다 | 응답 모델 선언이 모든 경로에 있는지 검토 |

### 2.5 흘리지 않기

| ID | 상위 | 요구사항 | 확인 방법 |
|---|---|---|---|
| NFR12.1 | NFR12 | 로그에 전사 본문을 남기지 않는다. 제공자 호출 로그에는 모델명·프롬프트 버전·소요 시간·식별자만 남긴다 `[rules]` BR6.3 | 로그 검사 — 전사 본문 0건 |
| NFR6.9 | NFR6 | 처리되지 않은 예외는 공통 오류 봉투로 나가되 내부 메시지를 노출하지 않는다. 스택은 로그에만 남긴다 `[practices]` Code Style | 예외 주입 시 응답에 내부 정보가 없는지 통합 테스트 |
| NFR8.1 | NFR8 | U1 이 만드는 공통 예외 처리기가 내는 **미처리 예외의 기본 메시지는 한국어**다. 봉투의 `code` 는 영어 고정 토큰으로 두고 `message` 만 한국어다 `[practices]` Code Style | 예외 주입 시 응답의 `message` 가 한국어인지 통합 테스트 |
| NFR7.1 | NFR7 | 그 기본 메시지에 금지 표현("사회성 부족", "정상/비정상", "점수", "진단", "치료", "상대의 진짜 마음", "정답", "실패했어요")이 들어가지 않는다 `[req]` NFR7 | 기본 메시지를 금지 표현 목록으로 검사해 0건 |
| NFR11.1 | NFR11 | 시드와 픽스처는 합성 데이터만 담는다. 실제 사용자 데이터를 넣지 않는다 `[req]` NFR11 | 시드·픽스처의 출처가 `docs/input/05_synthetic-test-data.md`·`06_seed-scenarios.md` 뿐인지 확인 |

**NFR7·NFR8 이 이 단위에 걸리는 범위** — 이 단위는 화면 문구를 만들지 않는다. 그러나 **오류 봉투 자체를
만들고**(`[unit]` U1 정의) 미처리 예외의 기본 메시지를 공통 예외 처리기가 직접 채운다. 그 문장 하나가 사람이
읽는 문구이므로 NFR7(금지 표현)과 NFR8(한국어)의 적용 대상이다. 기능별 오류 메시지는 각 기능 단위가 채운다.

## 3. 위협 검토 (STRIDE)

이 단위의 경계에 대해 여섯 가지를 각각 물었다. 로컬 전용·합성 데이터라는 전제가 대부분의 위협을 줄이지만,
**그 전제가 깨지는 경로**가 어디인지를 적는 것이 이 표의 목적이다.

| 분류 | 이 단위에서의 위협 | 판단 | 대응 |
|---|---|---|---|
| **S** 위장 | 인증이 없어 누구나 고정 사용자로 동작한다 | **받아들인다** — 로컬 전용이고 합성 데이터뿐이다. 계정이 들어오면(u11) 달라진다 | NFR6.1·NFR6.2 로 교체 지점을 한 곳에 모아 둔다 |
| **T** 변조 | 컨테이너 네트워크는 로컬이고 외부 노출이 없다 | 낮음 | — |
| **R** 부인 | 누가 무엇을 했는지 다툴 상황이 이번 범위에 없다 | 해당 없음 | 요청 식별자가 되짚기용으로 존재한다(NFR12) |
| **I** 정보 노출 | **전사 텍스트가 제3자에게 나가는 경로가 있다** — `live` 모드. 합성 데이터가 아닌 대화에 켜면 SC-02 가 깨진다 | **가장 중요한 위협** | NFR5.1·NFR5.2 의 fail closed, NFR6.5 의 키 부재, 그리고 프로젝트 금지 규칙(`live` 를 합성 아닌 대화에 켜지 않는다) |
| **I** 정보 노출 | 로그에 전사 본문이 남는다 | 중간 | NFR12.1 |
| **I** 정보 노출 | 오류 응답이 내부 구조를 드러낸다 | 중간 | NFR6.9 |
| **D** 서비스 거부 | 사용자 5명 로컬이라 공격자가 없다 | 해당 없음 | — |
| **E** 권한 상승 | 역할·권한 모델이 이번 범위에 없다 | 해당 없음 | u11·u12 가 들어올 때 다시 본다 |

**가장 중요한 결론** — 이 단위의 보안은 사실상 **"전사가 밖으로 나가지 않게 하는 것"** 하나로 수렴한다.
그것을 지키는 장치가 NFR5.1~NFR5.3 의 fail closed 이고, 그래서 그 셋은 이 단위에서 타협 대상이 아니다.

## 4. 이번 범위에서 다루지 않는 것

| 항목 | 이유 |
|---|---|
| 규제 프레임워크 대응(개인정보 보호 규정 등) | 모든 데이터가 합성이고 실제 사용자 데이터를 수집하지 않기로 확정되었다 `[req]` NFR11. 이 전제가 깨지면 이 판단도 함께 무효가 된다 |
| 전송 구간 암호화(HTTPS) | 로컬 `localhost` 전용이다. 브라우저가 `localhost` 를 보안 컨텍스트로 취급하는지는 첫 Bolt 에서 확인한다 `[raid:A1]` |
| 저장 데이터 암호화 | 합성 데이터뿐이고 로컬 볼륨이다 |
| 의존성 취약점 상시 검사 | 검사 수단은 ci-pipeline(3.7)이 만든다. 다만 **새 의존성의 패키지 이름을 리뷰어가 확인하는 규칙**은 이미 팀 관행에 있다 `[practices]` |
| 침투 시험·동적 검사 | 외부에 노출되는 표면이 없다 |

## Assumptions & Open Questions

### 가정

- "합성 데이터만 다룬다"가 이 문서의 모든 완화 판단을 떠받친다. 이 전제가 바뀌면 §4 의 판단을 전부 다시 봐야
  한다 — 특히 규제 대응과 전송 구간 암호화.
- 인증 부재를 받아들인 것은 로컬 전용이라는 전제 위에 있다. 외부에 노출되는 순간 성립하지 않는다.
