## 1. 이번 범위에서 확장성 목표를 두지 않는다

**결정**: 이 단위에 부하 처리량, 동시 사용자 목표, 자동 확장, 용량 계획을 두지 않는다 `[Q3]`.

**이유** — 세 가지가 모두 성립하기 때문이다.

| 사실 | 근거 |
|---|---|
| 클라우드 배포가 없고 실행 대상은 개발자 각자의 로컬 컨테이너뿐이다 | `[constraint:SC-01]`, `[req]` NFR10 |
| 사용자는 5명이고 각자 자기 환경을 올린다 — 한 대에 부하가 몰리는 상황이 없다 | `[constraint:OC-01][constraint:OC-03]` |
| Operation 단계(4.1~4.7)가 전부 범위 밖이라 확장을 실행할 단계 자체가 없다 | `[practices]` Deployment |

**이것은 빠뜨린 것이 아니라 뺀 것이다.** 검증할 수 없는 수치를 적어 문서 모양만 갖추는 쪽을 택하지 않았다
`[Q3]`.

## 2. 대신 이번 범위에서 지키는 것

확장성 목표 자리에 들어가는 것은, 나중에 확장이 필요해졌을 때 **막지 않을 성질**이다. 지금 비용이 0 이면서
나중에 선택지를 남기는 것만 담았다.

| ID | 상위 | 요구사항 | 왜 지금 지키는가 | 확인 방법 |
|---|---|---|---|---|
| NFR10.2 | NFR10 | 백엔드는 요청 사이에 프로세스 안 상태를 갖지 않는다. 상태는 저장소에 둔다 | 나중에 프로세스를 여러 개 띄우는 선택지를 남긴다. 지금도 재시작이 안전해진다 | 요청 간 공유되는 가변 전역 상태가 없는지 검토 |
| NFR10.3 | NFR10 | 저장소 연결은 한 번에 하나씩 열고 닫는 장치를 거친다. 연결이 새면 즉시 드러난다 `[rules]` BR5.2 | 연결 누수는 부하가 아니라 시간이 지나면 드러나는 문제라 로컬에서도 생긴다 | 통합 테스트 반복 실행 후 연결 수가 늘지 않는지 확인 |

## 3. 데이터가 늘어나는 속도

목표는 아니지만, 이번 범위에서 데이터가 얼마나 쌓이는지는 적어 둔다 — 로컬 디스크가 찰 일이 있는지 판단하기
위해서다.

| 항목 | 이번 범위의 양 | 판단 |
|---|---|---|
| 사용자 | 1명(시드 고정 사용자) | 무시할 수 있다 |
| 합성 대화 | 3건 + 시연 중 만드는 소수 | 무시할 수 있다 |
| 음성 파일 | 대화당 최대 5분 분량 `[req]` PM-01 | 수십 MB 수준. 로컬 볼륨으로 충분하다 |
| 판정·시도 기록 | 대화·연습 횟수에 비례 | 무시할 수 있다 |

디스크 용량 감시를 두지 않는다. 필요해지는 양에 도달하지 않는다.

## 4. 나중에 확장이 필요해지면 무엇부터 봐야 하는가

이 절은 요구사항이 아니라 **인계 메모**다. Operation 단계가 범위 밖이라 이 내용을 받을 단계가 없으므로 여기
남긴다.

1. **저장소 연결 수** — 백엔드 프로세스를 늘리면 가장 먼저 부딪히는 한계다.
2. **응답 이후 작업의 실행 방식** — 이번 범위에서는 같은 프로세스 안에서 돈다 `[spec]` W5. 프로세스를 늘리면
   같은 작업이 두 번 돌지 않게 하는 장치가 필요해진다.
3. **파일 저장소** — 로컬 볼륨을 전제로 경로가 설정값이다. 공유 저장소로 옮기면 경로 규칙부터 바뀐다.
4. **분석 경로의 외부 호출** — 제공자의 요청 한도가 실질적인 상한이 된다 `[raid:D2]`.
