## Q1. 제공자가 미정인 상태에서 외부 호출 타임아웃 값을 지금 정합니까?

요구사항 문서가 이 질문을 **이 단계로 명시적으로 넘겼습니다** — 열린 질문 OQ5: "live STT·LLM 제공자(D-37)
— NFR13 의 타임아웃 값과 live 응답시간 목표, 담당 nfr-requirements(3.2), 늦어도 3.5 착수 전" `[req]`.
U1 이 제공자 인터페이스와 어댑터를 만들므로 타임아웃을 거는 자리가 여기입니다. 문제는 어느 제공자를 쓸지
아직 정해지지 않았다는 것입니다 `[raid:D2]`.

- A. **지금 설정값으로 정하고 기본값을 둔다** — 연결 5초 / 읽기 60초를 기본값으로 두고 환경변수로 바꿀 수 있게
  한다. 제공자가 정해지면 값만 바꾼다. 지금 어댑터 코드가 완결되고, 값이 틀려도 코드 변경 없이 고쳐진다
- B. **Mock 경로에만 짧은 값을 두고 live 값은 제공자 확정 때 정한다** — Mock 은 1초, live 타임아웃은 미정으로
  남겨 제공자 선택 시 채운다. 지금 확실한 것만 적지만, live 구현체가 값 없이 남아 3.5 에서 다시 열어야 한다
- C. **타임아웃 자리만 만들고 값은 전부 설정 필수로 둔다** — 기본값 없이 설정에서 반드시 읽게 하여, 값을 안 정하면
  기동이 거부된다. 빠뜨릴 수 없지만 `ANALYSIS_MODE=mock` 인 기본 실행에도 값을 넣어야 해서 첫 실행이 번거로워진다
- X. Other (please specify)

## Q2. U1 이 소유한 엔드포인트의 응답 시간 목표를 둡니까?

확정된 성능 목표는 분석 경로의 것뿐입니다(NFR3, 접수 1초·완료 3초) `[req]`. U1 이 만드는 것은 헬스체크,
현재 사용자 조회, 첫 방문 동의 세 가지인데 `[spec]` W2~W4, 이들의 목표는 어디에도 없습니다. 헬스체크는
이제 저장소 확인 질의를 포함하므로 응답이 순간적이지 않습니다.

- A. **세 엔드포인트에 하나의 목표를 둔다** — 로컬에서 200ms 이내(p95). 단순하고, 저장소 확인이 느려지는 것을
  일찍 알아챈다. 통합 테스트에 단언 한 줄씩 붙는다
- B. **헬스체크에만 목표를 둔다** — 헬스체크는 시연 리허설과 컨테이너 확인이 기대는 지점이라 목표가 의미 있지만,
  사용자 조회·동의는 화면 한 번의 호출이라 목표를 두지 않는다
- C. **목표를 두지 않는다** — 사용자 5명 로컬 데모라 성능 목표가 비용만 된다. NFR3 의 분석 경로 목표만 유지한다
- X. Other (please specify)

[Answer]: A. **세 엔드포인트에 하나의 목표를 둔다** — 로컬에서 200ms 이내(p95). 단순하고, 저장소 확인이 느려지는 것을 일찍 알아챈다. 통합 테스트에 단언 한 줄씩 붙는다

## Q3. 로컬 전용이라 비어 있는 범주(확장성·가용성)를 어떻게 적습니까?

이 단계는 확장성·신뢰성 문서를 만들게 되어 있습니다. 그런데 클라우드 배포가 없고 `[constraint:SC-01]`
사용자는 5명이며 Operation 단계가 전부 범위 밖입니다. 가용성 목표(SLO), 자동 확장, 재해 복구는 걸 대상이
없습니다. 그래도 문서는 만들어야 하므로, 무엇을 적을지 정해야 합니다.

- A. **비목표를 명시적으로 적는다** — "이번 범위에서 확장성·가용성 목표를 두지 않는다"를 이유와 함께 적고,
  대신 이번 범위에서 실제로 지켜야 할 것(한 명령 기동, 실패 시 사람이 알아채는 방법, 되돌리기)을 적는다.
  나중에 클라우드로 갈 때 무엇이 비어 있는지가 한눈에 보인다
- B. **명목 목표를 적는다** — 동시 사용자 5명, 가용성 목표 없음 같은 최소 수치를 적어 형식을 채운다.
  문서 모양은 갖춰지지만 검증할 수 없는 수치가 남는다
- C. **해당 범주 문서를 만들지 않는다** — 적을 것이 없으면 만들지 않는다. 다만 이 단계가 만들기로 한 산출물
  목록에서 두 개가 빠지고, 뒤 단계가 그것을 결손으로 읽을 수 있다
- X. Other (please specify)

[Answer]: A. **비목표를 명시적으로 적는다** — "이번 범위에서 확장성·가용성 목표를 두지 않는다"를 이유와 함께 적고, 대신 이번 범위에서 실제로 지켜야 할 것(한 명령 기동, 실패 시 사람이 알아채는 방법, 되돌리기)을 적는다. 나중에 클라우드로 갈 때 무엇이 비어 있는지가 한눈에 보인다

## Q4. 로그를 어디에 어떤 수준으로 남깁니까?

요청 식별자와 전사 본문 제외는 정해졌습니다(NFR12) `[req]`. 안 정해진 것은 **로그가 어디로 나가고, 어떤
수준이 기본이며, 얼마나 보관되느냐**입니다. 컨테이너 안에서 도는 로컬 환경이라 선택이 단순합니다.

- A. **표준 출력으로 구조화해서 내보내고 보관은 컨테이너에 맡긴다** — 한 줄에 한 건, 기계가 읽을 수 있는 형태로
  표준 출력에 쓴다. 기본 수준은 정보. 보관 정책을 앱이 갖지 않는다. `docker compose logs` 로 바로 본다
- B. **표준 출력 + 파일 둘 다** — 파일로도 남겨 시연 뒤에 되짚어 볼 수 있게 한다. 대신 파일 경로·회전·무시 규칙이
  늘고, 전사 본문이 실수로 들어가면 디스크에 남는다
- C. **사람이 읽기 좋은 평문으로 표준 출력에** — 개발 중 읽기는 가장 편하지만, 나중에 검색·집계가 어렵고
  요청 식별자로 묶어 보기가 번거롭다
- X. Other (please specify)

[Answer]: A. **표준 출력으로 구조화해서 내보내고 보관은 컨테이너에 맡긴다** — 한 줄에 한 건, 기계가 읽을 수 있는 형태로 표준 출력에 쓴다. 기본 수준은 정보. 보관 정책을 앱이 갖지 않는다. `docker compose logs` 로 바로 본다

## Q5. `docker compose up --build` 부터 쓸 수 있을 때까지의 시간 목표를 둡니까?

느리고, 이후는 캐시가 있어 빠릅니다.

- C. **목표를 두지 않는다** — 뜨기만 하면 된다. 느려지는 것을 알아챌 장치가 없어진다
