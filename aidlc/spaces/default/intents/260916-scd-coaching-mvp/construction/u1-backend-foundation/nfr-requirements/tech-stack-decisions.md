## 1. 확정된 선택 (이 단계가 다시 고르지 않는다)

| 항목 | 선택 | 확정한 결정 | 이 단위에서의 의미 |
|---|---|---|---|
| 백엔드 언어 | Python 3.11 | D-30, D-31 | 팀 배경은 React+Java 인데 Python 으로 확정되었다. Python 경험이 일부뿐인 것이 이번 프로젝트의 가장 큰 기술 위험이다 `[constraint:OC-04][raid:R1]` |
| 웹 프레임워크 | FastAPI | `docs/input/02_tech-environment.md` | 라우트는 동기 `def` 로 쓴다. 프레임워크가 스레드풀에서 돌리므로 이벤트 루프를 막지 않는다 `[practices]` |
| 패키지 관리자 | uv | **D-54** | 가상환경 활성화라는 개념이 사라져 Python 이 처음인 사람이 첫 주에 넘어지는 자리를 없앤다. 잠금 파일을 커밋하고 설치는 잠금에서만 한다 |
| ORM | SQLAlchemy 2.0 declarative — **동기** | **D-54** | 선언 스타일이 JPA 엔티티와 읽는 느낌이 가깝고 타입 검사가 그대로 이해한다. 비동기로 가면 전파·테스트 픽스처 복잡도가 따라오는데, 로컬 데모에 사용자 5명이라 동시성 요구가 없다 |
| 마이그레이션 | Alembic | **D-54** | 모델 정의에서 초안을 뽑을 수 있다. 전진 방향만 쓰고 되돌리기 스크립트는 쓰지 않는다 `[practices]` Deployment |
| 저장소 | PostgreSQL 16 | D-31 | 초기 리비전 하나로 테이블 20개를 만든다 `[contract]` C15 |
| 린터·포매터 | Ruff 하나 | **D-54** | 규칙 집합 `E, F, I, UP, B, SIM, TID, RUF, S`. `S` 를 넣어 도구를 늘리지 않고 정적 보안 검사를 얻는다 |
| 타입 검사 | mypy (`strict` 는 끄되 검사가 실제로 걸리게) | **D-54** | `app.service.*` 에만 타입 필수를 켜서 "`service/` 공개 함수는 타입 필수"가 문장이 아니라 검사가 된다 |
| 설정 | pydantic-settings | `[practices]` Code Style | 기동 시 한 번 파싱해 설정 객체 하나를 주입한다 `[rules]` BR1.3 |
| 실행 | Docker Compose 3 컨테이너 | `[constraint:TC-04]`, `[req]` NFR10 | frontend, backend, postgres |
| 테스트 | pytest, httpx 테스트 클라이언트, Testcontainers(PostgreSQL) | `[practices]` Testing Posture | 스키마는 세션 시작 시 마이그레이션으로 한 번 만든다 |

**이 단계가 확인한 것** — 위 선택들이 이 단위의 품질 요구와 충돌하지 않는다. 한 곳만 짚어 둔다: 동기 ORM 선택은
"응답 이후에 도는 작업"(전사·분석)이 요청을 막지 않아야 한다는 NFR10.4 와 부딪히지 않는다. 프레임워크가 동기
라우트를 스레드풀에서 돌리고, 응답 이후 작업은 자기 연결을 새로 열기 때문이다 `[spec]` W5, `[rules]` BR5.1.

## 2. 빠뜨리면 첫 주에 막히는 의존성

확정된 도구 목록에는 있지만 쉽게 빠지는 것들이다 `[practices]` Code Style.

| 패키지 | 왜 필요한가 |
|---|---|
| `python-multipart` | 파일 업로드 경로에 필수다. 없으면 업로드 라우트가 **기동 시점에** 죽는다 |
| `pydantic-settings` | 설정 관리가 별도 패키지로 분리되어 있다 |
| `httpx` | 테스트 도구로 이미 잡혀 있으니 제공자 호출에도 같은 것을 쓴다 |

**새 의존성을 추가하는 커밋은 리뷰어가 패키지 이름 각각을 공식 문서와 배포 페이지에서 확인한다** `[practices]`.
전원이 AI 보조로 작업하고 Python 경험이 일부뿐인 조합에서 가장 흔한 공급망 실패는 알려진 취약점이 아니라
**존재하지 않는 패키지 이름을 제안받아 설치하는 것**이다 `[raid:R1]`.

## 3. 이 단계에서 새로 정한 설정값

기술 선택이 아니라 **값**이다. 전부 설정으로 노출하고 코드에 박지 않는다 `[req]` NFR4.

| 설정 | 기본값 | 정한 근거 | 요구사항 |
|---|---|---|---|
| 분석 모드 | `mock` (미설정·빈 값·모르는 값 포함) | 기본 실행 경로가 Mock 이어야 한다 `[constraint:SC-04]` | NFR5.1 |
| 제공자 연결 타임아웃 | **5초** | 이 단계에서 새로 정했다 `[Q1]` — 제공자 미정 상태에서 넉넉하되 매달리지 않는 값 | NFR13.3, NFR4.2 |
| 제공자 읽기 타임아웃 | **60초** | 같음. 전사·판정은 수십 초가 걸릴 수 있어 연결보다 크게 잡았다 | NFR13.3, NFR4.2 |
| 제공자 재시도 횟수 | **1회** (타임아웃·연결 실패에만) | `[contract]` C14, 무한 재시도가 시연 중 화면이 멈추는 가장 흔한 원인이다 | NFR13.4 |
| 녹음 최대 길이 | 5분 | 이미 확정 `[constraint]` PM-01 | NFR4.1 |
| Mock 분석 응답 시간 목표 | 3초 | 이미 확정 `[constraint]` PM-02 | NFR4.1 |
| 비교 불충분 기준 | 유효 기회 3회 미만 | 이미 확정 `[constraint]` PM-03 | NFR4.1 |
| 원음 보관 기간 | 30일 | 이미 확정 `[constraint]` PM-04 | NFR4.1 |
| 업로드 최대 크기 | 설정값 (코드에 숫자를 박지 않는다) | `[practices]` Code Style | NFR6.8 |
| 업로드 저장 경로 | 설정값, 볼륨으로 뺀다 | `[practices]` Code Style | — |
| 로그 기본 수준 | 정보 | `[Q4]` | NFR12.4 |

**타임아웃 두 값이 이 단계의 실질적인 새 결정이다.** 요구사항 문서가 이 단계로 넘긴 열린 질문 OQ5 가 이 두
값으로 닫힌다 — 제공자가 정해지면 코드가 아니라 값만 바꾼다 `[Q1]`.

## 5. 테스트 유지보수성 요구사항

상위 NFR14("유지보수성 — 테스트")가 이 단위에 거는 것을 파생 ID 로 적는다. 테스트 도구가 §1 에 있으므로 여기
둔다.

| ID | 상위 | 요구사항 | 확인 방법 |
|---|---|---|---|
| NFR14.1 | NFR14 | 합성 대화의 전사와 기대 판정은 `backend/app/fixtures/` 의 대화별 파일 한 벌이 **단일 출처**다. Mock 제공자·백엔드 단위 테스트·프론트엔드 모의 응답·종단 시험이 모두 이 한 벌을 읽고, 값을 코드나 테스트에 옮겨 적지 않는다 `[rules]` BR4.3, `[Q<n>]` Q5 | Mock 이 각 대화 키에 대해 픽스처와 같은 값을 돌려주는지 대조 테스트 |
| NFR14.2 | NFR14 | 이 단위가 만드는 `backend/app/service/` 코드는 저장소 전체에 걸린 라인 커버리지 80% 바닥을 낮추지 않는다. 바닥 **자체의 검증은 build-and-test(3.6)**가 하고, 이 단위는 자기 코드가 그 바닥을 넘게 유지한다 `[practices]` Testing Posture (D-57) | 커버리지 리포트 |
| NFR14.3 | NFR14 | 스키마는 테스트에서도 마이그레이션으로 만든다(모델에서 직접 만들지 않는다). 그래야 마이그레이션이 실제로 한 번은 실행된다 `[practices]` Testing Posture | 테스트 세션 시작 시 마이그레이션이 적용되는지 확인 |

NFR14.1 은 `security-requirements.md` NFR11.1(합성 데이터만)과 `NFR4.1`(설정값 노출)과 이웃하지만 서로 다른
것을 말한다 — NFR11.1 은 **무엇이 들어가는가**, NFR4.1 은 **값을 코드에 박지 않는가**, NFR14.1 은 **같은 값을
여러 곳에 옮겨 적지 않는가** 이다.

## 6. 판단하기 어려웠던 자리

이 단계에서 실제로 고민한 것은 하나뿐이다 — **타임아웃 값을 지금 정할 것인가.**

| 선택지 | 받아들이는 비용 | 얻는 것 |
|---|---|---|
| **A. 지금 기본값을 둔다** (택함) | 값이 제공자에 안 맞을 수 있다 | 어댑터 코드가 지금 완결되고, 값이 틀려도 코드 변경 없이 고쳐진다. 열린 질문 OQ5 가 닫힌다 |
| B. live 값은 미정으로 남긴다 | 코드 작성 단계에서 다시 열어야 한다 | 확실한 것만 적는다 |
| C. 기본값 없이 설정 필수 | mock 기본 실행에도 값을 넣어야 해 첫 실행이 번거로워진다 | 빠뜨릴 수 없다 |

A 를 택한 근거는 값이 **설정값**이라는 점이다 `[Q1]`. 코드에 박히는 값이었다면 B 가 나았을 것이다.
