### 1.3 반드시 로그가 남는 자리

이 목록은 "어디서 실패했는지 알 수 없다"가 생기지 않도록 정한 최소 지점이다.

| 시점 | 남기는 내용 | 근거 |

| 기동 — 분석 모드 결정 | 정해진 모드, 그리고 모르는 값이어서 mock 으로 정했다면 그 사실 `[rules]` BR1.1 | AC9.1.2 |

| 기동 완료 | 기동이 끝나 요청을 받기 시작했다는 것 | NFR10.1 측정의 기준점 |
| 요청 수신·완료 | 경로, 상태 코드, 소요 시간, 식별자 | NFR12.5 |
| 응답 이후 작업 시작·성공·실패 | 작업 종류, 대상 식별자, 두 식별자, 실패 시 사유 `[spec]` W5 | NFR10.13 |

| 처리되지 않은 예외 | 스택 — **로그에만**, 응답에는 넣지 않는다 `[practices]` Code Style 오류 처리 | NFR6.9 (`security-requirements.md`) |

## 2. 헬스체크

| ID | 상위 | 요구사항 | 확인 방법 |
|---|---|---|---|

| NFR10.12 | NFR10 | 헬스체크는 저장소가 응답할 때만 정상이라고 답한다 `[rules]` BR3.1 | 저장소를 내린 상태에서 실패하는지 통합 테스트 |
| NFR10.15 | NFR10 | 저장소 확인 질의의 시간 제한은 1초다(`reliability-requirements.md` §2.6 에서 확정) | 저장소 응답을 지연시킨 상태에서 1초 뒤 실패로 답하는지 통합 테스트 |

헬스체크가 이번 범위의 **유일한 상태 조회 지점**이다. 시연 리허설이 분석 모드를 눈으로 보지 않고 단언할 수
있는 근거가 이것이다.

## 3. 이번 범위에서 두지 않는 것

| 항목 | 왜 두지 않는가 |
|---|---|
| 지표 수집과 대시보드 | 상시 떠 있는 서비스가 아니고 Operation 단계가 범위 밖이다. 수집할 기간도 볼 사람도 없다 |
| 경보 | 경보를 받을 사람과 절차가 이번 범위에 없다. 사람이 옆에 있는 로컬 환경이다 |
| 분산 추적 | 서비스가 하나다. 경계를 넘는 추적이 필요한 구조가 아니다 |
| 로그 보관 기간·색인 | 앱이 정책을 갖지 않고 컨테이너에 맡긴다 `[Q4]` |
| 로그 중앙 수집 | 각자 자기 노트북에서 본다 |

**대신 이번 범위에서 "관찰"의 실질은 이렇다** — 무엇이 잘못되면 (1) 화면에 실패 표시가 뜨고,
(2) `docker compose logs` 에 식별자로 묶인 줄이 남고, (3) 헬스체크가 현재 상태를 말한다. 이 셋이면 로컬에서
원인에 도달할 수 있다.

## 4. 되짚기 시나리오 — 이 요구사항들이 실제로 통하는지

요구사항이 충분한지 확인하는 방법은 실제 상황을 따라가 보는 것이다.

**상황**: 시연 리허설에서 "S2 를 올렸는데 전사가 안 뜬다"는 신고가 들어왔다.

1. 헬스체크를 조회한다 → 분석 모드가 `mock` 인지, 저장소가 붙어 있는지 확인된다 (NFR10.11, NFR10.12).
2. 업로드 요청의 로그를 찾는다 → 경로·상태 코드·식별자가 있다 (NFR12.5).
3. 그 요청의 식별자로 전사 작업 로그를 찾는다 → 작업이 자기 식별자와 원래 요청의 식별자를 함께 남겼으므로
   이어진다 (NFR12.6).
4. 작업 로그에 실패 사유가 있다 → 저장 실패인지 전사 실패인지 갈린다 (NFR10.13, `[rules]` BR7.5).
5. 제공자 호출이었다면 모델명·프롬프트 버전·소요 시간이 있다 → 타임아웃인지 계약 위반인지 갈린다 (NFR12.7).

다섯 단계 어디에서도 전사 본문을 읽을 필요가 없다 (NFR12.8). 이것이 이 문서가 목표한 수준이다.

## Assumptions & Open Questions

### 가정

- 표준 출력만으로 충분하다는 판단은 "사람이 옆에 있고 컨테이너 로그를 바로 본다"는 전제 위에 있다.
- 기본 로그 수준을 정보로 둔 것은 시연 중 로그가 지나치게 많아지지 않게 하기 위해서다. 개발 중에는 설정으로
  상세를 켠다.

### 열린 질문

없다. 이 문서의 결정은 이번 범위 안에서 닫혀 있다.
